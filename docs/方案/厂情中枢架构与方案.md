# 厂情中枢：架构与方案（对标 Palantir）

2026-10-05 · 状态：**架构方案，待 Eddie 确认**（确认后拆成第 17 轮各期的实施细则）

承接：数字工厂第 1–16 轮（统一数据总线、历史库、ERPNext 桥接、MES、质量、PLM、CAE / CFD / MBD / CAM、数字孪生、AI 工厂助手）。

---

## 一、我们要做的是什么

Palantir（Foundry / AIP）在制造业被看重，不在于某一个算法，而在于四件事连成了一个闭环：

| Palantir 的核心 | 一句话 | 在问渠数字工厂里对应什么 |
|---|---|---|
| **本体（Ontology）** | 把零散在各个系统里的数据，变成业务人员认得的“对象”（设备、工单、订单、零件……）和它们之间的“关系”，所有应用和 AI 都在这张图上工作 | 新建：**工厂本体**。数据来源是已有的总线历史、ERPNext、PLM、计算服务、零件库、孪生 |
| **数据集成与血缘** | 各系统的数据自动同步进本体；每个数值都能追到它从哪条原始记录来 | 已有统一数据总线和历史库，相当于一半的数据集成已经做了；新增同步器和溯源 |
| **动作（Actions）与人在回路** | 在对象上定义“能做的事”（改派、加班、采购……），带参数、校验、权限、审批，执行后写回各业务系统，全程留痕 | 已有“提议 → 确认 → 执行”，扩展成正式的**动作框架** |
| **AIP（AI 平台）** | 大模型不直接看原始数据库，而是通过本体查询、推演、起草动作这些“工具”工作；结论带引用，写操作必须人批准 | 已有 AI 工厂助手（工具调用、国内 DeepSeek / 美国 Claude），改成在本体上工作的**代理** |

再加两项 Palantir 常用于工厂的能力：
- **场景推演**（Vertex / Scenarios）：在当前状态的副本上试一组改动，比较结果；
- **运营应用**（Workshop 搭出来的“作战室”）：给厂长、计划员用的一页式指挥台。

**厂情中枢 = 工厂本体 + 异常与追因 + 场景推演 + 动作 + AI 代理 + 运营指挥台。** 它不替代前 16 轮的任何页面，而是把它们的数据连成一张图，在图上发现问题、算清影响、给出可执行的方案。

### 最能说明价值的一个故事（数字主线）

> 港口客户的一台 WQR-105 数字孪生报警：中间轴轴承 B 振动上升。
> 在中枢里点这台设备，沿着链接一路往回走：
> 现场设备 → 出厂序列号 → 总装工单 → 输出轴 SH301-00016-05 → 三坐标测量（轴承位 Ø35 k6 偏上限 2 µm）→ 加工它的外圆磨床 GRD-01 → 当时砂轮剩余寿命 23% → 同一砂轮寿命区间里磨的另外 6 根轴 → 它们装进了哪 6 台减速器、在哪些客户现场。
> AI 给出判断和依据：同批 6 台建议提前点检；同时起草两个动作：开 6 张服务工单，把磨床砂轮的修整间隔从 30 件改成 20 件。人确认后执行。

前 16 轮的数据其实都有：孪生的出厂数据里记着输出轴序列号，测量和砂轮寿命都在总线上。只是从来没有被连起来。这就是本体的意义。

## 二、总体架构

```
┌──────────────────────────── 应用层（网页） ────────────────────────────┐
│ 厂情中枢指挥台 │ 对象浏览器（任何对象的 360 页、关系图、时间线）│ 推演工作台 │
│ 动作收件箱（待我批准 / 我发起的）│ AI 对话（带引用）│ 现有各页嵌入“对象卡片” │
└───────────────▲───────────────────────────────▲────────────────────────┘
                │ 本体 API（查询 / 遍历 / 搜索）  │ 动作 API / 推演 API / AI API
┌───────────────┴──────────────── 服务层 ────────┴────────────────────────┐
│ ① 对象查询与图遍历  ② 异常检测（规则库）  ③ 影响分析（追因 / 影响面）       │
│ ④ 场景推演（仿真副本 / 解析模型）  ⑤ 动作框架（校验·权限·审批·执行·审计）    │
│ ⑥ AI 代理（工具 = ①–⑤；引用；运行记录）  ⑦ 主动提醒与复盘                    │
└───────────────▲─────────────────────────────────────────────────────────┘
                │
┌───────────────┴──────────────── 本体层 ─────────────────────────────────┐
│ 对象类型 · 属性 · 链接类型 · 时间序列 · 事件     （Postgres：对象表、链接表、 │
│ 本体定义写成声明式文件 ontology.yaml，改定义不改代码   事件表；可按时间回看）   │
└───────────────▲─────────────────────────────────────────────────────────┘
                │ 同步器（增量、可重放）＋ 映射规则 ＋ 身份解析 ＋ 血缘
┌───────────────┴──────────────── 数据源 ─────────────────────────────────┐
│ 统一数据总线历史（设备、MES、质量、物流、孪生现场、虚拟 PLC）│ ERPNext（经桥接 erp.doc）│
│ PLM（设计提交、工艺规程、数控程序）│ 计算服务（CAE/CFD/MBD/OPT/CAM 作业）│ 零件库 │ 课程任务单 │
└─────────────────────────────────────────────────────────────────────────┘
                ▲ 动作执行器回写：MES 指令（总线）· ERPNext（桥接）· PLM · 内部表
```

架构上的四条原则：

1. **本体是唯一的“业务语言”**。网页、AI、推演、动作都只认对象和链接，不直接拼 SQL 查原始消息。新增一个数据源，只需在本体里加映射。
2. **事件溯源，可回看任意时刻**。总线历史本来就是事件流，本体由它重放得到。因此可以问“昨天 14:00 车间是什么状态”，推演和复盘都依赖这一点。
3. **AI 只读本体、只起草动作**。所有写操作都走动作框架，由人批准，留审计。没配大模型时，规则版照样能用。
4. **教学和生产同一套**。教学模式的数据来自仿真车间，生产模式来自真设备和真 ERPNext；本体、应用和动作完全一样。

### 3.2 链接类型（主要的）

```
客户 ─下单→ 销售订单 ─生成→ 工单 ─包含→ 工序任务 ─在→ 设备 ─装有→ 刀具
工单 ─产出→ 零件实物 ─测得→ 测量 ─触发→ 不合格品 / 质量异常单
零件实物 ─加工于→ 工序任务（带时间，可查当时的刀具寿命）
零件实物 ─装入→ 零件实物（输出轴装进减速器总成）─出厂为→ 现场设备 ─有→ 服务工单
工单 ─需要→ 物料 ─库存→ 库存 ─来自→ 采购单 ─供应商→ 供应商
物料 ─现行版本→ 设计版本 ─分析→ 分析作业；物料 ─工艺→ 工艺规程 ─程序→ 数控程序
异常 ─涉及→（任何对象）；场景 ─基于→ 异常；动作记录 ─作用于→（任何对象）
```

### 3.3 存储与实现

- **本体定义**写在 `ontology.yaml`：对象类型、属性（类型、单位、显示名、是否时间序列）、链接类型、每个属性的映射规则（来自哪种消息、哪个字段，怎样合并）。改本体只改这个文件，同步器自动重建。
- **存储**用现有的 Postgres，不引入图数据库。教学工厂一个学期几十万条消息，对象几万个，Postgres 加内存图足够。
  - 对象表：类型、主键、属性 jsonb、版本、有效时间；
  - 链接表：起点、终点、类型、有效时间；
  - 时间序列：设备状态、库存、刀具寿命，复用历史库，按需降采样。
- **同步器**：订阅总线，增量更新本体；也能从历史库从头重放，重放结果和实时同步一致（测试核对）。每个对象和属性都记来源消息的编号，这就是血缘。
- **身份解析**：同一个东西在不同系统里的编号统一起来。例如轴承在 ERPNext 里是 BRG-6207，在零件库里是 A-BRG-DG/6207，在孪生里叫“中间轴轴承 B”，对应关系写在映射规则里。

## 四、六项核心能力

### 4.1 对象浏览器（先做，所有后面的能力都建在它上面）

- 全局搜索：输入单号、序列号、设备号、物料号、客户名都能跳到对象。
- **对象 360 页**：属性；关系图（一跳、两跳展开，可以点着走）；时间线（这个对象的所有事件，按时间排）；相关的异常、场景和动作；每个数值旁边都能点“来源”，看到原始消息。
- 对象集：按条件筛一组对象（如“本周延期风险的订单”“砂轮寿命低于 30% 时磨的轴”），可以保存、分享，也可以作为 AI 和推演的输入。

### 4.2 异常检测

规则库，每条规则都是声明式的，可以单独测试：

| 类型 | 规则（举例） |
|---|---|
| 设备 | 停机 / 故障；OEE 连续低于目标；换刀频率异常 |
| 交期 | 销售订单的预计完工晚于交期（预计完工由 4.4 的“什么都不做”推演给出） |
| 物料 | 净需求为正且到货晚于需要日期；低于安全库存 |
| 质量 | SPC 判异（超差、连续 7 点同侧、连续 6 点上升等 Western Electric 规则）；不合格率上升 |
| 成本 | 工单实际成本超标准 10% 以上 |
| 服务 | 孪生报警（散热、轴承、过载）；同一批次多台报警 |

异常是本体里的对象：有严重度、状态（新 / 处理中 / 已解决）、负责人，处理过程留痕。

### 4.3 追因与影响面（影响分析）

在本体图上做两个方向的传播：

- **往下游：影响了谁、影响多大**。停机 → 该设备上排队的工序任务 → 工单 → 订单 → 延期几天、损失多少。“多大”不靠估，而是调用 4.4 的推演，对比“有这个异常”和“假设没有这个异常”两种情况。
- **往上游：为什么**。超差 → 零件 → 加工它的工序和设备 → 当时的刀具寿命、程序版本、操作工、注入的问题情景（教学模式只给老师看）。同类异常还会和历史对比，例如“上次砂轮寿命低于 25% 时也出现过 3 次”。

结果用**因果链图**展示：每条边都写明“依据：哪条规则、哪些数据”。大模型只把链条讲成人话，不负责猜。

### 4.4 场景推演

- **场景** = 某一时刻的状态快照 + 一组改动 + 推演结果。可以保存、比较、分享，事后还能和实际发生的结果对照（复盘）。
- **推演引擎**分两种：
  - **仿真副本**（主力）：用仿真车间同一套离散事件引擎，在后台复制当前状态，用虚拟时钟快进，几秒算完几天的生产。教学模式由仿真车间直接给出精确快照；生产模式从本体重建状态（设备、队列、在制、工单、日历）。教学模式下可以拿两种快照的结果互相核对，用来验证生产模式的重建。
  - **解析模型**（快速粗算）：MRP 算料、产能负荷、成本公式，用于不需要逐件仿真的问题，比如“紧急采购提前 3 天到货，缺料解除了没有”。
- **可试的改动**（第一期）：改派到同类设备；工单插队或调序；加班（需要先给仿真车间加**班次日历**，见第七节）；紧急采购（提前到货、加急费）；外协（工序外协 N 件，费用和运输天数）；维修加急（停机时间缩短、多付费用）；什么都不做（作对照）。可以组合，一次最多比较 4 个方案。
- **输出**：每张订单的预计完工、延期天数；设备负荷甘特图；额外成本；风险提示（某设备连续满负荷、单点依赖）。

### 4.5 动作框架

每种动作是一个定义：参数、前置校验、谁能发起、谁能批准、执行器、回写到哪里、审计。

| 动作 | 执行器 | 回写 |
|---|---|---|
| 改派工序 | MES 指令 | 总线 machine.cmd |
| 调整工单顺序 | MES | 总线 |
| 安排加班 | 班次日历 | 工厂日历 + 仿真车间 |
| 紧急采购 / 外协 | 桥接 | ERPNext 采购单 |
| 开服务工单 | 桥接 | ERPNext Issue |
| 开质量异常单（8D）、改砂轮修整间隔 | 内部表 / 工艺参数 | 质量模块 / 工艺规程 |
| 下达工单、改安全库存 | MES / 桥接 | 总线 / ERPNext |

- 任何动作都可以先“试运行”：把它作为改动交给推演，看影响后再提交。
- 提交后进入**动作收件箱**，按权限批准。批准后执行，执行结果回到本体，并关联到发起它的异常和场景。
- 现有的“提议”（ai.proposal）就是动作框架的第一个实例，迁移过来，不另起炉灶。

### 4.6 AI 代理（AIP 式）

- **工具**全部是上面的能力：搜索对象、读对象、沿链接遍历、算指标、跑追因、跑推演、起草动作（只能起草）。不给大模型执行写操作的工具。
- **引用**：AI 的每个结论都附上它依据的对象和原始消息，网页上点开即可核对。
- **运行记录**：每次 AI 运行的提问、调用了哪些工具、得到什么、最终回答，都存为对象，可以回看和评审。
- **评测集**：用实验 7 情景和注入的问题，做一组固定题（“GRD-01 停机影响哪张订单？”“轴承位为什么偏大？”），每次改动都跑一遍，看 AI 答对没有。
- **模型**：国内用已备案模型（DeepSeek），美国用 Claude；没配模型时用规则模板生成文字，追因和推演照样能用。
- **主动提醒**：后台定时扫描异常，发现严重的新异常，就把因果链和备选方案准备好，推到首页和指挥台，“已备好 3 个方案”。

## 六、治理与安全

- **权限**：按角色控制到对象类型、属性和动作。例如学生看不到老师注入的问题情景；操作工不能批准采购。企业版沿用企业成员与角色（第 8 轮）。
- **审计**：谁在什么时候看了什么、发起和批准了什么动作、AI 做了什么，全部记录，不可删改。
- **数据质量**：同步器检查缺字段、编号对不上、时间倒序等问题，在“数据健康”页列出来。数据有问题的对象，在 360 页上标黄。
- **合规**：国内部署只用已备案模型；本体数据不出本服务器；AI 调用只发必要的对象摘要。

## 八、技术选型

| 需要 | 选择 | 理由 |
|---|---|---|
| 本体存储 | Postgres（现有），对象 / 链接 / 事件三张表，jsonb 加索引 | 规模几万对象，不需要图数据库；运维不增加 |
| 图遍历 | 递归查询 + 进程内 networkx（BSD） | 追因一般不超过 6 跳 |
| 推演 | 现有仿真引擎（自写）+ 现有 MRP / 成本模块 | 和车间同一套模型，可用事后数据检验 |
| 关系图前端 | Cytoscape.js（MIT） | 成熟，可交互，体积小 |
| 甘特图 | 自写 SVG | 需求简单 |
| AI | 现有 llm.py（DeepSeek / Claude，工具调用） | 已上线 |

不引入 Kafka、Spark、图数据库或新的消息中间件：现有总线和 Postgres 能撑住教学工厂和中小企业的规模。

## 十一、主要风险与对策

| 风险 | 对策 |
|---|---|
| 本体设计返工 | 定义写在 yaml 里，同步器可从头重放；17A 先覆盖 22 类对象，按需要扩展 |
| 推演和实际对不上，用户不信 | 每次推演都存档，事后自动和实际对比（复盘），偏差公开显示；教学模式用精确快照兜底 |
| 生产模式的状态重建不准（真设备数据不全） | 教学模式下用两种快照的结果互相核对；重建时缺什么数据就标出来，并在结果上注明置信度 |
| AI 编造 | 只能用本体工具，结论必须带引用；评测集把关；规则版兜底 |
| 工作量大 | 分四期，每期都能独立上线、演示；预计每期规模与前几轮相当 |
