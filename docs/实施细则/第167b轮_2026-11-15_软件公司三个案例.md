## 一、照第 161 / 166b 轮的路子

每个案例走八步（任务书 → 方案 → 计算 → 仿真 → 三维与图纸 → 工艺 → 制造 → 总结），由 `tools/cases/software_<案例号>.py` 重新生成，
放 `factory/cases/software/A–C/`，数字工厂“设计案例”页直接显示（页面、接口不用改）。软件没有三维零件，“三维与图纸”一步出的是**架构图、时序图、机房与故障域布置图**。
“制造”一步就是软件公司的生产线：数字工厂仿真车间按现行工艺路线跑版本构建（发布门禁）或订阅开通（服务验收），量的是清单里那几项测量。

三个案例连起来：A 的实时 OS 跑在电路板厂的关节驱动板上（REL-RTOS）；B、C 用的机房就是计算机厂案例 C 的 20 柜算力中心（320 台 WQ-SV2U）。

## 三、规则

1. 数都有出处：教材公式（排队论、实时调度、可靠性）、仿真、软件公司 / 计算机厂清单、计算机厂案例 C；外部数据（MCU 主频、盘的年故障率、电价、租户规格）写通用名称和示例值，不编型号。
2. 校核全过才交付；校核不过的在案例里改设计（写“改了什么、为什么”），不放宽要求。
3. 仿真和公式互相对照，差多少写明；蒙特卡洛罕见事件用加速故障率对照，写明换算方法。
4. 不改软件公司清单的测量规格；案例 A 用到的 8 μs 中断延迟上限、C 用到的 50 ms 延迟上限、99.9 % 可用性就是清单里的规格。

**改动与偏差**

1. 案例 B 的三副本小文件 p99 31.2 ms 超了 30 ms 的要求；按规则 2 改设计，加“对冲读”（20 ms 没回就向另一个副本再发一次，多发约 7 % 的读），p99 28.1 ms。
2. 案例 B 的马尔可夫链开始用线性方程求平均吸收时间，数太悬殊（10⁻⁶ 对 10⁻¹）解不准，和近似公式差 7.6 %；改用生灭过程首达时间的精确求和公式（全是正项），差 < 0.1 %。
3. 案例 C 开始把虚拟机 CPU 利用率整个跟着请求量的日周期走，高峰物理 CPU 108 %，选定方案通不过；改成“六成是跟请求量无关的底子、四成跟请求量走”（常见量级，写进脚本），高峰 75 %；方案比较表用同一个系数，2 倍超分仍然通不过。
4. 案例 C 的装箱仿真开始只有通用型虚拟机，碎片几乎为 0（装箱效率 100 %，不真实）；加上计算型（1:2）、内存型（1:8），装到连一台 8 vCPU / 32 GB 都放不下为止，95.2 %。网关算出每区 1 台就够，按区内也要能坏一台取 2 台。
5. 通用工具 `tools/cases/caselib.py`：`run_shop` 加 `units`（指定在哪台设备上做，案例 C 把订阅开在 cl-a2）；`shop_table` 对上限 100 % 的百分比特性（测试通过率、覆盖率、可用性、良率）只算下限 Cpl——上限是自然界限，原来按双边算会把测试通过率的 Cpk 算成 0.4。以前的案例没有重新生成，下次重新生成时芯片厂的良率 Cpk 会按这个口径。
6. `tests/test_cases.py` 的按厂列出案例加上软件公司。
