依据：11-17 美东 22:46–23:20 数字工厂 502（部署撞上每天的数据库备份，备份导一张 13.7 GB 的历史表 30 多分钟）；11-18 Eddie：“看看那些还可以搬到另一个服务器”，看了数据后回“好”（先做两件：凸轮、轴承、电子只留企业服务器一份；查数字工厂数据库为什么一直忙）。

## 一、现状（11-18 只读体检，`Server check` 和 `Enterprise server · check`）

| | 教育服务器（8 GB） | 企业服务器（8 GB，161.35.185.35） |
|---|---|---|

| 吃得最多的 | 数字工厂数据库 CPU 1.4 核；ERPNext 两个队列各 0.6 核；ERPNext 数据库 656 MB、演示工厂 495 MB、数字工厂数据库 405 MB | — |

数字工厂数据库为什么一直忙（`pg_stat_user_tables`，7 天累计）：

1. **`bus_message` 全表扫描**：主厂 144 万次、读 807 亿行；缝纫机厂 509 亿行、试点厂 222 亿行、演示厂 180 亿行……12 个库加起来上千亿行。原因是轮询查询按 `mode`、`seq`、`source like`、`corr like` 找，表上只有 `(type, ts)`、`(topic, ts)`、`corr` 三个索引，用不上（`hub/maint.py` 每次取 `max(seq) where mode=…`、取 `machine.event where mode=… and seq > …`；`hub/kpi.py` 的 `source like 'demo%'`；`hub/ai.py` 的 `corr like 'MFG-WO-%'` 等）。
2. **`energy_read`、`maint_inspection`、`notification`、`ehs_person` 也是一轮一轮全表扫**（各几亿到上百亿行）。
3. **`anomaly` 不停地改**：试点厂 8400 万次更新，表里才 3300 行——每一轮把所有异常行都重写一遍。
4. **`ont_event` 13.7 GB、3880 万行**（主厂），只增不删；每天备份要导它，就是 11-17 卡住的原因。

## 二、决定

| 编号 | 决定 |
|---|---|
| D-1 | **凸轮、轴承、电子只留企业服务器一份**：官网下的 `/cam/`、`/bearing/`、`/eda/` 改成跳到 `app.wenquestrobotics.com` 的同一路径（永久跳转，路径和参数原样带过去）；教育服务器停掉 `cam`、`bearing`、`eda` 三个容器（`docker-compose` 里去掉，数据卷不删）。省约 470 MB。国内服务器不动 |
| D-1b | 以后学习平台部署成功后，自动把企业服务器上这三个软件更新到同一版本（`deploy.yml` 末尾加一步，做的事和手动跑 `Enterprise server · deploy` 一样）——第 146 轮说过改 `deploy.yml` 要 Eddie 同意，本条即请 Eddie 同意 |
| D-2 | **数字工厂数据库减负（功能不变）**：①给 `bus_message` 补轮询用得上的索引（`(mode, seq)`、`(type, mode, seq)`，`corr`、`source` 前缀查询用 `text_pattern_ops`），改写用不上索引的几句；②`energy_read`、`maint_inspection`、`notification`、`ehs_person` 按实际查询补索引；③`anomaly` 只在内容变了的时候才更新；④`ont_event` 明细只留 30 天（更早的已经汇总在 `ont_metric_daily`），每天夜里分批删一次、避开 3:30 的备份；第一次清理也分批、夜里做 |
| D-3 | **枢纽启动改表限时**：建表、加索引时设 `lock_timeout`（10 秒），等不到锁就跳过这一句、下次启动再做，不再卡住整个启动（11-17 就是卡在这里 35 分钟） |
| D-4 | 不搬的：数字工厂主体和 ERPNext 留教育服务器（11-10 Eddie 定“教育要数字工厂实训”）；演示工厂等做“企业中枢”那一轮再看 |
