## 一、慢在哪里（按第 22 章的实际过程算）

| 环节 | 第 22 章的做法 | 为什么慢 |
|---|---|---|
| 一轮的粒度 | 一轮一章 | 每章都要单独拖一次全书构建（《人工智能》261 节整本过一遍）、一次全套网关测试（470 项）、一次上线（GitHub Actions 几小时）。固定开销全摊在一章上 |
| 章内顺序 | 程序 → 图 → 动画 → 浏览器实验 → GPU 实验 → 正文 → 构建，串着做 | 后面几样其实只依赖“程序定下来的数”，不依赖彼此，却排在一条队里 |
| 等部署 | 推上去之后盯着 run 看完 | 这段时间什么都没产出 |
| 网关测试 | 全跑 | CLAUDE.md 本来只要求“改了平台要读的数据格式”时连着跑 |
| 全书构建 | 中途跑了多次 | 中途只需要验单节 |

## 二、决定

| 编号 | 决定 |
|---|---|
| D-1 | **一轮三章。** 细则一次写三章的安排，Eddie 一次确认；构建、测试、上线各一次，摊到三章上。资料卡仍按章各一份（口径不能混） |
| D-2 | **章内并行。** 图、浏览器实验、GPU 实验、动画各开一个子任务同时做；我先把“程序定下来的数”和每样的接口定死，子任务只管各自那一样，最后由我对数、拼正文。跨章之间也并行（三章的程序先后脚跑） |
| D-3 | **不等部署。** 推上去就接着写下一批；部署结果由后台任务盯，红了再回头当场修（CLAUDE.md 那条“红了当场修”不变，只是不再空等） |
| D-4 | **网关测试按条件跑**：只有改了平台要读的数据格式（教材 `web/index.json` 的字段或类型等）才连 `services/gateway` 一起跑；只加章节内容不改格式的，跑教材构建即可 |
| D-5 | **全书构建只在交付前跑一次**（不带 `--only`）。中途用 `--only <节号>` 试单节——用过 `--only` 之后交付前必须再跑一次不带 `--only` 的全书构建（原规矩不变） |

## 三、不改的（这几条是质量的来源，一条都不松）

1. **先定方案，再施工**：细则还是先写、Eddie 还是要确认，只是一次管三章。
2. **数字只能由程序交给正文**，正文里不出现手打的数；资料卡口径不全（基线、统计期、测量方）就不印。
3. **程序的输出推翻了计划里的结论，改正文、不改数。** 第 22 章三处：泄漏在强周期序列里其实很小；安全层不留余量就等于没代价；储能策略“越激进越省”是假的。
4. **交付前**：不带 `--only` 的全书构建 0 错误 + 用真实构建产物把页面打开一遍。
5. 停用租用 GPU（Lambda）那条照旧：GPU 实验是学生自己的云笔记本，本仓库不开 Lambda 机器。
