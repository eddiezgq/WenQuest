# 实施细则 · 第 60 轮：部署提速（教材检查不再每次从头跑）

日期：2026-10-31
起因：第 58 轮上线时，学习平台的“Build and deploy”一次要 1.5～2 小时，几乎全耗在《机器人学》全书检查上；中间别的推送只能排队，排着的会被更新的推送顶掉。
状态：**草案，待 Eddie 确认**。（第 59 轮编号已被“机器人厂打开设备维护、能源、经营财务”用了，本轮顺延为第 60 轮。）

## 一、现在的样子（实测，GitHub Actions 运行记录）

| 运行 | 改了什么 | 总时长 | 其中《机器人学》检查 | 其余最长的一项 |
|---|---|---|---|---|
| 41058099361（10-30） | 第 58 轮：机器人学第 29 章 + 数字工厂 | 约 2 小时 | **90 分钟** | 《人工智能》20 分钟、镜像到国内 16 分钟 |
| 41041621931（10-30） | 第 58 轮：零件库 WQ-CR5 + 数字工厂 | 约 2 小时 | **113 分钟** | 《机械设计》14 分钟 |
| 41040730327（10-30） | 只改细则 | 约 15 分钟 | 没跑（没改教材） | 测试 9 分钟 |

找到的三个原因：

1. **算过的结果每次都扔掉。** 构建程序本来就按“程序内容的散列”缓存每个算例程序的结果（`textbook/build/<书>/values/`），程序没改就直接用旧结果。但 GitHub 每次都是一台干净的机器，这个缓存没有保存下来，所以《机器人学》30 章、几百个程序（中英两遍）每次都从头跑。本地同样的全书构建，第一次 40 分钟，之后只跑改过的章，几分钟。
2. **一改数字工厂，九本书全部重查。** 判断“哪些书要查”时，`factory/` 下任何文件改动都算“共用文件改了”，于是九本书全部重跑，哪怕改的只是机器人厂的一个页面。实际上各书只读数字工厂里很少几个文件。
3. **虚拟实验每次全部试做一遍。** `--labs` 在无头浏览器里把每个实验的全部任务做一遍，章没改、实验没改也照做。

另外发现一个隐患：《机器人学》《人工智能》《PLC》的算例程序读了数字工厂的文件（如 `factory/factory/data.py`、`factory/plants/wenquest-robot.yaml`、`factory/digital/cae/wqcr5.py`），但没有在 `meta.yaml` 的 `program_deps` 里登记。这样一来，那些文件改了，本地缓存不知道要重算。现在 CI 每次从头算，所以没出事；一旦按原因 1 保存缓存，就会出事。所以要先补登记。

## 二、决定（建议）

| 编号 | 决定 | 理由 |
|---|---|---|
| D-1 | **补登记书外依赖**：《机器人学》《人工智能》《PLC》等各书 `meta.yaml` 的 `program_deps` 补全程序读的书外文件。加一项测试：扫描每本书 `code/` 里出现的 `factory/`、`library/`、`labs/`、`services/` 路径，没登记的报错 | 缓存要对，前提是“改了什么、要重算什么”说得清 |
| D-2 | **CI 保存构建缓存**：每本书的 `values/`、`values-en/`、`figs/`、三维动画、CUDA / HIP 编译检查的缓存，用 GitHub 的缓存功能存下来，下次先取回。缓存的名字带上 Python 包版本；版本一变，全部重算 | 程序没改就不重跑。缓存按内容散列判断，不会用错 |
| D-3 | **“哪些书要查”按登记的依赖判断**：只有改到某本书 `program_deps` 里的文件，或改到真正共用的部分（`textbook/tools/`、实验检查器、实验工具包），才查那本书；`factory/` 下其他文件不再触发九本书全查 | 改机器人厂页面不该重查《微积分》 |
| D-4 | **虚拟实验试做也缓存**：每章实验页的内容（含实验工具包、检查器、用到的模型）算一个散列，试做全部通过就记下；下次散列相同就跳过 | 实验没改，不用再做一遍 |
| D-5 | **记录各阶段用时**：构建结束时打印“跑程序 / 生成页面 / 试做实验 / 生成 PDF”各用了多少分钟，CI 的摘要里能看到 | 以后哪里慢一眼看出来 |
| D-6 | **定期全量检查不丢**：每周一次（周日夜里）不用缓存、九本书全部从头查一遍；手动点“运行”也走全量 | 防缓存掩盖问题；和现在的“全书检查”同样严格 |

不做的：不把《机器人学》拆成几台机器并行（有了缓存，平时只跑改过的章，不需要；第一次全量照旧 1.5 小时左右，每周一次可以接受）。数字工厂的部署（约 50 分钟，主要是真 ERPNext 演练）这轮不动，它和学习平台是两条线，互不阻塞。

## 三、规则

1. 检查的严格程度不降：同样的程序、数字、公式、引用、术语、实验检查，只是“没改的不重做”。
2. 缓存只按内容散列命中；任何拿不准的情况（缓存坏了、版本变了、手动运行、每周全量）都从头算。
3. 本地构建的行为不变（本地本来就有缓存）。
4. CLAUDE.md 里“交付前跑不带 `--only` 的全书构建”不变。

## 四、交付物

- `textbook/*/meta.yaml` 补全 `program_deps`；`textbook/tools/tests/` 加依赖登记的测试。
- `textbook/tools/build.py`：实验试做缓存、各阶段用时。
- `.github/workflows/deploy.yml`：保存 / 取回构建缓存；“哪些书要查”按登记的依赖；每周全量。
- `docs/帮助/`：在部署说明里补一段“为什么有时快、有时慢，怎样手动全量检查”。

## 五、施工顺序与验收

1. D-1（先补登记和测试），D-5（用时），本地跑通全部教材工具测试。
2. D-4 实验缓存：本地连跑两次《机器人学》第 29 章 `--labs`，第二次实验部分跳过。
3. D-2、D-3、D-6 改 CI。
4. 验收（推送后在 GitHub 上看）：
   - 第一次推送：全量（没有缓存），时长和现在差不多；
   - 再推一次只改《机器人学》一节的文字：《机器人学》检查 **≤ 15 分钟**，整次部署 **≤ 30 分钟**；
   - 推一次只改机器人厂页面：不触发任何教材检查；
   - 手动运行一次：九本书全量，全部通过。
5. 结果写回本细则，帮助文件同步。
