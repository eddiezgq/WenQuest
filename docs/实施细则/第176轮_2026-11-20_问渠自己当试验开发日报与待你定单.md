## 二、决定（建议）

| 编号 | 决定 |
|---|---|
| D-1 | **全方位扫描**：一个扫描程序 `tools/devops/scan.py`（只读），每次扫：① 所有仓库的细则状态、待确认问题、提交；② 所有工作流的运行结果（含定时、推送检查、部署），红灯从什么时候开始；③ Actions 用量、GPU 遗留机器（调 `GPU check` 的同一查法）、服务器检查；④ 线上三站可用性；⑤ 定时任务清单与最近运行（这一项由定时会话读，程序拿不到）；⑥ claude.ai 项目文档的更新。扫到的结果写成一份 JSON，再排成日报。接不上的一项如实写“未接入”，不编 |
| D-2 | **开发日报**：每天一次，由定时会话跑扫描、写日报，发到一个固定的 claude.ai 私有页面“问渠开发现状”（同一网址每天更新，不往仓库里天天提交，免得推送更碎）。日报四块：今天要你定的事 / 红灯与花钱 / 没收尾的轮（卡在哪一步、等谁） / 空转或异常的定时任务。**有要你定的事或红灯才推送通知**，全正常不打扰 |
| D-3 | **待你定一张单**：所有细则里“请 Eddie 确认”表中还没确认的问题汇成一张单，每条带编号（如 `176-Q2`）、一句话问题、建议。你回“都按建议”或“176-Q2 改为……”，会话把回复写回各轮细则的确认记录 |
| D-4 | **长期授权写清楚**（写进 CLAUDE.md，可随时收回）：**不用问**——修红灯、补测试、补帮助、收尾验收、改错字、按已确认细则施工中的小偏差（事后写回细则）；**要问**——新功能和界面、花钱（GPU、服务器、付费接口、加预算）、删除任何东西、对外发布和投稿、改 CLAUDE.md 的规矩、停掉或新建定时任务 |
| D-5 | **轮号统一发放**：`docs/实施细则/轮号登记.md` 一行一号（号、日期、题目、哪个会话）。开新一轮先拉最新、登记、立刻推送；推不上（别的会话抢先）就拉下来取下一个号。推送检查加一条：新加的细则文件号不能和已有的重复（已有的 10 组重号不动） |
| D-6 | **红灯自动修**：开发日报的定时会话发现 main 的推送检查或部署红了，按 CLAUDE.md 当场修、推送、跟到变绿；修不好或要花钱才能修，列进待你定单并推送通知。本轮只修本仓库 |
| D-7 | **这轮不做**（放第二轮）：收尾自动对账（逐条核对验收条款）、经验库（事故记录 → 起草新规矩） |

## 四、施工顺序与验收

1. `scan.py` 先跑本仓库：细则状态、待确认问题、工作流运行，结果和本轮第一节的统计对得上。
2. 补登轮号登记，加重号检查，故意建一份重号细则，检查要红。
3. `report.py` 出第一份日报，发到私有页面，你看一眼排版。
4. 写 CLAUDE.md 授权一节、帮助、README 里的定时任务提示词。
5. 推送前本地跑相关测试；推送后看推送检查变绿。
6. 建定时任务（要你确认，见 Q4），连续跑两周。
7. **验收**：两周里日报每天都出；红灯从出现到有人处理不超过一个日报周期；没有新撞号；没收尾的轮数比 11-20 的 78 份少；你每天只需回一次待你定单。结果写回本细则。

## 五、边界

- 扫描只读，不改任何东西；改动只经 D-4“不用问”的那几类和你批准的待你定单。
- 不读任何私人渠道；日报里不给个人打分。
- 不开 GPU、不加预算；扫到要花钱的事一律列进待你定单。
