### 15.3.1 问题的提出

有了状态转换图，怎样写成程序？最直接的做法是“照着电路想”：压头什么时候下行？夹紧到位以后、压到底以前、按钮按着的时候。于是写出

```
Y_PressDown := B_Clamped AND NOT B_PressDown AND S_Hand1 AND S_Hand2;
```

这一行看起来没错，但它很快就会出问题。压头回程时，夹紧还没松开、压头已经离开下位、操作工如果还按着按钮——压头又下去了。为了防止这种情况，得加一个“已经压过”的标志；有了标志，又得想清楚它在什么时候清零……每加一个条件，就要重新检查所有其他条件，程序像打补丁一样越补越乱。PLC 行业把这种写法叫“经验设计法”，它适合三五个输出的小设备，设备一复杂就难以为继（第 14 章）。

问题出在：这种写法里，“设备现在处于哪个阶段”这一信息是隐含的，散落在各个输出的条件里。状态机设计法反其道而行之：用一个变量明明白白地记住“现在处于哪个状态”，所有的逻辑都围绕这个变量组织。

### 15.3.2 状态机的三个要素

**定义 15.3.1（有限状态机）** 一个**有限状态机**由三样东西组成：有限个**状态**；引起状态改变的**事件**；以及在状态中或转移时执行的**动作**。在任一时刻，状态机处于且只处于一个状态；某个事件发生、且它在当前状态下有定义时，状态机转移到一个新状态。

对 PLC 程序来说：状态用一个枚举变量表示；事件就是输入信号的变化或定时器、计数器的到达（“夹紧到位开关接通”“定时器到时”）；动作就是输出（“夹紧阀得电”）和内部变量的修改（“记录最大压装力”）。

状态机有两种基本形式。如果输出只由当前状态决定，称为**摩尔型状态机**；如果输出由当前状态和当前输入共同决定，称为**米利型状态机**。压装工位的“夹紧阀”只取决于状态（夹紧、压装、回程三个状态都得电），是摩尔型的；“压头下行阀”除了状态还取决于双手按钮和光幕（压装状态下、两个按钮按着、光幕无遮挡），是米利型的。实际的 PLC 程序几乎总是两者混用：能用摩尔型的尽量用摩尔型——它简单、不受输入抖动的影响；安全条件则直接写在输出上，构成米利型的部分，这样安全条件一失去，输出在同一个扫描周期就断开，不必等状态转移。

### 15.3.3 设计步骤

状态机设计法分五步：

1. **列状态**：从控制要求说明的动作顺序出发，每一个“在等某件事完成”的阶段是一个状态。给每个状态起一个说明含义的名字，定义为枚举类型。
2. **画状态转换图**：对每个状态，写出离开它的所有转移和转移条件。
3. **列状态—事件表**：逐一检查每个状态下每个事件的处理（15.3.5 节），补上遗漏的转移。
4. **写转移**：用一个 CASE 语句，每个状态一个分支，分支里只写“离开这个状态”的条件和转移时要做的事。
5. **写输出**：在 CASE 之后，每个输出写一行，等号右边是“在哪些状态下得电”，再加上安全条件。

### 15.3.4 程序的结构

程序 15.3.1 有三个特点，值得逐一说明。

**状态用枚举类型。** 程序开头的 TYPE 语句定义了枚举类型 E_Press，状态变量 state 的类型就是它。与用整数 0、1、2……表示状态相比，枚举有两个好处：程序里写的是 PRESSING 而不是 2，一看就懂；编译器会检查赋值，不会把一个不存在的状态号赋给 state。在监视表里，state 的值也直接显示成状态名。有一个陷阱要注意：ST 不区分大小写，枚举值的名字和变量的名字不能相同。如果另有一个变量叫 fault，又有一个枚举值叫 FAULT，`state := FAULT;` 到底指哪一个？IEC 61131-3 允许写成 `E_Press#FAULT` 来消除歧义，问渠实验台遇到这种情况会直接报错，要求改名——15.5 节的程序就因此把故障代码变量叫作 faultCode。

**转移与输出分开。** 程序分成两部分。第一部分是 CASE 语句，只管“什么条件下换状态”；第二部分是一组赋值，只管“每个输出在什么状态下得电”。这样分开以后，检查转移只看第一部分，检查输出只看第二部分，互不干扰。每个输出只在一处赋值，不会出现第 4 章讲过的双线圈问题。

**转移时做的事写在转移处。** 有些事只在转移的那一刻做一次：启动时清除上一件的结果、把最大压装力清零；压到底时判定合格与否。这些写在 CASE 分支里、`state := …` 的旁边。而“在状态内每个扫描都做”的事——更新最大压装力——写在分支里转移条件的前面。

**准则 15.3.1（状态机程序的写法）** 用枚举变量表示状态；用一个 CASE 语句写转移，每个分支只写离开该状态的条件；输出在 CASE 之后统一赋值，每个输出只写一次，由状态决定，再与上安全条件；只在转移时做一次的事，写在转移处。

再看下行阀那一行：`Y_PressDown := state = PRESSING AND S_Hand1 AND S_Hand2 AND S_LC;`。前半部分是摩尔型的（由状态决定），后半部分是安全条件（米利型）。CASE 里压装状态的第三个分支也检查了松手和挡光，在那里它的作用是“中止本件、转去回程”；输出行上的同样条件，作用是“这一个扫描就断开下行阀”。两处缺一不可。只有输出上的条件，松手时压头停住了，但状态还在压装，操作工再按下按钮压头又会下去。只有 CASE 里的条件，在这个程序里倒也能在同一个扫描断开下行阀（CASE 在输出之前执行，转移和输出发生在同一个扫描里），但安全就依赖于转移逻辑处处正确；程序以后一改——15.4 节的单步方式中，松手时状态并不转移——保护就悄悄地没了。安全条件直接写在输出上，不管状态机怎样改，它都起作用。再看上行阀那一行：在状态机里，压装和回程是两个不同的状态，下行阀和上行阀不可能同时得电，但程序还是加了 `AND NOT Y_PressDown`。这是一道多余的、便宜的保险：程序以后被修改时，它能防止有人不小心破坏了互斥。问渠实验台的“程序检查”发现两个互为反向的输出彼此没有联锁时，会给出提醒。

### 15.3.5 完备性检查：状态—事件表

状态转换图画好了，怎样确认没有漏掉情况？一个系统的方法是列**状态—事件表**：行是状态，列是所有可能的事件，每一格写明“这个状态下发生这个事件，做什么”。表 15.3.1 是压装工位的状态—事件表（只列与安全和质量有关的主要事件）。

表中每一格都必须有明确的内容。“忽略”也是一种明确的处理：回程中操作工再次按下双手按钮，不应该有任何反应。表里的“？”就是程序 15.3.1 的漏洞：动作超时和急停在任何状态下都没有处理。如果夹紧到位开关坏了，设备会永远停在夹紧状态，没有任何提示；如果按下急停——急停回路切断了压头阀的电源，压头停了，但程序不知道，松开急停后会接着往下走。15.5 节补上这些格子。

状态—事件表的格数是状态数乘事件数，看起来工作量不小。但它是迄今为止发现顺序控制漏洞最有效的方法：大部分现场事故都出在“设计时没想到的那一格”。表列出来之后，每一个非“—”的格子正好对应一个测试用例。

一个测试用例在问渠实验台上写成这样（光幕测试）：

```
放上工件；等 0.2 s；按下两个双手按钮；等 1.5 s（压头在下行途中）；
挡住光幕；等 0.02 s；检查：下行阀断开，没有危险动作；
撤去遮挡；等压头回到上位、夹具松开（最多 6 s）；检查：不合格灯亮。
```

它与控制要求说明中的句子一一对应。在实验 15.3 中，读者从一个只有框架的程序开始，按本节的步骤写出状态机，用这五个测试检验；测试不通过时，实验台会指出哪一步、哪个信号与期望不符。实验台上另有四个测试检验 15.5、15.7 节的异常处理，学完那两节、程序加上异常处理以后再用。
