### 6.2.1 事件

前两章的程序一直用 CUDA **事件**计时，这里把它说完整。事件是插在流里的一个标记：`cudaEventRecord(e, s)` 把事件 `e` 放进流 `s`，当 GPU 执行到这个位置时，事件被“完成”，并记下当时的 GPU 时钟。于是：

- **计时**：在一段操作的前后各记录一个事件，`cudaEventElapsedTime(&ms, a, b)` 给出两者之间的 GPU 时间（毫秒，分辨率约半微秒）。它量的是 GPU 上实际经过的时间，不受主机一侧的干扰。
- **等待**：`cudaEventSynchronize(e)` 让主机等到事件完成；`cudaStreamWaitEvent(s2, e)` 让另一个流等它（6.1.4 节），不阻塞主机。
- **查询**：`cudaEventQuery(e)` 不等待，只问完成了没有，主机可以在等 GPU 的同时做别的事。

用事件计时有两点要注意。第一，事件与被计时的操作必须在同一个流里，否则两者没有确定的先后关系，量出来的数没有意义。（传统的默认流与其他流互相同步，事件记在默认流上有时也能量对，但那是依赖隐含的规则；用 `--default-stream per-thread` 编译或使用非阻塞的流时就不灵了。）第二，GPU 第一次执行一个核函数时要加载代码、初始化，时间偏长，所以要先预热，再重复多次取中位数——这正是 4.1 节以来 `time_ms` 的做法。

### 6.2.2 启动开销

主机启动一个核函数，要经过运行时库、驱动，把命令写进 GPU 的队列，这本身要花几微秒。启动是异步的：主机发出命令就返回，GPU 慢慢执行。只要核函数比启动开销长，主机就能跑在 GPU 前面，命令在队列里排着，GPU 一个接一个地执行，启动开销被藏住了。反过来，如果核函数很短，GPU 做完一个，下一个还没发过来，GPU 就闲着等主机。

**算例 6.2.1** 第 2 章小型 Transformer 一次训练前向（$B = 32$，$T = 256$）约 {{ex6_2.GFLOP:.0f}} GFLOP，A10 半精度张量核心峰值下至少 {{ex6_2.t_fwd_us:.0f}} μs；按每层 12 个核函数（层归一化、QKV、注意力分数、softmax、加权求和、输出投影、残差、前馈网络……）计，共约 {{ex6_2.kernels}} 个，平均每个约 {{ex6_2.avg_fwd:.0f}} μs，比每次约 {{ex6_2.launch_us:.0f}} μs 的启动开销长得多，启动开销可以被藏住。

**算例 6.2.2** 同一个模型逐词生成（批大小 1）时，每生成一个词元要把全部 {{ex6_2.weights_MB:.0f}} MB 权重读一遍，A10 上只要 {{ex6_2.t_dec_us:.0f}} μs；可核函数还是那 {{ex6_2.kernels}} 个左右（量级；生成时还有写键值缓存等核函数），平均每个只有 {{ex6_2.avg_dec:.1f}} μs，比启动开销短得多。这时主机成了瓶颈：光是发出这些启动就要约 {{ex6_2.over_dec:.0f}} μs，是读权重时间的 {{ex6_2.ratio_dec:.0f}} 倍。GPU 大部分时间在等主机。用 PyTorch 逐个执行运算时更明显：每个运算在 Python 与框架中还要花上 10 μs 以上，远比驱动本身的启动开销大。

### 6.2.3 CUDA 图

**CUDA 图**把一串操作（核函数、复制、事件……）连同它们之间的依赖关系，事先记录成一张图；以后每次只要一条命令 `cudaGraphLaunch` 就把整张图交给 GPU。驱动在实例化时已经把所有准备工作做完，每次提交几乎没有逐个启动的开销，GPU 也能更紧凑地安排各个节点。

最方便的建图办法是**捕获**：让一个流进入捕获模式，照常发出各个操作，它们不执行，而是被记录下来：

```cpp
cudaStreamBeginCapture(s, cudaStreamCaptureModeGlobal);
for (int i = 0; i < 1000; i++) add1<<<4, 256, 0, s>>>(x);     // 只记录，不执行
cudaStreamEndCapture(s, &graph);
cudaGraphInstantiate(&exec, graph, 0);                       // 一次性的准备
cudaGraphLaunch(exec, s);                                    // 以后每次一条命令
```

实测：同样 1000 个核函数，用 CUDA 图提交后平均每个 {{run6_2.graph_us:.2f}} μs。

CUDA 图的代价是灵活性：图里的核函数参数、数组地址都是捕获时的值，形状变了就要重新捕获或更新节点；捕获期间不能做同步之类的操作。所以它最适合每次形状都一样、反复执行的计算，例如大模型推理的逐词生成：每一步的计算完全相同。vLLM 等推理引擎为一组批大小（1、2、4、8……）各捕获一张图，PyTorch 提供 `torch.cuda.graph`、`torch.cuda.CUDAGraph` 与 `make_graphed_callables` 等接口，`torch.compile` 的 `mode="reduce-overhead"` 也是靠 CUDA 图（第 7、9 章）。

另一种减少启动次数的办法是 5.1 节的融合：把几个小核函数合成一个，既省启动又省显存往返。融合与 CUDA 图常常一起用。

**工程师笔记**

- 计时用事件，事件与被测操作在同一个流里；先预热，再取多次的中位数。
- 核函数平均只有几微秒时，启动开销就成了瓶颈：用 Nsight Systems 看时间线上核函数之间的空隙。
- 形状固定、反复执行的一串小操作，捕获成 CUDA 图；能融合的先融合。
- 不要在循环里无谓地同步（如每一步都 `cudaDeviceSynchronize` 或把一个标量 `.item()` 传回主机），那会把 GPU 和主机拖成一步一等。
