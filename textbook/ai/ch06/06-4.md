### 6.4.1 集合通信

数据并行训练的每一步，$p$ 块 GPU 各有一份长度为 $n$ 的梯度，要求每块 GPU 最后都得到它们的和。这种“大家一起参与”的通信称为**集合通信**，这一种叫**全归约**。常用的还有：

- **广播**：一块 GPU 的数据发给所有 GPU（如开始训练时同步初始参数）；
- **归约**：所有 GPU 的数据加起来，结果只放在一块上；
- **全收集**：每块 GPU 有一段，最后每块都拿到所有段拼起来的整体（完全分片数据并行在前向计算前用它收集参数）；
- **归约—散播**：所有 GPU 的数据加起来，但结果切成 $p$ 段，每块 GPU 只拿一段。

全归约 = 归约—散播 + 全收集，这一点马上就会用到。

### 6.4.2 α–β 模型

分析通信算法的耗时，常用最简单的 **α–β 模型**：发一条长 $m$ 字节的消息要 $\alpha + m/\beta$，$\alpha$ 是固定的延迟（启动通信、同步、链路往返），$\beta$ 是带宽。小消息时 $\alpha$ 起主导作用，大消息时 $m/\beta$ 起主导作用。机器内经 NVLink 时 $\alpha$ 是几微秒的量级，$\beta$ 是几百 GB/s。

**朴素的算法**：所有 GPU 把数据发给 0 号，0 号加好，再发回去。0 号要收 $p - 1$ 份、发 $p - 1$ 份，它的链路成了瓶颈，耗时约 $2(p-1)(\alpha + n/\beta)$，随 GPU 数线性增长。

### 6.4.3 环形全归约

把 $p$ 块 GPU 排成一个环，每块只和右邻通信。每块 GPU 的数组切成 $p$ 块：

1. **归约—散播**（$p - 1$ 步）：第 $s$ 步，第 $r$ 块 GPU 把自己的第 $(r - s) \bmod p$ 块发给右邻，右邻加到自己的同一块上。$p - 1$ 步之后，第 $r$ 块 GPU 的第 $(r + 1) \bmod p$ 块已经是全部 $p$ 块 GPU 的和。
2. **全收集**（$p - 1$ 步）：把这块完整的和沿环往下传，每步每块 GPU 把刚收到的完整块转发给右邻。$p - 1$ 步之后，每块 GPU 的每一块都是完整的和。

每一步所有 GPU 同时发送、同时接收，每条链路都在忙；每块 GPU 一共发出 $2(p-1)$ 次、每次 $n/p$ 字节，耗时

$$
T_{\text{环形}} = 2(p - 1)\,\alpha + \frac{2(p - 1)}{p}\cdot\frac{n}{\beta} . \tag{6.4.1}
$$

带宽项几乎与 $p$ 无关：GPU 再多，每块要发的数据也不超过 $2n$。可以证明，在网络本身不做计算的前提下，任何全归约算法每块 GPU 至少要发出 $2(p-1)n/p$ 字节，环形算法正好达到这个下限（交换芯片能做归约时可以突破它，见 6.4.4 节）。它的代价是延迟项随 $p$ 线性增长，小消息、GPU 很多时吃亏。

树形全归约把 GPU 组织成二叉树，先沿树向上归约、再向下广播，消息切成小块流水线式地传，延迟项只有 $2\log_2 p\,\alpha$ 的量级。NCCL 用两棵互补的二叉树（每块 GPU 在一棵树里是叶子、在另一棵里是内部节点），各传一半数据，让所有链路都用上。大消息时树形的带宽项比环形略大，小消息、GPU 很多时它的延迟优势明显。上面的公式是理想流水线下的近似，忽略了分块带来的额外延迟。实际上 NCCL 的双二叉树主要用在机器之间；单机 8 卡经 NVSwitch 互联时，它通常用环形（Hopper 起还有交换芯片归约），所以下面算例中“树形最快”只是模型之间的比较。

### 6.4.4 NCCL

NVIDIA 的 **NCCL**（NVIDIA Collective Communications Library，读作“nickel”）实现了上面所有的集合通信。它探测机器的拓扑（NVLink、NVSwitch、PCIe、网卡），自动选择环形或树形算法、分多少个通道（同时跑几个环，占满所有链路），在 Hopper 一代起的 NVSwitch 上还能利用交换芯片本身做归约（NVLink SHARP）。用起来只要几行：

```cpp
ncclCommInitAll(comms, p, devs);                 // 一个进程管 p 块 GPU 时，一次建好所有通信器
ncclGroupStart();
for (int r = 0; r < p; r++)
    ncclAllReduce(send[r], recv[r], count, ncclFloat, ncclSum, comms[r], stream[r]);
ncclGroupEnd();                                  // 一组调用一起发出，避免互相等待而死锁
```

集合通信像核函数一样放进流里，异步执行。多进程时（每块 GPU 一个进程，跨多台机器），用 `ncclGetUniqueId` 生成一个标识，经 MPI 或 TCP 发给所有进程，各自调用 `ncclCommInitRank` 加入。PyTorch 的 `torch.distributed`（后端 `nccl`）和分布式数据并行（DDP）就是这样用 NCCL 的。

衡量全归约的速度，NCCL 的测试工具定义了两个带宽。**算法带宽** = 消息字节数 ÷ 耗时；**总线带宽** = 算法带宽 × $2(p-1)/p$。由式 (6.4.1)，环形算法的总线带宽在大消息时趋于链路带宽 $\beta$，与 GPU 数无关，所以可以直接拿它和硬件的链路带宽比较，看通信用足了多少。

### 6.4.5 通信与计算重叠

即使用了最好的算法，70 亿参数的梯度在机器内全归约也要几十毫秒，跨机器时更多。**算例 6.4.3** 16 台机器、每台 8 块 GPU，机器之间每块 GPU 一块 InfiniBand NDR 网卡（{{ex6_4.ib_GBs:.0f}} GB/s）。先在机器内归约—散播，每块 GPU 只负责 1/8 的数据在机器之间做环形全归约，再在机器内全收集；单是机器之间这一段就约 {{ex6_4.inter_ms:.0f}} ms。它并不比机器内的全归约长多少，原因是分层以后每块 GPU 只在机器之间传 1/8 的数据，而且 8 块网卡同时在传；网卡的带宽虽然只有 NVLink 的六分之一，被这两个因素弥补了大半。

办法是让通信藏在计算后面。反向传播从最后一层往前算，最后几层的梯度最先算好；PyTorch 的 DDP 把梯度分成若干“桶”，一个桶的梯度算完就立刻在另一个流里启动全归约，与前面各层的反向计算重叠（6.1 节的思路）。理想情况下，等反向传播结束，大部分梯度已经加好了。第 9 章讲大模型训练时还会看到，通信的量与重叠的方式决定了能用多少块 GPU 有效地训练一个模型。

**工程师笔记**

- 多 GPU 之间的集合通信一律用 NCCL（AMD 上的对应物是 RCCL，昇腾上是 HCCL，第 10 章）。
- 看通信用足了没有，用总线带宽和链路带宽比；小消息看延迟。
- 梯度很多但每个都小时，把它们拼成大的桶再全归约（DDP 默认 25 MB 一个桶），避免被 $\alpha$ 拖垮。
