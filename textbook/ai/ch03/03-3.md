### 3.3.1 问题的提出

CPU 与 GPU 都是用同样的半导体工艺、在面积和功耗都相近的芯片上做出来的。为什么一个擅长运行操作系统、浏览器和数据库，另一个擅长矩阵乘法？答案不在于哪一个“更先进”，而在于它们为两种不同的目标做了不同的取舍：CPU 要让一件事尽快做完，GPU 要让单位时间内做完的事尽量多。本节说明这两种目标怎样决定了芯片面积的分配，并用利特尔定律说明 GPU 为什么需要同时驻留那么多线程。

### 3.3.2 延迟与吞吐

**延迟**是一项工作从开始到完成所需的时间；**吞吐率**是单位时间内完成的工作量。两者常常不能兼得。打个比方：从仓库往车间送零件，派一辆摩托车，十分钟就能送到一箱，延迟短，但每小时只能送几箱；派一辆大货车，装满再走，第一箱要等一个小时，但一趟送几百箱，吞吐率高。

一个运行操作系统和交互程序的处理器，面对的大多是一长串前后依赖的指令：下一条要用上一条的结果，分支走哪边要等比较的结果。对这样的工作，唯一的提速办法是缩短每一条的延迟。而矩阵乘法、图像滤波、神经网络的一层，面对的是成千上万个互相独立的小任务，每一个早一点还是晚一点完成并不重要，重要的是全部做完的时间——也就是吞吐率。

### 3.3.3 CPU：把面积花在降低延迟上

现代 CPU 的每个核心都是为单个线程尽快执行而设计的。它的主频高（3～5 GHz）；它能**乱序执行**，在等待某条指令的数据时，先执行后面不依赖它的指令；它能做**分支预测**，在比较结果出来之前就猜测分支的方向并提前执行，猜错再撤回；它有几级大容量的缓存（每核几 MB，全芯片几十到几百 MB），让常用的数据尽量在几个到几十个周期内就能取到，而不必等待一百纳秒左右的内存访问。这些部件都占用大量芯片面积和功耗，而真正做运算的单元只占一小部分（图 3.3.1(a) 左）。

CPU 也有并行能力：多个核心（服务器 CPU 有几十个），每个核心有宽向量单元。本书第 1 章采用的代表性服务器 CPU 有 {{ex3_3.cpu_cores}} 个核心，单精度峰值约 {{ex3_3.P_cpu_T:.1f}} TFLOP/s，内存带宽 {{ex3_3.cpu_bw_G:.0f}} GB/s。

### 3.3.4 GPU：把面积花在运算单元上

GPU 做了相反的取舍（图 3.3.1(a) 右）。它的每个运算单元都很简单：没有乱序执行、没有复杂的分支预测，主频也较低（约 2 GHz）；32 个运算单元共用一套取指令和控制的逻辑（这就是线程束，3.6 节）。省下的面积用来放更多的运算单元：H100 有 {{ex3_3.cores_h}} 个 FP32 运算通道和 {{ex3_3.tc_total}} 个张量核心。它的缓存按每个线程算很小，但有极大的寄存器堆（3.5 节），让成千上万个线程同时驻留在芯片上。

**算例 3.3.1** 比较单个执行单元：CPU 的一个核心每周期可以做 64 次单精度运算，峰值 {{ex3_3.P_core_G:.0f}} GFLOP/s；H100 的一条 FP32 通道每周期做一次乘加，峰值 {{ex3_3.P_lane_G:.2f}} GFLOP/s，只有前者的约 1/{{ex3_3.r_core_lane:.0f}}。但全芯片相比，H100 的单精度峰值 {{ex3_3.P_h_T:.0f}} TFLOP/s 是这颗 CPU 的 {{ex3_3.r_P:.1f}} 倍，显存带宽 {{ex3_3.h_bw_T:.2f}} TB/s 是它的 {{ex3_3.r_bw:.1f}} 倍；若拿 AI 常用的半精度张量核心（{{ex3_3.P16_T:.1f}} TFLOP/s，3.4 节）与这颗 CPU 的单精度比，差距约 {{ex3_3.r_P16:.0f}} 倍——两者口径不同（服务器 CPU 也有低精度的矩阵指令），只作量级参考。GPU 用数量弥补了单个单元的弱小。

这样的取舍有代价。一个单独的线程在 GPU 上运行得很慢：主频低，没有乱序执行，一次访问显存要等几百纳秒。GPU 的高吞吐只有在同时有成千上万个线程、而且它们做的事情基本相同时才能体现出来。所以 CPU 与 GPU 是互补的：CPU 负责控制流复杂、前后依赖的串行部分（操作系统、数据准备、调度），GPU 负责大规模的数据并行运算。CUDA 程序的结构正是如此：主机（CPU）上的程序准备数据、启动核函数，设备（GPU）上成千上万个线程执行核函数（第 4 章）。

### 3.3.5 利特尔定律：路上要有多少数据

GPU 怎样应付几百纳秒的显存延迟？先看一个排队论中的普遍规律。1961 年，利特尔（J. D. C. Little）证明：在一个稳定的系统中，系统内平均的“顾客”数等于顾客到达的速率乘以每个顾客在系统中平均停留的时间。用于存储系统，“顾客”是一次访问请求：

$$
\text{在途数据量} = \text{带宽}\ \beta\ \times\ \text{延迟}\ \tau . \tag{3.3.1}
$$

这称为**利特尔定律**。它的意思是：每次访问都要等 $\tau$ 才返回，要让数据以速率 $\beta$ 源源不断地到达，就必须同时有 $\beta\tau$ 这么多数据已经发出请求、还在路上。在途的数据少于这个数，带宽就用不满，无论带宽本身有多高。

**算例 3.3.2** CPU：内存带宽 {{ex3_3.cpu_bw_G:.0f}} GB/s，访问内存的延迟取 {{ex3_3.cpu_lat_ns:.0f}} ns（服务器 CPU 的常见量级），在途数据量为 {{ex3_3.cpu_inflight_kB:.1f}} kB，即 {{ex3_3.cpu_lines:.0f}} 个 64 字节的缓存行，分到 {{ex3_3.cpu_cores}} 个核心，每个核心约 {{ex3_3.cpu_lines_core:.1f}} 个。CPU 核心靠乱序执行和硬件预取，能同时有十几个未完成的缓存行请求，所以用满带宽并不难。

**算例 3.3.3** H100：一项对 H100 的测量（无负载、逐个依赖的访问）给出显存访问延迟约 {{ex3_3.tau_ns:.0f}} ns，按最高频率 {{ex3_3.clock_G:.2f}} GHz 折算约 {{ex3_3.tau_cyc:.0f}} 个时钟周期。带宽 {{ex3_3.h_bw_T:.2f}} TB/s，在途数据量为 {{ex3_3.gpu_inflight_MB:.2f}} MB，分到 132 个流多处理器，每个约 {{ex3_3.per_sm_kB:.1f}} kB。一个线程束的 32 个线程各读一个 4 字节的数，一次共读 128 字节；每个流多处理器要同时有约 {{ex3_3.warp_loads:.0f}} 次这样的读取在路上。而一个流多处理器最多只能驻留 {{ex3_3.warps_max}} 个线程束，平均每个线程束要有约 {{ex3_3.loads_per_warp:.1f}} 次读取同时在途。

算例 3.3.3 揭示了 GPU 设计与 GPU 编程的核心：**靠大量线程的并发来隐藏延迟**。CPU 用缓存和乱序执行缩短每次访问的等待；GPU 不去缩短它，而是让足够多的访问同时在路上，一个线程束等待时别的线程束继续工作（3.7 节）。还要注意，353 ns 是无负载时测得的延迟，带宽接近用满时排队使延迟明显增加，所以按式 (3.3.1) 算出的在途数据量是下限，实际需要的更多。由此也得出 GPU 编程的几条基本要求：线程要足够多，每个线程最好同时发出几个独立的访问（如一次读 16 字节而不是 4 字节），这些在第 5 章中逐一实践。

### 3.3.6 生活中的例子

一家餐馆有两种经营方式。一种请一位技艺高超的大厨，每道菜他都从头做到尾，客人点单后几分钟就能上菜，但一晚上能做的菜有限。另一种像中央厨房：几十位帮厨站成一排，每人只负责一个简单的工序，第一份菜要等一阵才出来，但之后每分钟都有几十份菜出锅。小饭馆接待零散的客人，适合前者；给一个工厂几千名工人供应午餐，非用后者不可。CPU 是那位大厨，GPU 是那间中央厨房。中央厨房还有一个讲究：总有几十份菜同时在锅里，帮厨不用站在锅前等一份菜煮好——这就是利特尔定律说的“在途”。

**工程师笔记**

- GPU 上，一个线程的速度没有意义，要看所有线程合起来的吞吐率。线程太少（例如只启动几百个线程）时，GPU 甚至比 CPU 还慢。
- 估计一个程序能否用满显存带宽：在途字节数 = 带宽 × 延迟。H100 上每个流多处理器约需 9 kB 在途，线程束不够多时，让每个线程一次读 16 字节（`float4`）或同时发出几次独立的读取。
- 本书把在 CPU 上执行的部分称为主机端，在 GPU 上执行的称为设备端（第 4 章），两者之间的数据传输往往是被忽视的瓶颈。
