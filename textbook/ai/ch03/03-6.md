### 3.6.1 问题的提出

回到检测工位（算例 3.1.1）。每个线程负责一个像素：先做滤波，再判断“是不是缺陷”，是缺陷的像素还要做一段额外的处理，比如计算缺陷区域的边界。在 CPU 上，这样的 `if` 语句几乎不花代价——分支预测猜对了就不耽误时间，不是缺陷的像素直接跳过那段处理。在 GPU 上却不一样：同一个线程束的 32 个线程是一起执行指令的，有的要做额外处理、有的不要时，会发生什么？本节说明 GPU 执行指令的方式——SIMT，并用 GPU 执行模拟器量出一个分支的代价。

### 3.6.2 SIMT：单指令多线程

3.5 节说过，一个处理块的调度器每个周期发出一条指令，由 32 条运算通道同时执行。这 32 条通道执行的是同一条指令，各自处理自己线程的数据。这 32 个一起执行的线程称为一个**线程束**（warp）。一个线程块的线程按编号顺序每 32 个分成一个线程束：线程 0～31 是第一个，32～63 是第二个，依此类推。

从硬件看，这就是 SIMD：一条指令，32 份数据。但与 CPU 的向量指令不同，程序员写的不是“对 16 个数做加法”的向量指令，而是一个普通的、只处理一个元素的标量程序（核函数），每个线程执行它的一个实例，有自己的寄存器，可以有自己的分支和循环。硬件自动把 32 个线程拼成一条 SIMD 指令执行，并记录每个线程是否参与当前这条指令（称为活动掩码）。NVIDIA 把这种方式称为**单指令多线程**，简称 SIMT。

SIMT 让程序员用简单的标量思维写出大规模并行的程序，这是 CUDA 易学的重要原因。但硬件毕竟是 SIMD，标量程序中的分支会带来代价。

### 3.6.3 线程束分化

设核函数中有这样一段：

```cpp
x = ...;                  // 分支前：所有线程都执行
if (cond(threadIdx.x)) {
    y = f(x);             // then 路径
} else {
    y = g(x);             // else 路径
}
z = h(y);                 // 分支后：所有线程都执行
```

如果一个线程束的 32 个线程条件都成立（或都不成立），线程束只执行 then（或 else）一条路径，没有损失。如果有的成立、有的不成立，线程束就不得不两条路径都执行：先执行 then 路径，这时条件不成立的线程被掩码关闭、空转；再执行 else 路径，条件成立的线程空转；两条路径都执行完后，所有线程重新汇合，一起执行分支后的指令（Volta 以后的变化见 3.6.6 节）。这种现象称为**线程束分化**。

衡量分化的损失，用 SIMT 效率：

$$
\text{SIMT 效率} = \frac{\text{活动线程·指令数}}{32\times\text{发射的指令数}} , \tag{3.6.1}
$$

分子是每条发射的指令上实际参与的线程数之和，分母是假如每条指令 32 个线程都参与时的数。没有分化时效率为 100%。

**算例 3.6.1** 用 GPU 执行模拟器（部分 ②）计算：分支前后各 2 条指令，then、else 两条路径各 4 条。按线程号的奇偶分支时，每个线程束里奇、偶线程各占一半，两条路径都要执行，每个线程束发射 {{ex3_6.odd_issued}} 条指令；没有分支时只需 {{ex3_6.none_issued}} 条。用时是 {{ex3_6.ratio_time:.1f}} 倍，SIMT 效率为 {{ex3_6.odd_eff:.0f}}%（图 3.6.1(a)）。按“线程号小于 16”分支，结果完全相同。改为按线程束的编号分支（例如 `if ((threadIdx.x / 32) % 2)`），同一个线程束的线程条件一致，每个线程束只走一条路径，效率为 {{ex3_6.warp_eff:.0f}}%（图 3.6.1(b)）。

### 3.6.4 按数据分支

实际的分支条件往往取决于数据，比如“这个像素是不是缺陷”。设每个线程的条件以概率 $p$ 成立、彼此独立，则一个线程束的 32 个线程全走同一条路的概率是

$$
p^{32} + (1 - p)^{32} . \tag{3.6.2}
$$

**算例 3.6.2** 用模拟器对 4096 个线程束、同样的程序计算。$p = 0.5$ 时几乎每个线程束都分化，效率 {{ex3_6.eff50:.1f}}%，与奇偶分支相同。$p = 0.9$ 时，按式 (3.6.2) 只有 {{ex3_6.uni90:.1f}}% 的线程束不分化（模拟中为 {{ex3_6.fu90:.1f}}%），效率仍只有 {{ex3_6.eff90:.1f}}%——90% 的线程走同一条路，也几乎无济于事。$p = 0.99$ 时不分化的线程束占 {{ex3_6.uni99:.1f}}%（模拟 {{ex3_6.fu99:.1f}}%），效率升到 {{ex3_6.eff99:.1f}}%；$p = 0.999$ 时为 {{ex3_6.uni999:.1f}}%（模拟 {{ex3_6.fu999:.1f}}%），效率 {{ex3_6.eff999:.1f}}%。

可见在 GPU 上，“少数情况才走的分支”并不便宜：只要一个线程束里有一个线程要走，整个线程束都要陪着走一遍。缺陷像素只占 1% 时，仍有约四分之一的线程束要执行缺陷处理的代码。

### 3.6.5 减少分化的方法

**重新组织数据。**先用一个核函数把需要额外处理的像素挑出来、紧凑地排在一起，再用另一个核函数只处理它们。这样第二个核函数的每个线程束里全是缺陷像素，没有分化。这种“筛选—压缩”的模式在 GPU 程序中非常常见，第 6 章会用前缀和实现它。

**让短分支变成选择。**如果两条路径都很短（如 ReLU 的 `x > 0 ? x : 0`），编译器会把分支改写成“两边都算、再按条件选一个结果”，称为谓词执行。这样根本没有分支，代价是多算一点。

**注意长短不一的循环。**分化不只来自 `if`。如果每个线程的循环次数不同，整个线程束要一直执行到循环次数最多的那个线程结束，其余线程在后面的轮次中空转。自然语言处理中，一批句子长短不一时补齐到同样长度，在填充的位置上做无用的计算，道理相同；把长度相近的句子分到同一批，就能减少这种浪费。

### 3.6.6 独立线程调度

早期的 GPU 一个线程束只有一个程序计数器，分化的两条路径必须一条执行完再执行另一条。从 Volta 架构（2017 年）开始，NVIDIA 引入独立线程调度：每个线程有自己的程序计数器，硬件可以在两条分化的路径之间交替执行，这让线程束内的线程可以安全地互相等待（例如等待另一个线程释放一把锁）。但这并没有消除分化的代价：任何时刻，一个线程束仍然只执行一条指令，不在这条路径上的线程仍然空转。独立线程调度带来的是正确性上的便利，而不是性能上的。也因为这个变化，同一个线程束的线程不再保证步调一致，分化的线程也不保证在分支结束处自动汇合（编译器通常会插入汇合的指令），程序需要它们同步时，要显式调用 `__syncwarp()`（第 6 章）。

### 3.6.7 GPU 执行模拟器与实验

本节和 3.7 节的算例用的是本书的 **GPU 执行模拟器**。它是一个逐周期执行的教学模型。调度部分（3.7 节）模拟一个调度器和它的线程束，指令只有“读显存”和“算术”两种示意性的类型，读显存的延迟是固定值，算术指令之间没有依赖延迟、可以逐周期连发（真实 GPU 上互相依赖的乘加指令之间有约 4 个周期的延迟）；分化部分按 3.6.3 节的规则统计两条路径上发射的指令和活动线程，不逐周期模拟。它不模拟缓存、双发射、寄存器存储体等细节，也不对应任何真实的指令集，因此它给出的周期数只用来比较不同写法的相对好坏。模拟器有两个版本：书中程序用的 Python 版（`code/_gpusim.py`）和实验用的网页版，两者逐行对应，测试保证它们在同一组参数下给出相同的结果。

**工程师笔记**

- 判断分化：看分支条件是否只依赖 `threadIdx.x / 32` 及以上的量（如 `blockIdx`）。依赖线程号低 5 位或依赖数据的分支，都可能分化。
- 罕见情况的处理（越界检查、异常值）不必担心：边界上只有一两个线程束分化。需要担心的是比例在 1% 到 99% 之间、又很长的分支。
- Nsight Compute 报告中的“每个线程束的平均活动线程数”（Avg. Active Threads Per Warp）和“分化的分支数”（Divergent Branches）直接给出分化的程度（第 7 章）。
