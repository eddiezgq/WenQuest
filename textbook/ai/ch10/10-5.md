### 10.5.1 问题的提出

既然硬件会换，能不能一开始就写得与厂商无关？能，但要付出代价：越可移植的写法，离硬件越远，越难榨干它。关键是知道自己站在哪一层（图 10.5.1）。

### 10.5.2 四个层次

**框架层（PyTorch 等）**：最可移植的一层。模型用框架的算子搭起来，换硬件时换一个后端：NVIDIA 与 AMD 是上游支持，昇腾用 `torch_npu`、摩尔线程用 `torch_musa` 这样的扩展。绝大多数人应该停在这一层——第 7 章讲过，框架本身的开销与融合才是常见瓶颈，不是语言。

**编译器层（torch.compile 及各家后端）**：把一段模型图交给编译器，由它生成融合后的核函数。NVIDIA 与 AMD 上都成熟（第 7、8 章），国产后端在补。可移植性来自“你描述的是计算，不是指令”。

**Triton**：用 Python 写核函数，描述块怎样搬、怎样算，由编译器决定线程怎样排（8.6 节）。NVIDIA 与 AMD 是上游一等后端，同一份 Triton 代码两边都能编译；昇腾的后端在 Triton 官方组织下的独立仓库里，Intel 的 GPU 也有。**对自定义算子，Triton 是今天性价比最高的可移植写法**——这也是第 8 章用它而不是用 CUDA 写融合算子的原因之一。

**厂商语言（CUDA C++、HIP、Ascend C、BANG C……）**：最快，也最绑定。HIP 与 CUDA 近乎同构，两者之间移植便宜；到昇腾、寒武纪就是另一套模型了。

还有一条横着的路：**SYCL**（Intel 的 oneAPI 与社区的 AdaptiveCpp 是两种实现）与更老的 **OpenCL**，它们用标准 C++ 写一份代码、编到多家硬件。标准漂亮，但在人工智能这一侧，主流框架与算子库并不以它们为主路径，各家的后端也要自己构建，实际使用远不如 Triton 与厂商语言普遍。教学上它们仍值得讲：OpenCL 的经历说明，可移植标准赢不了生态——库、工具、文档、社区比语言本身更决定一家的生死。

### 10.5.3 写得可移植的几条习惯

即使用 CUDA 写，也能让以后的移植便宜得多：

- 用 `warpSize` 而不是常数 32；归约的循环起点写成 `warpSize / 2`（10.2.3 节）。
- 分块大小、每个线程算几个输出这类参数做成模板参数或常量，别散落在代码里。
- 把厂商库的调用集中在少数几个文件里，核心算法与库解耦（算例 10.2.1 中最难移植的恰是整篇调库的那个文件）。
- 正确性检查与算法分开写，移植后第一件事是跑同一套检查（全 1 求和、与 CPU 逐位比较）。
- 自定义算子优先用 Triton；非写不可时，先写一个正确的参考实现，再写快的那个。

**工程师笔记**

- 多数项目应该停在框架层；真正要写核函数时先问“Triton 够不够”。
- 可移植不是目标，可换才是：把绑定集中起来，换的时候只动那几处。
- 别被“一份代码跑遍所有硬件”说服就放弃实测——同一份代码在两家硬件上的效率可以差几倍。
