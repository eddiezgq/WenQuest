**一字不改的：向量加法。** 用 `hipify-perl` 转一遍，变的只有名字；核函数一个字没改（程序 10.6.1）。

### 10.6.3 没有 AMD 卡也能核对

本书的构建机上没有 AMD 显卡。三个 HIP 程序仍每次构建都被检查一遍：用 AMD 开源的 **HIP-CPU**（一组头文件，把 HIP 的核函数当作 CPU 上的并行循环执行）编译运行，每个程序自己与主机算出的参照比较，不一致就报错（`textbook/tools/hipcheck.py`）。HIP-CPU 不是 GPU 的仿真，跑出来的时间没有意义——它只回答“逻辑对不对”。有意思的是，HIP-CPU 把 `warpSize` 设为 64，所以归约那个错版在它上面也会错，错的方式与真卡一致（程序 10.6.2 的输出）。

这与第 4、5 章的做法是一脉相承的：没有显卡时用 clang 的 CUDA 前端做编译检查、用 CPU 逐线程块模拟核对下标（第 5 章的程序说明），有显卡时才测速度。**正确性在哪里都能查，性能只能实测。**

### 10.6.4 性能部分

AMD 与昇腾上的实测（三个程序的速度、与 A10 的对照、rocBLAS 与 cuBLAS 的差距、Ascend C 版矩阵乘法）要等问渠接上相应的云平台。接上之后，本节的数字会按与第 4—9 章相同的方式补入，并注明芯片型号、ROCm 或 CANN 的版本与时间。

### 10.6.5 一个移植清单

把本章的做法收成一张可照做的清单：

1. 先扫一遍代码，估工作量（程序 10.2.2）；把库调用的位置标出来。
2. 用 HIPIFY 转换，先编译通过。
3. 检查与线程束宽度有关的每一处：洗牌、掩码、每块的波前数、共享内存的大小。
4. 跑原来的正确性检查；没有检查就先补一个（全 1、小矩阵与 CPU 逐位比较）。
5. 再谈性能：重调分块与每线程的工作量，必要时按 MFMA 的形状重写张量核心部分。
6. 记录下来：哪些自动换、哪些手改、花了多少时间——这是下次选型时最有用的数据。

**工程师笔记**

- 移植的顺序永远是“能编译 → 结果对 → 再调快”，跳过第二步最费时间。
- 库调用集中在少数文件里，移植成本能降一大截（算例 10.2.1）。
- 在没有目标硬件的机器上也要把正确性检查自动跑起来，别等拿到卡才发现逻辑错。
