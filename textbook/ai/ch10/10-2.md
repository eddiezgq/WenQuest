### 10.2.1 问题的提出

手上是第 4、5 章写好的 CUDA 程序，机器换成了 AMD 的 MI300X。要从头再学一套编程模型吗？不用：AMD 的 **HIP** 几乎是 CUDA 的同义词改名——`cudaMalloc` 叫 `hipMalloc`，`__global__`、`threadIdx`、`__shared__`、`__syncthreads` 一字不改，核函数的写法完全一样。AMD 还提供 **HIPIFY** 自动完成改名。真正要动脑筋的是名字换不掉的那部分：硬件本身不一样。

### 10.2.2 ROCm 与 HIP

以下软件栈的状况截至 2026 年 10 月。**ROCm** 是 AMD 的 GPU 计算软件栈，相当于 CUDA 工具包：编译器（`hipcc`）、运行时、库与调试工具。各层的对应关系：

| CUDA | ROCm | 作用 |
|---|---|---|
| CUDA C++ | HIP | 编程语言与运行时接口 |
| 线程束（warp，32 道） | 波前（wavefront，64 道） | 一起执行同一条指令的一组线程 |
| SM（流多处理器） | 计算单元（CU） | 片上的基本处理单元 |
| 共享内存 | 本地数据共享（LDS） | 线程块内共享的片上存储 |
| 张量核心（WMMA） | 矩阵核心（MFMA 指令、rocWMMA 库） | 做小矩阵乘累加的硬件单元 |
| cuBLAS / cuDNN / NCCL / CUB | rocBLAS、hipBLASLt / MIOpen / RCCL / hipCUB | 矩阵、卷积、集合通信、并行原语 |
| Nsight Systems / Compute | rocprof / ROCm Systems Profiler、ROCm Compute Profiler（旧称 Omnitrace、Omniperf） | 性能分析 |

PyTorch 对 ROCm 是上游支持：装上 ROCm 版的 PyTorch 后，程序里的设备名仍写 `"cuda"`，`torch.cuda` 的接口照常可用——这是为了让已有代码不改，不是笔误。

### 10.2.3 波前 64 道

**波前**是 AMD 上与线程束对应的概念，CDNA 架构（数据中心卡）固定 64 道；消费级的 RDNA 可以是 32 道也可以是 64 道。凡是把 32 写进代码的地方都要重看：

- **线程束内归约**：32 道 {{ex10_2.n_steps}} 层洗牌，64 道要 {{ex10_2.a_steps}} 层。把循环起点写死 16 的版本搬过去，每个波前只算出低 32 道与高 32 道各自的和，结果约为正确值的一半（程序 10.6.2 在 CPU 上验证了这一点）。可移植的写法是起点取 `warpSize / 2`。
- **掩码**：CUDA 的 `__shfl_down_sync(0xffffffff, …)` 用 32 位掩码；HIP 的洗牌不带掩码参数，64 道的集体投票（`__ballot`）返回 64 位。
- **每个线程块的波前数**：256 个线程在 32 道上是 {{ex10_2.n_groups}} 个线程束，在 64 道上是 {{ex10_2.a_groups}} 个波前，暂存部分和的共享内存从 {{ex10_2.n_smem}} 字节减到 {{ex10_2.a_smem}} 字节。
- **一次访存请求的大小**：每道读 4 字节时，32 道一次请求 {{ex10_2.n_req}} 字节（正好一个缓存行），64 道 {{ex10_2.a_req}} 字节（图 10.2.1）。按 128 字节精心对齐的写法（第 4 章）在 64 道上要重新想一遍。
- **占用率**：片上存储的容量不同——A10 每个 SM 100 KB，CDNA 3 每个计算单元 64 KB，CDNA 4 增加到 160 KB。分块矩阵乘法每块用 {{ex10_2.tile_KB:.0f}} KB，单看这一道限制，三者分别允许驻留 {{ex10_2.tile_a10}}、{{ex10_2.tile_cdna3}}、{{ex10_2.tile_cdna4}} 块。但这只是其中一道：这个核函数每块 1024 个线程，A10 每个 SM 最多驻留 1536 个线程，所以实际只能驻留 {{ex10_2.tile_a10_threads}} 块（3.7 节、算例 5.9.2）——各家的线程、寄存器与工作组上限都不同，占用率要几道一起看。

### 10.2.4 HIPIFY 能做什么

HIPIFY 有两个工具：`hipify-perl` 是文本替换，不懂语义，装上就能用，适合先看一眼工作量；`hipify-clang` 用 Clang 前端把 CUDA 解析成语法树再改写，复杂的模板和宏也能处理，但要求代码能被正确解析（头文件齐全）。两者都只改接口名，不改算法。

**算例 10.2.1** 程序 10.2.2 扫描本书第 4—7 章的 CUDA 程序（内容相同的副本只数一遍，共 {{ex10_2b.n_files}} 个文件、{{ex10_2b.n_lines}} 行），分四类：内建变量与限定符 {{ex10_2b.n_same}} 处一个字都不用改（HIP 里是同一个名字）；运行时接口、头文件、启动语法、原子操作等 {{ex10_2b.n_auto}} 处可以自动替换，占要改的 {{ex10_2b.n_change}} 处的 {{ex10_2b.pct_auto:.0f}}%；与线程束绑在一起的（洗牌、作掩码用的 32 位全 1、写死起点的归约循环）{{ex10_2b.n_hand}} 处要人看一眼；张量核心、HIP 没有对应物的内建函数与厂商库共 {{ex10_2b.n_rewrite}} 处要重写。{{ex10_2b.n_files}} 个文件里有 {{ex10_2b.n_clean}} 个一处都不用人改。要重写最多的是 `{{ex10_2b.worst}}`（{{ex10_2b.worst_rewrite}} 处），它整篇都在调 cuDNN——**库调得越深，移植越贵**。

### 10.2.5 库与生态

移植的难点几乎总在库上：

- 矩阵乘法与卷积：rocBLAS、hipBLASLt、MIOpen 与 cuBLAS、cuBLASLt、cuDNN 大致对应，接口名也刻意相近，但自动调优的结果、支持的数据类型组合与尾处理（第 7 章）不会完全一致。
- 集合通信：RCCL 的接口与 NCCL 相同（第 6 章的程序几乎不用改），拓扑与算法不同，带宽要重测。
- 张量核心：CUDA 的 WMMA 片段接口在 AMD 上对应 rocWMMA 库，底层是 MFMA 指令（如 `v_mfma_f32_32x32x8f16`，形状与 NVIDIA 的 16×16×16 不同）。用了 WMMA 的核函数要按 AMD 的形状重排数据。
- Triton（第 8 章）：AMD 是上游支持的后端，用 Triton 写的核函数改一行都不用就能在 ROCm 上编译——这是本书推荐用 Triton 写自定义算子的一个额外理由（10.5 节）。

### 10.2.6 实测

AMD 卡上的实测（矩阵乘法各版本的速度、HIP 与 CUDA 的差距、rocBLAS 与 cuBLAS 的对照）要等问渠接上 AMD 的云平台后补入；在那之前，本章的 HIP 程序在没有显卡的机器上核对正确性（10.6.3 节），性能部分只给纸面估算。

**工程师笔记**

- 新写 CUDA 代码时就按可移植的习惯来：用 `warpSize` 而不是 32，少用只有一家有的接口，算子优先用 Triton 写。
- 先用 `hipify-perl` 粗转一遍看工作量，工程化迁移用 `hipify-clang`。
- 移植后的第一件事不是测速度，是用和原来一样的检查（全 1 求和、与 CPU 逐位比较）确认结果对；波前宽度的错误往往不报错，只是数值不对。
