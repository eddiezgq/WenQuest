### 4.8.1 问题的提出

到目前为止的核函数，每个线程只写自己的那一份结果，线程之间互不相干。但很多计算要把许多线程的结果合在一起：统计检测图像的灰度直方图，每个像素要给 256 个箱中的一个加 1，成千上万个线程会同时去加同一个计数器。本节讨论线程之间怎样安全地协作：数据竞争、同步、原子操作，以及 CUDA 提供的协作组。

### 4.8.2 数据竞争

“给计数器加 1”在硬件上是三步：从内存读出、在寄存器里加 1、写回内存。两个线程同时做时，这三步可能交错。

**算例 4.8.1** 计数器原来是 5，线程 A、B 各给它加 1。若执行顺序是：A 读（5）、B 读（5）、A 写（6）、B 写（6），结果是 {{ex4_8.counter}} 而不是 7，丢了 {{ex4_8.lost}} 次加法（图 4.8.1(a)）。

两个以上的线程访问同一个地址、至少有一个在写、又没有确定先后的机制，称为**数据竞争**。它的结果取决于线程碰巧的执行顺序，每次运行都可能不同，是并行程序中最难发现的错误。compute-sanitizer 的 `racecheck` 能发现共享内存上的数据竞争。

### 4.8.3 线程块内的同步

`__syncthreads()` 是线程块内的**屏障**：块内每个线程执行到这里都要停下，等所有线程都到了，才一起继续；并且屏障之前对共享内存和全局内存的写，屏障之后对块内所有线程可见。4.7 节的转置中，线程先把数据写进共享内存，`__syncthreads()` 之后再读别的线程写的数据，就是这种用法。

使用 `__syncthreads()` 有一条铁律：块内所有线程都必须执行到同一个 `__syncthreads()`。把它放在只有部分线程进入的分支里（如 `if (threadIdx.x < 16) __syncthreads();`），会使程序挂起或产生未定义的结果；compute-sanitizer 的 `synccheck` 能发现这种错误。

线程块之间没有这样的屏障：一个核函数中，不同线程块不能互相等待（3.5.8 节；同一线程块簇内的线程块例外，4.2.2 节）。需要全局同步时，通常把计算拆成两个核函数，两次启动之间的边界就是全局的同步点；协作组（4.8.5 节）也提供了受限的全网格同步。

### 4.8.4 原子操作

**原子操作**把“读—改—写”作为一个不可分割的整体完成，其他线程不会在中间插进来。最常用的是 `atomicAdd(&addr, v)`：把 `v` 加到 `addr` 处，并返回原来的值。此外还有 `atomicSub`、`atomicMax`、`atomicMin`、`atomicExch`、`atomicCAS`（比较并交换，可以用它实现任意的原子操作）等，都能用于全局内存和共享内存。支持的类型因函数而异：`atomicAdd` 支持整数、单精度、双精度（计算能力 6.0 起）和半精度；`atomicSub`、`atomicMax`、`atomicMin` 只支持整数；`atomicCAS` 按整数的位模式比较，浮点数要先转成同宽度的整数。

用原子操作统计直方图：

```cpp
__global__ void hist(const uint8_t* y, int n, unsigned* bins) {
    for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += gridDim.x * blockDim.x)
        atomicAdd(&bins[y[i]], 1u);
}
```

结果正确了，但不一定快。多个线程同时对同一个地址做原子操作时，硬件只能一个一个地完成，这称为**争用**。

**算例 4.8.2** 测试图共 {{ex4_8.px}} 个像素，只用到 {{ex4_8.bins_used}} 个灰度级（图 4.8.1(b)），最多的一个灰度级有 {{ex4_8.top_count}} 个像素。相邻像素的灰度往往相同：抽样统计，一个线程束的 32 个相邻像素中，像素最多的那个箱平均有 {{ex4_8.mean_serial:.1f}} 个，这个线程束的原子操作就要排至少这么多次队。直接对全局内存做原子加法，共 {{ex4_8.global_atomics_M:.2f}} 百万次。

**私有化**是减少争用的标准办法：每个线程块先在共享内存里建一份自己的 256 个箱，块内的线程对共享内存做原子加法（快得多，而且只和本块的线程争用）；块内统计完、同步之后，再把这 256 个箱加到全局的直方图上。用网格跨步循环、{{ex4_8.blocks}} 个线程块时，全局的原子操作只剩 {{ex4_8.private_atomics_M:.3f}} 百万次，减少到约 1/{{ex4_8.reduce:.0f}}。

### 4.8.5 协作组

**协作组**是 CUDA 9 引入的接口，用来显式地描述“哪一组线程在一起协作”。常用的几种：

```cpp
#include <cooperative_groups.h>
#include <cooperative_groups/reduce.h>                       // cg::reduce、cg::plus
namespace cg = cooperative_groups;

cg::thread_block block = cg::this_thread_block();          // 本线程块
block.sync();                                               // 等价于 __syncthreads()
cg::thread_block_tile<32> warp = cg::tiled_partition<32>(block);   // 按 32 个线程分组：一个线程束
float s = cg::reduce(warp, x, cg::plus<float>());           // 线程束内求和（CUDA 11 起）
```

协作组的好处是把“同步的范围”写进类型里：对一个线程束的组同步，就只等这 32 个线程；对整个网格的组同步（`cg::this_grid().sync()`，需要以协作方式启动核函数，且所有线程块必须同时驻留在 GPU 上），可以实现全局屏障。3.6.6 节说过，Volta 以后线程束内的线程不再保证步调一致，用协作组或 `__syncwarp()` 显式同步，才能写出正确的线程束级代码。

**工程师笔记**

- 写共享内存之后、别的线程读之前，一定要 `__syncthreads()`；循环中反复使用同一块共享内存时，下一轮写之前也要再同步一次。
- 原子操作先在共享内存里做，再合并到全局内存；对同一个地址的大量原子操作是性能杀手。
- 浮点数的原子加法顺序不确定，结果在最后几位上每次可能不同（3.1.6 节）。
