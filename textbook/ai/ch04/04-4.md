### 4.4.1 问题的提出

GPU 程序出错时往往不会崩溃，而是悄悄地算出错误的结果：越界的线程写坏了别的数据，没有同步的线程读到了旧值，启动配置不合法时核函数根本没有运行。成千上万个线程同时执行，也让传统的单步调试很难用。本节讲怎样让错误尽早暴露出来，以及几种调试工具。

### 4.4.2 检查每一个调用

CUDA 运行时的每个函数都返回一个错误码（类型 `cudaError_t`），成功时为 `cudaSuccess`。不检查它，错误就会被忽略，直到后面某个不相干的地方出现奇怪的现象。本书的程序都用程序 4.4.1 中的宏 `CHECK` 包住每个调用：出错时打印文件名、行号和错误说明，然后退出。

核函数的启动没有返回值，它的错误分两种。一是**启动错误**：启动配置不合法（例如每块 2048 个线程）、资源不够，核函数根本没有运行；启动后立即调用 `cudaGetLastError()` 就能查到。二是**执行错误**：核函数运行中发生越界访问等，由于执行是异步的，要等它结束时才知道，通常在下一个同步的调用（如 `cudaMemcpy`、`cudaDeviceSynchronize`）返回时报告。程序 4.4.1 的 `CHECK_LAUNCH` 两者都查。调试时在每个核函数后都调用它，定位错误；正式运行时去掉同步，以免损失并行性。

一个执行错误（如非法地址访问）发生后，这个进程的 CUDA 上下文就损坏了，此后所有 CUDA 调用都会返回同一个错误，只能重启进程。所以看到错误信息时，要找的是第一次出错的地方。

### 4.4.3 compute-sanitizer

CUDA 工具包中的 compute-sanitizer 在程序运行时检查每一次内存访问，类似于 CPU 上的 Valgrind：

- `memcheck`（默认）：越界访问、访问已释放的内存、未对齐的访问；
- `racecheck`：共享内存上的数据竞争（4.8 节）；
- `initcheck`：读了没有初始化的显存；
- `synccheck`：`__syncthreads()` 的错误用法（4.8 节）。

用法是在程序前加上它：`compute-sanitizer --tool memcheck ./vadd`。它会指出出错的核函数、线程编号、源代码行和访问的地址。程序会因此慢几十到几百倍，所以调试时用小规模的数据。

**例** 把程序 4.1.1 中的 `if (i < n)` 去掉、取 $n = 1000$，程序可能照常运行、结果看起来也对——最后 24 个多余的线程读、写了数组后面不属于它的显存。memcheck 会报告读、写两类越界（“Invalid __global__ read of size 4”“Invalid __global__ write of size 4”），涉及线程块 (3, 0, 0) 中的线程 232～255，例如线程 (232, 0, 0)，它的 $i = 3\times256 + 232 = 1000$。

### 4.4.4 其他调试手段

**核函数中的 printf。**核函数可以调用 `printf`，输出在核函数结束后显示。它是最简单的调试手段，但成千上万个线程一起打印会淹没屏幕，要加条件只让个别线程打印，如 `if (i == 0) printf(...)`。

**cuda-gdb。**CUDA 版的 gdb，可以在核函数中设断点、切换到指定的线程块和线程查看变量。编译时加 `-G` 生成设备端的调试信息（会关闭大部分优化）。

**与 CPU 的结果比较。**最可靠的验证方法是：用 CPU 上简单、可信的实现算出同样的结果，逐元素比较。本书的每个 GPU 程序都这样做：程序 4.2.2 在 CPU 上数出的暗斑像素数，就是检查灰度化核函数的参照。浮点运算要允许微小的误差（3.1.6 节）；整数运算，以及每个结果只经过一次加法或比较的运算，应当完全相同。还要注意，`nvcc` 默认把乘法和加法合成一条融合乘加（FMA）指令，只舍入一次，所以 GPU 上的浮点结果可能与 CPU 上差最后一位；灰度化取整后个别像素可能差一级，本书的测试图已经核对过没有这样的像素。

**工程师笔记**

- 所有 CUDA 调用都包上 `CHECK`；调试阶段每个核函数后 `CHECK_LAUNCH`。
- 结果不对时，第一件事是用 compute-sanitizer 跑一遍小规模的数据。
- PyTorch 中，设置环境变量 `CUDA_LAUNCH_BLOCKING=1` 让每个核函数同步执行，报错的位置才是真正出错的地方。
