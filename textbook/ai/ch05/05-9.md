### 5.9.1 寄存器分块

5.8 节的分块版中，每个线程算 $C$ 的一个元素：从共享内存读 $A$ 的一个数、$B$ 的一个数，只做一次乘加。如果每个线程算 $C$ 的 $t_m\times t_n$ 个元素，那么每一步 $k$ 读 $A$ 的 $t_m$ 个数、$B$ 的 $t_n$ 个数放进寄存器，就能做 $t_m t_n$ 次乘加——两个向量的**外积**（图 5.9.1(c)）。每次乘加读共享内存的次数从 2 降到

$$
\frac{t_m + t_n}{t_m t_n} , \tag{5.9.1}
$$

$t_m = t_n = t$ 时为 $2/t$。这就是**寄存器分块**：共享内存的块被块内的线程复用，寄存器中的数又被同一个线程复用。

**算例 5.9.1** 线程块负责 $C$ 的 128×128 块，沿 $K$ 每步 8。由 GPU 执行模拟器部分 ⑤：每个线程算 1×1、2×2、4×4、8×8 个元素时，每次乘加读共享内存 {{ex5_9.smem_1:.0f}}、{{ex5_9.smem_2:.0f}}、{{ex5_9.smem_4:.1f}}、{{ex5_9.smem_8:.2f}} 个数，线程块分别要 {{ex5_9.thr_1}}、{{ex5_9.thr_2}}、{{ex5_9.thr_4}}、{{ex5_9.thr_8}} 个线程。前两种的线程数超过了上限，第三种仍超过每次乘加 {{ex5_9.budget:.2f}} 次共享内存读的预算（算例 5.8.2）；8×8 在没有存储体冲突时恰好等于预算，用 256 个线程。这就是程序 5.7.1 中 `regtile` 的选择。

块大了，显存的复用也更好：计算强度（不计缓存）升到 {{ex5_9.I:.1f}} FLOP/B。共享内存只要两块 128×8 的单精度数，共 {{ex5_9.smem_KB:.0f}} KB；每个线程要 {{ex5_9.acc}} 个寄存器放累加和，加上从共享内存取来的 16 个数和地址，约 {{ex5_9.regs}} 个寄存器。程序中给核函数加了 `__launch_bounds__(256, 2)`，要求编译器把寄存器控制在 65 536 ÷ (256 × 2) = 128 个以内；实际用了多少、有没有溢出到本地内存，程序运行时用 `cudaFuncGetAttributes` 查出：`regtile` {{run5_7.regtile_regs}} 个、`vec` {{run5_7.vec_regs}} 个、`dbuf` {{run5_7.dbuf_regs}} 个寄存器（溢出 {{run5_7.dbuf_spill}} 字节）。

```cpp
for (int k = 0; k < BK; k++) {
    for (int i = 0; i < TM; i++) ra[i] = As[k][trow * TM + i];   // A 的 8 个数
    for (int j = 0; j < TN; j++) rb[j] = Bs[k][tcol * TN + j];   // B 的 8 个数
    for (int i = 0; i < TM; i++)
        for (int j = 0; j < TN; j++) acc[i][j] += ra[i] * rb[j];  // 64 次乘加
}
```

`acc`、`ra`、`rb` 是局部数组，但所有循环的次数都是编译时常量，编译器把它们完全展开，下标都变成常量，三个数组就都放在寄存器里（4.5 节说过，用变量下标访问的局部数组只能放在本地内存）。`A` 的块在共享内存中转置存放（`As[k][m]`），这样内层循环读的 8 个数是连续的。

### 5.9.2 占用率与指令级并行

**算例 5.9.2** 每个线程约 {{ex5_9.regs}} 个寄存器，每个线程块 256 个线程，一个 SM 的 65 536 个寄存器只够放 {{ex5_9.blocks_sm}} 个线程块、{{ex5_9.warps_sm}} 个线程束，占用率只有 {{ex5_9.occ:.0f}}%（A10 每个 SM 最多 48 个线程束）。按 3.7 节的思路，这么少的线程束能藏住延迟吗？

能。每个线程束一步之内有 64 条互不依赖的乘加指令，调度器可以从同一个线程束里连续发出，不必等前一条的结果。这是 3.7.5 节沃尔科夫的观点：线程级并行不够时，用指令级并行补上——**更低的占用率，更高的性能**。寄存器分块的矩阵乘法是这一观点最好的例子。

实测（{{run5_7._gpu}}）：`regtile` {{run5_7.regtile_GFs:.0f}} GFLOP/s。

### 5.9.3 向量化访存与存储体冲突

`regtile` 还有两处浪费。

第一处是读共享内存时的存储体冲突。一个线程束的 32 个线程中，`tcol` 取 0—15，线程读 `Bs[k][tcol*8 + j]`，16 个不同的字相隔 8 个字。由模拟器部分 ④，这是 {{ex5_9.ways_reg}} 路冲突。按算例 5.8.2 的算法：每一步 $k$，一个线程束读 $A$ 8 次（只有 2 个不同的字，在不同的存储体上，各 1 次访问）、读 $B$ 8 次（每次 {{ex5_9.ways_reg}} 次访问），共 40 次访问，配 64 条乘加指令，每条乘加 {{ex5_9.acc_reg:.3f}} 次访问，是预算的 2.5 倍——`regtile` 最多只能达到峰值的 {{ex5_9.bound_reg:.0f}}%。（编译器若把连续的读合成 128 位的读，情况会好一些，以 SASS 为准。）

第二处是指令数。读 8 个连续的数要 8 条读指令。GPU 有一次读 16 字节的向量指令：把地址转换成 `float4*` 读，一条指令就读 4 个数。全局内存的读写也一样：`A`、`B` 的块用 `float4` 读进来，指令数减为四分之一。

版本 `vec` 同时解决这两个问题。线程负责的 8 列不再连续，而是分成两组：`tcol*4 + {0..3}` 与 `64 + tcol*4 + {0..3}`，行也一样（图 5.9.1(b)）。每组 4 个数用一条 `float4` 指令读。通常认为，16 字节的读按四分之一个线程束（8 个线程）为一组处理（这一规则来自微基准测试，NVIDIA 的文档没有明确写出，可以用 Nsight Compute 的共享内存访问次数验证）：一组 8 个线程读的正好是连续的 32 个字，落在 32 个不同的存储体上，冲突路数为 {{ex5_9.ways_vec}}。这样每一步 $k$ 是 4 条 128 位的读、共 16 次访问，配 64 条乘加指令，每条 {{ex5_9.acc_vec:.2f}} 次，正好等于预算。可见 `vec` 并没有减少共享内存要搬的字节，它的收益在于消除冲突、把读指令从 16 条减到 4 条。

用 `float4` 访问时，地址必须是 16 字节对齐的：`cudaMalloc` 分配的地址至少按 256 字节对齐，矩阵的宽度是 4 的倍数，块的起点也是 4 的倍数，共享内存数组声明时加 `__align__(16)`。

实测：`vec` {{run5_7.vec_GFs:.0f}} GFLOP/s。

### 5.9.4 双缓冲

到这里，每一步仍是“读块—同步—计算—同步”：读块的几百个周期里，线程束只能等待（占用率又低，可供切换的线程束不多）。**双缓冲**让读与算重叠：共享内存开两份，计算这一份的时候，下一步的数据已经在往另一份里读。

```cpp
for (int t = 0; t < steps; t++) {
    Frag next;
    if (t + 1 < steps) next = load_tiles(…, (t + 1) * BK, …);    // 先发出下一步的读（不等它到）
    compute_step(As[cur], Bs[cur], …);                          // 读在路上时，计算这一步
    if (t + 1 < steps) store_tiles(next, As[cur ^ 1], Bs[cur ^ 1], …);
    __syncthreads();                                            // 每步只同步一次
}
```

读全局内存的指令发出后不必等结果，线程可以接着执行后面不依赖它的指令（3.7 节），所以把读提前到计算之前，读的延迟就被 64×8 次乘加盖住了。每步只需同步一次：写入另一份共享内存时，上一步的计算早已用完它（上一步末尾同步过）。代价是共享内存加倍，{{ex5_9.smem2_KB:.0f}} KB。

实测：`dbuf` {{run5_7.dbuf_GFs:.0f}} GFLOP/s。

计算能力 8.0（A100）起——包括我们用的 A10（8.6）——还可以用 `cp.async` 指令把数据从全局内存直接异步复制到共享内存，不经过寄存器；Hopper（9.0）进一步有张量内存加速器（TMA），一条指令搬一整块。CUTLASS 等库用它们做三级、四级的流水线。

程序 5.9.2 照抄 CUDA 程序的下标表达式，在 CPU 上逐个线程块地执行，共享内存的每个位置先填成 NaN：只要哪个位置没有被正确写入就被读到，结果中就会出现 NaN。三个核函数在 256×256 的矩阵上都与 NumPy 的结果完全一致。CUDA 程序中最容易出错的正是这些下标，在没有 GPU 的机器上先这样核对一遍，比在 GPU 上调试省事得多。但这种模拟只核对下标：缺了同步造成的数据竞争（例如 `dbuf` 少一次 `__syncthreads()`，模拟照样通过）、`float4` 的对齐、存储体冲突，它都查不出来。所以实测脚本在计时之前，还先在小矩阵上用 compute-sanitizer 的 racecheck 与 memcheck（4.4 节）各跑一遍。

**工程师笔记**

- 寄存器分块是矩阵乘法提速最多的一步：每个线程算 8×8（或 8×4、4×8）个输出，共享内存的读与乘加之比降到四分之一。
- 局部数组要用编译时常量的下标（循环展开）才能放进寄存器；编译时加 `-Xptxas -v` 检查有没有溢出到本地内存。
- `float4` 读写要求 16 字节对齐；读共享内存时按四分之一个线程束检查存储体冲突。
- 占用率低不一定慢：看指令级并行是否充足。
