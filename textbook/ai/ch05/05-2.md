### 5.2.1 问题的提出

检测程序要监视光源是否老化：每一帧算出全部像素的平均亮度，与开机时比较。这就要把几百万个数加起来。训练神经网络时这样的计算更多：损失是一个批次中各个样本损失的和，softmax 要对一行求和、求最大值，层归一化要求均值与方差，数据并行训练要把各 GPU 的梯度加起来。把许多个数用一个满足结合律的运算（加法、乘法、最大值、最小值……）合成一个数，称为**归约**。

3.1 节已经说明，归约可以组织成一棵树：第一层两两相加，第二层再两两相加，$n$ 个数 $\lceil\log_2 n\rceil$ 层就加完，工作量仍是 $n - 1$ 次加法。可是 GPU 上的线程分属不同的线程块，块与块之间不能同步（4.8 节），树要怎样“长”在线程块上？这一节从最直接的写法开始，经过五个版本，把归约的速度提高到接近显存带宽。前四个版本取自哈里斯（M. Harris）2007 年的一份 NVIDIA 技术报告（原报告有七个版本，是学习 CUDA 优化的经典材料）；第五个版本用到的线程束洗牌指令是 Kepler（2012）才引入的。这里按现代 GPU 的情况重写。

### 5.2.2 线程块内的树形归约

最直接的写法分两步。第一步，每个线程块负责 256 个数：每个线程把一个数读进共享内存，然后在共享内存里做树形归约，块内的 0 号线程把这块的部分和写到全局内存。第二步，再启动一个核函数，把所有线程块的部分和加起来。两次启动之间的边界就是全局的同步点。

树形归约的第一种写法（版本 1）照着图 5.2.1(a) 写：第 $s$ 层（$s = 1, 2, 4, \dots$）由编号是 $2s$ 的倍数的线程把位置 $\text{tid} + s$ 上的数加到自己的位置上，

```cpp
for (int s = 1; s < B; s *= 2) {
    if (tid % (2 * s) == 0) sm[tid] += sm[tid + s];
    __syncthreads();                           // 这一层全部加完，才能进入下一层
}
```

### 5.2.3 分化与存储体冲突

**算例 5.2.1** 线程块有 $B = {{ex5_2.B}}$ 个线程、8 个线程束，树形归约共 {{ex5_2.levels}} 层。版本 1 的第一层只有 {{ex5_2.v1_l1_active}} 个线程干活（判断条件 `tid % (2 * s)` 本身也不便宜：对变量取模要编译成十几到几十条整数指令），但它们分散在全部 {{ex5_2.v1_l1_warps}} 个线程束里，每个线程束都要发出加法指令，而其中一半的线程空转；越往上，每个线程束里干活的线程越少。用 GPU 执行模拟器（3.6 节）的规则统计，8 层合计要发出 {{ex5_2.v1_issued}} 条“线程束加法指令”，SIMT 效率只有 {{ex5_2.v1_eff:.0f}}%（程序 5.2.2）。

改进的办法是让干活的线程连在一起（版本 2）：第 $s$ 层由前 $B/(2s)$ 个线程干活，第 $\text{tid}$ 个线程处理位置 $k = 2s\cdot\text{tid}$，

```cpp
for (int s = 1; s < B; s *= 2) {
    int k = 2 * s * tid;
    if (k < B) sm[k] += sm[k + s];
    __syncthreads();
}
```

干活的线程挤在前面的线程束里，后面的线程束整个跳过，线程束指令降到 {{ex5_2.v2_issued}} 条，SIMT 效率升到 {{ex5_2.v2_eff:.0f}}%（只剩最后几层不足 32 个线程的线程束有空转）。但新的问题出现了：一个线程束的 32 个线程以跨步 $2s$ 个字访问共享内存，有存储体冲突（4.7 节）。由模拟器部分 ④，前四层分别是 {{ex5_2.v2_l1_ways}}、{{ex5_2.v2_l2_ways}}、{{ex5_2.v2_l3_ways}}、{{ex5_2.v2_l4_ways}} 路冲突。按“每条共享内存指令要分几次完成”合计，版本 1、2 都是 {{ex5_2.v1_passes}} 次。版本 2 省掉了大部分线程束指令和取模运算，所以仍比版本 1 快；但共享内存一侧的代价没有减少。

版本 3 换一种配对方式（图 5.2.1(b)）：第 $s$ 层（$s = B/2, B/4, \dots, 1$）由前 $s$ 个线程把后一半位置上的数加到前一半上，

```cpp
for (int s = B / 2; s > 0; s >>= 1) {
    if (tid < s) sm[tid] += sm[tid + s];
    __syncthreads();
}
```

干活的线程连在一起，没有分化；相邻线程访问相邻的字，也没有冲突。线程束指令和共享内存的访问次数都是 {{ex5_2.v3_passes}}。这种配对称为顺序寻址。

### 5.2.4 让每个线程多干活

版本 3 的树已经没有明显的浪费，但整个程序还有一个毛病：$n = 2^{25}$ 个数用了 $n/256 = {{ex5_2.part_v1}}$ 个线程块，每个线程只读一个数；树形归约的第一层就有一半线程闲着，之后每层再闲一半，8 次同步也都要付出。读一个数只做不到一次加法，却要付出这么多“管理”的代价。

由布伦特定理（定理 3.1.1），处理器个数有限时，最好的办法是先让每个处理器顺序地加一大段数，再把这些部分和用树加起来：顺序相加没有任何同步开销，树只需要处理“处理器个数”那么多的数。GPU 上的“处理器”就是同时驻留的线程。版本 4 只启动“SM 数 × 每个 SM 能同时驻留的线程块数”个线程块（程序中用 `cudaOccupancyMaxActiveBlocksPerMultiprocessor` 查出后者），正好一波，用网格跨步循环（4.2 节）让每个线程先在寄存器里加许多个数，最后再做一次版本 3 的树形归约：

```cpp
float s = 0.0f;
for (int i = blockIdx.x * B + threadIdx.x; i < n; i += gridDim.x * B) s += x[i];   // 读合并，只在寄存器里累加
s = block_tree(s, sm);                                                           // 版本 3 的树
```

A10 有 {{ex5_2.sms}} 个 SM，每个 SM 能驻留 {{ex5_2.fit}} 个 256 线程的线程块，于是启动 {{ex5_2.g_blocks}} 个线程块、{{ex5_2.g_threads}} 个线程，每个线程加约 {{ex5_2.per_thread:.0f}} 个数，树形归约的开销分摊到这么多个数上，可以忽略不计。部分和也从 {{ex5_2.part_v1}} 个减少到 {{ex5_2.g_blocks}} 个，第二个核函数几乎不花时间。这一步通常是五个版本中提速最多的。

### 5.2.5 线程束洗牌

版本 4 的树仍要经过共享内存、同步 9 次（写入后一次，每层一次）。最后 6 层（$s \le 32$）只剩 0 号线程束在干活，而一个线程束内的 32 个线程本来就在同一个调度器上执行，交换数据不必绕道共享内存。**线程束洗牌**指令让一个线程直接读同一线程束中另一个线程的寄存器：

```cpp
float v2 = __shfl_down_sync(0xffffffff, v, off);   // 第 lane 号线程得到第 lane + off 号线程的 v
```

第一个参数是参与的线程的掩码（32 位全 1 表示整个线程束）；`lane + off` 超出 31 时返回自己的值。连续做 5 次，`off` 取 16、8、4、2、1，0 号线程就得到 32 个数的和（动画 5.2.1 的后半段）：

```cpp
__device__ float warp_sum(float v) {
    for (int off = 16; off > 0; off >>= 1) v += __shfl_down_sync(0xffffffffu, v, off);
    return v;
}
```

版本 5 先用网格跨步循环累加，再在每个线程束内洗牌求和，每个线程束只把一个数写进共享内存；同步一次以后，0 号线程束把这 8 个数再洗牌加起来。整个线程块只同步一次，共享内存只用 32 字节。

洗牌指令的名字带 `_sync`，是因为 Volta 以后线程束内的线程不再保证步调一致（3.6.6 节）：掩码中的线程会先在这里会合，再交换数据。CUDA 9 以前的 `__shfl_down` 没有这一步，已经废弃。用协作组（4.8.5 节）时，同样的事情写成 `cg::reduce(warp, v, cg::plus<float>())`。

版本 4、5 应当接近显存带宽：归约是受带宽限制的运算，再快也快不过把数据读一遍。实际工作中不必自己写归约：CUB（CUDA 工具包自带的并行原语库）的 `cub::DeviceReduce` 针对每一代 GPU 调好了参数，Thrust 的 `thrust::reduce` 和 PyTorch 的 `sum` 在内部也调用类似的实现。自己写的意义在于两点：一是理解这些原语为什么快；二是把归约融合进别的核函数——softmax、层归一化里的归约都和逐元素运算写在同一个核函数里（第 8、9 章），这时只能自己写线程束级、线程块级的归约，版本 5 的 `warp_sum` 就是它们的基本构件。

最后的部分和也可以不用第二个核函数，而让每个线程块用一次 `atomicAdd` 加到全局的结果上。这样少一次启动，但浮点加法的顺序取决于线程块完成的先后，每次运行的结果在最后几位可能不同（3.1.6 节）。需要可复现的结果时，用固定顺序的两步法。

**工程师笔记**

- 线程束内的归约用洗牌（或 `cg::reduce`），线程块内用共享内存，线程块之间用第二次启动或原子操作。
- 先让每个线程顺序地处理许多元素，再做树形归约——这条原则（“算法级联”）对扫描、直方图同样适用。
- 求最大值、求最小值、求均值与方差都是归约，写法相同；求方差用韦尔福德（Welford）算法合并部分结果，比先求平方和再相减更准确。
- 现成的 `cub::DeviceReduce`、`cub::BlockReduce`、`cub::WarpReduce` 分别对应全局、线程块、线程束三级，优先使用。
