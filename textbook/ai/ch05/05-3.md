### 5.3.1 问题的提出

灰度化之后，检测程序要把所有暗像素的坐标收集成一个列表，交给后面的程序去拟合暗斑的轮廓。每个线程都知道自己的像素暗不暗，可是如果它是暗的，应该写到列表的第几个位置？答案是：它前面有几个暗像素，它就写到第几个。把“是否暗”记成 0 或 1，第 $i$ 个像素的写入位置就是前 $i$ 个数的和。

给定 $x_0, x_1, \dots, x_{n-1}$，**前缀和**（又称**扫描**）有两种：

$$
\text{包含式：}\ y_i = \sum_{j=0}^{i} x_j , \qquad \text{排他式：}\ y_i = \sum_{j=0}^{i-1} x_j\ \ (y_0 = 0) . \tag{5.3.1}
$$

上面的问题要的是排他式。像这样“每个元素各自产生 0 个或若干个输出，用前缀和算出写入位置，再把输出收集成紧凑的数组”的操作称为**流压缩**。前缀和是并行计算中用途最广的基本操作之一：基数排序、构造稀疏矩阵的行指针（5.6 节）、为不定长的输出分配空间，都靠它。

前缀和看起来每一项都依赖前一项，顺序算法 $y_i = y_{i-1} + x_i$ 只能一步一步地做。它能并行吗？可以，因为加法满足结合律（3.1 节习题 3.1.6）。

### 5.3.2 希利斯—斯蒂尔扫描

1986 年希利斯（W. D. Hillis）和斯蒂尔（G. L. Steele）在连接机上用了一种简单的办法：第 1 步每个位置加上左边相邻的数，第 2 步加上左边相隔 2 的数，第 3 步相隔 4……（同样的结构在电路设计中早已有之，即 1973 年的科格—斯通加法器。）第 $k$ 步之后，每个位置上是它左边（含自己）$2^k$ 个数的和，$\lceil\log_2 n\rceil$ 步完成（图 5.3.1(a)）。每一步中所有位置同时更新，用的都是上一步的值。

跨度只有 $\log_2 n$，但工作量是 $\sum_k (n - 2^k) = n\log_2 n - (n - 1)$ 次加法，比顺序算法多了 $\log_2 n$ 倍。

**算例 5.3.1** $n = 16$ 时，希利斯—斯蒂尔扫描 {{ex5_3.hs_steps16}} 步、{{ex5_3.hs_adds16}} 次加法，顺序算法只要 15 次。$n = 2^{20}$ 时它要 {{ex5_3.hs_adds_M:.1f}} 百万次加法，是顺序算法（{{ex5_3.seq_adds_M:.2f}} 百万次）的 {{ex5_3.hs_ratio:.0f}} 倍。处理器少于 $n$ 时，多出的工作量都要实打实地做完，这种算法称为不是**工作高效**的。

### 5.3.3 布莱洛赫扫描

工作高效的并行前缀算法早在 1980 年前后就有了（拉德纳—费舍尔 1980、布伦特—孔 1982）；1990 年布莱洛赫（G. Blelloch）把下面这种分两趟的扫描作为基本的并行原语系统地阐述，GPU 上的实现大多以它为蓝本（图 5.3.1(b)）：

- **上扫**：与归约的树一样，两两相加，建出一棵和树，第 $d$ 层（$d = 1, 2, 4, \dots$）做 $a_{k+2d-1} \mathrel{+}= a_{k+d-1}$。根上是全部的和。
- **下扫**：把根置零，从上往下，每个节点把自己的值交给左子，把“自己的值 + 左子原来的值”交给右子。到了叶子，每个位置上就是它左边所有数的和——排他前缀和。

两趟各 $n - 1$ 次加法，工作量 $2(n - 1)$，与顺序算法同一个量级；跨度 $2\log_2 n$。

**算例 5.3.2** $n = 16$ 时布莱洛赫扫描 {{ex5_3.bl_steps16}} 步、{{ex5_3.bl_adds16}} 次加法；$n = 2^{20}$ 时 {{ex5_3.bl_steps}} 步、{{ex5_3.bl_adds_M:.2f}} 百万次加法，约为顺序算法的 2 倍。

两种算法各有用处。处理器（线程）远少于数据时，工作量决定耗时，用布莱洛赫；处理器与数据一样多时，步数决定耗时，希利斯—斯蒂尔反而更快。一个线程束正是后一种情形：32 个线程本来就在，空着也是空着，所以线程束内的扫描都用希利斯—斯蒂尔，只要 5 步。

### 5.3.4 GPU 上的三段式扫描

线程块之间不能同步，长数组的扫描要分层做。程序 5.3.1 的做法分三段：

1. **块内扫描**：每个线程块扫描 1024 个数。线程束内用 `__shfl_up_sync` 做希利斯—斯蒂尔扫描（第 $d$ 步，lane $\ge d$ 的线程加上 lane $- d$ 的值）；32 个线程束各自的和写进共享内存，由 0 号线程束再扫描一次；每个线程加上它前面各线程束的和。块的总和另写到数组 `sums`。
2. **扫描各块的和**：对 `sums` 递归地做同样的扫描。$2^{24}$ 个数有 16 384 个块，块和再分成 16 块，最后只剩一块。
3. **加回**：每个线程块的每个数加上它前面各块的总和。

```cpp
__device__ unsigned warp_scan(unsigned v, int lane) {
    for (int d = 1; d < 32; d <<= 1) {
        unsigned t = __shfl_up_sync(0xffffffffu, v, d);   // 取 lane − d 号线程的值
        if (lane >= d) v += t;
    }
    return v;
}
```

三段式扫描是工作高效的，但它把数据读写了两遍：第一段读 $x$、写 $y$，第三段再读 $y$、写 $y$。前缀和受带宽限制，搬运量就是耗时。

**算例 5.3.3** $n = {{ex5_3.n_M:.0f}}$ M 个 32 位整数。三段式扫描搬运的字节约为输入的 {{ex5_3.three_phase:.1f}} 倍（各级块和只占约千分之一），而前缀和最少只需读一遍输入、写一遍输出，即 {{ex5_3.single_pass}} 倍。所以三段式扫描最多只能达到显存带宽的一半，耗时至少是下限 {{ex5_3.t_min_us:.0f}} μs 的两倍。

### 5.3.5 单遍扫描

能不能读一遍、写一遍就完成？难点在于第 $b$ 个线程块要知道前面所有块的总和，而前面的块可能还没算完。2016 年梅里尔（D. Merrill）和加兰（M. Garland）提出**退耦回看**：每个线程块先算出本块的和，立即把它连同一个状态标志写到全局内存（“只有本块的和”）；然后向前查看前面各块的状态，把它们的和一路加上去，直到遇到一个已经公布了“包含式前缀”（从第 0 块到它自己的总和）的块就停下；最后公布自己的包含式前缀，再完成本块的扫描写出结果。大多数块只需回看一两个邻居，等待的时间很短，整个扫描只读写一遍数据。它依赖一个条件：被回看的块一定已经开始执行，否则后面的块可能一直等下去。稳妥的做法是不按 `blockIdx` 分配数据，而用一个原子计数器按线程块实际开始执行的先后给它们编号。

### 5.3.6 流压缩

**算例 5.3.4** 回到本节开头的问题。测试图共 {{ex5_3.px_M:.1f}} 百万个像素，阈值 40 以下的暗像素有 {{ex5_3.dark}} 个。对标志数组求排他前缀和，每个暗像素就知道自己在列表中的位置；最后一个位置上的前缀和加上它自己的标志，就是列表的长度。列表的第一项是第 {{ex5_3.first_row}} 行第 {{ex5_3.first_col}} 列的像素——暗斑的最上沿（程序 5.3.2）。

流压缩在 GPU 上随处可见：目标检测中筛掉置信度低的候选框，图算法中收集下一层要访问的顶点，粒子模拟中删除飞出边界的粒子。CUB 提供现成的 `cub::DeviceSelect::If` 和 `cub::DeviceSelect::Flagged`；PyTorch 中 `x[mask]` 的背后也是一次前缀和。

**工程师笔记**

- 线程束内的扫描用 `__shfl_up_sync`（希利斯—斯蒂尔），线程块内两级，全局用 CUB 的单遍扫描。
- 排他前缀和 = 包含式前缀和 − 自身。流压缩、分配输出位置用排他式。
- 前缀和受带宽限制：衡量实现好坏的是有效带宽，目标是读一遍、写一遍。
- 浮点数的前缀和同样受舍入的影响，长数组的前缀和误差会逐项累积；需要高精度时用双精度或补偿求和。
