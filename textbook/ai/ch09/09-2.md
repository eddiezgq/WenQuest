### 9.2.1 问题的提出

6.4 节的数据并行，每块 GPU 存一份完整的模型，各算一份数据，反向后全归约梯度。它简单、通信也只在每步一次，但有一个根本的浪费：$p$ 块 GPU 上存着 $p$ 份一模一样的参数、梯度与优化器状态。7B 模型的模型状态约 108 GB（算例 9.1.3），数据并行时每块 GPU 都要这么多，再多的 GPU 也放不下。

### 9.2.2 零冗余优化器

拉杰班达里（S. Rajbhandari）等 2020 年提出的**零冗余优化器**（ZeRO）把这些冗余切掉。记参数个数为 $\Psi$、GPU 数为 $p$，分三级：

- **ZeRO-1** 切分优化器状态：每块 GPU 只保存 $1/p$ 参数的 AdamW 状态与主权重，只负责更新这一部分参数。梯度全归约改成归约—散播（每块只拿到自己那 $1/p$ 的梯度之和），更新完再全收集参数（6.4 节）。环形算法下，归约—散播加全收集的通信量与一次全归约相同。
- **ZeRO-2** 再切分梯度：反向时梯度一算出就归约—散播，每块 GPU 只留自己那份。
- **ZeRO-3** 再切分参数：每块 GPU 平时只存 $1/p$ 的参数；计算某一层之前，用全收集把这一层的完整参数临时凑齐，算完就丢掉。前向、反向各要全收集一次，通信量约为数据并行的 1.5 倍。

### 9.2.3 PyTorch 的 FSDP

PyTorch 的**完全分片数据并行**（FSDP）实现的就是 ZeRO-3。用法与 DDP（`DistributedDataParallel`）几乎一样，只是多了一个“按什么单位切”的选择：

```python
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP
from torch.distributed.fsdp.wrap import ModuleWrapPolicy
model = FSDP(model, auto_wrap_policy=ModuleWrapPolicy({Block}))   # 每个 Transformer 块一个单元
```

每个单元的参数被展平、切成 $p$ 份；前向进入一个单元时全收集它的参数，出来时释放；反向同理，并把梯度归约—散播。单元越小，同时完整存在的参数越少，但通信的次数越多、每次越小。把 `sharding_strategy` 设为 `SHARD_GRAD_OP` 就是 ZeRO-2；较新的 PyTorch 推荐改写后的接口 `fully_shard`（常称 FSDP2），按参数逐个切分，用法类似。程序以 `torchrun --nproc_per_node=8 train.py` 启动，每块 GPU 一个进程。

**工程师笔记**

- 模型状态放得下时用 DDP（最简单、最快，可设 `gradient_as_bucket_view=True` 省一份梯度的显存）；放不下时先试 ZeRO-1/2，再用 FSDP（ZeRO-3）。
- FSDP 按 Transformer 块包装；开启参数的预取，让全收集与计算重叠。
- 用 FSDP 保存检查点时，选“分片保存”，避免把整个模型收集到一块 GPU 上。
