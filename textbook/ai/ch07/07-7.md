### 7.7.1 问题的提出

前馈网络第一层的输出要加偏置、再过 GELU。PyTorch 的写法 `F.gelu(x + b)` 是两个运算、两个核函数：加法读 $X$ 写 $Z$，GELU 读 $Z$ 写 $Y$，中间结果 $Z$ 在显存里走了一个来回。7.2.5 节可以把它放进 cuBLASLt 的尾处理，但那要求自己调用 cuBLASLt；更一般的情况是，框架里根本没有我们要的那个运算——一种新的激活函数、一种特殊的归一化、一个机器人运动学里的专用计算。这时可以自己写一个 CUDA 核函数，接进 PyTorch，并且不丢掉自动微分。

把运算接进 PyTorch 有几条路：用现有运算组合（最简单，但每个运算一个核函数）；交给 `torch.compile` 自动融合（7.8 节）；用 Triton 写（第 8 章）；或者像本节这样，直接写 CUDA 核函数，用 C++ 扩展接进来。最后一种最灵活，也最费事，适合其他办法都达不到要求的时候。

### 7.7.2 核函数与 C++ 包装

一个**自定义算子**由三部分组成：CUDA 核函数，把 PyTorch 张量交给核函数的 C++ 函数，以及（要训练时）它的反向。程序 7.7.1 的前向核函数逐个元素计算 $y = \mathrm{GELU}(x + b)$，GELU 用 tanh 近似（与 2.9 节相同），用网格跨步循环（4.2.5 节）处理任意长度：

```cpp
template <typename T> __global__ void fwd_kernel(const T* x, const T* b, T* y, int64_t n, int64_t f) {
    for (int64_t i = blockIdx.x * (int64_t)blockDim.x + threadIdx.x; i < n; i += (int64_t)gridDim.x * blockDim.x) {
        T d;
        y[i] = gelu_parts(x[i] + b[i % f], &d);     // b 按最后一维广播
    }
}

torch::Tensor forward(torch::Tensor x, torch::Tensor b) {
    TORCH_CHECK(x.is_cuda() && x.is_contiguous(), "x 要在 GPU 上、连续存放");
    auto y = torch::empty_like(x);                  // 经缓存分配器（7.5.4 节）
    int64_t n = x.numel(), f = b.size(0);
    auto stream = at::cuda::getCurrentCUDAStream(); // 发在 PyTorch 当前的流上
    AT_DISPATCH_FLOATING_TYPES(x.scalar_type(), "bias_gelu_fwd", [&] {
        fwd_kernel<scalar_t><<<blocks(n), 256, 0, stream>>>(x.data_ptr<scalar_t>(), b.data_ptr<scalar_t>(),
                                                            y.data_ptr<scalar_t>(), n, f);
    });
    C10_CUDA_KERNEL_LAUNCH_CHECK();
    return y;
}
```

几个要点。`AT_DISPATCH_FLOATING_TYPES` 按张量的数据类型为单精度、双精度各生成一份核函数（双精度用来做梯度检查）。核函数必须发在 `getCurrentCUDAStream()` 上，否则与 PyTorch 其余的运算没有先后保证（6.1 节）。核函数直接读写张量的存储，所以要先检查它在 GPU 上、连续存放；不连续的输入可以先 `.contiguous()`。

编译有两种方式：正式的扩展包用 `setuptools` 与 `torch.utils.cpp_extension.CUDAExtension` 构建；做实验时用 `load_inline`，把 C++/CUDA 源程序写在字符串里，第一次导入时调用 nvcc 编译（约一分钟），以后用缓存。

### 7.7.3 接入自动微分

要让新算子能参与训练，用 `torch.autograd.Function` 告诉 PyTorch 它的反向：

```python
class BiasGelu(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x, b):
        ctx.save_for_backward(x, b)                 # 反向要用的张量
        return ext.forward(x, b)

    @staticmethod
    def backward(ctx, dy):
        x, b = ctx.saved_tensors
        dx = ext.backward(dy.contiguous(), x, b)    # dx = dy · GELU′(x + b)
        return dx, dx.sum(dim=tuple(range(dx.dim() - 1)))   # 对每个输入返回一个梯度；b 广播过，要求和
```

反向的核函数按 GELU 的导数（tanh 近似）

$$
\mathrm{GELU}'(t) = \tfrac12\left(1 + \tanh u\right) + \tfrac12\, t\left(1 - \tanh^2 u\right)\sqrt{2/\pi}\,\left(1 + 3a\, t^2\right) \tag{7.7.1}
$$

逐元素算出 $\partial x$，其中 $u = \sqrt{2/\pi}\,(t + a t^3)$，$a = {{ex7_7.a:.6f}}$ 是 tanh 近似中的常数。偏置 $b$ 在前向时沿前面各维广播（2.3.4 节），反向时它的梯度要把这些维加起来。

自己写的导数最容易出错，必须检验。`torch.autograd.gradcheck` 用数值差分逐个检查：把输入的每个元素加减一个很小的量，看输出的变化是否与我们的反向一致。它要在双精度、小张量上做（单精度的差分误差太大）。程序 7.7.3 先在 CPU 上核对了式 (7.7.1)：与中心差分的最大差 ${{ex7_7.dgelu_err:sci1}}$。

### 7.7.4 值不值得

**算例 7.7.1** 形状为 8192×1536 的单精度张量（{{ex7_7.MB:.0f}} MB）。前向：不融合要读写 4 遍（加法读 $X$ 写 $Z$，GELU 读 $Z$ 写 $Y$），A10 上至少 {{ex7_7.unf_f_us:.0f}} μs；融合只读 $X$、写 $Y$，至少 {{ex7_7.fus_f_us:.0f}} μs，快 {{ex7_7.speed_f:.0f}} 倍。反向：不融合时 GELU 的反向读 $\partial Y$ 与 $Z$、写 $\partial Z$，加法的反向对 $x$ 直接传递 $\partial Z$，偏置的梯度再读一遍 $\partial Z$ 求和；融合时读 $\partial Y$ 与 $X$、写 $\partial X$，求和同样再读一遍——两者都是 4 遍，至少 {{ex7_7.fus_b_us:.0f}} μs。前向加反向合计只快 {{ex7_7.speed_all:.2f}} 倍。两种写法为反向保存的都是一个同样大的张量（不融合存 $Z$，融合存 $X$），显存一样。

实测（程序 7.7.2，{{run7_7._gpu}}，PyTorch {{run7_7.torch}}）：

| | 前向（μs） | 前向加反向（μs） |
|---|---|---|
| 原生写法 `F.gelu(x + b)` | {{run7_7.native_f_us:.0f}} | {{run7_7.native_fb_us:.0f}} |
| 自定义融合算子 | {{run7_7.fused_f_us:.0f}} | {{run7_7.fused_fb_us:.0f}} |

融合算子的前向达到 {{run7_7.fused_f_GBs:.0f}} GB/s，比原生写法快 {{run7_7.speed_f:.1f}} 倍，前向加反向快 {{run7_7.speed_fb:.2f}} 倍。前向结果与原生写法的最大差 {{run7_7.fwd_err:.1e}}，$\partial x$ 的最大差 {{run7_7.dx_err:.1e}}，双精度的梯度检查通过；编译这个扩展用了 {{run7_7.build_s:.0f}} s。

这个例子说明了自定义算子的两面。融合省下的是显存往返，收益可以用算例 7.7.1 那样的流量账事先算出；而为了这点收益，要写两个核函数、一个 C++ 包装、一个反向，还要负责它在各种形状、数据类型、设备上的正确性。表中最后一行是 `torch.compile` 自动生成的融合核函数：若它与手写的相当，就不必手写。手写的价值在编译器做不到的地方——例如把偏置梯度的求和也并进反向的核函数，或者像 FlashAttention 那样改变算法本身。

还有一个工程上的细节：用 `autograd.Function` 接入的算子，`torch.compile` 会尝试追踪进它的内部，遇到 C++ 扩展的调用就会图中断（7.8 节）。PyTorch 2.4 起推荐用 `torch.library.custom_op` 把它登记成一个正式的算子，并提供一个只推算输出形状的“假实现”，编译器就能把它当作一个整体放进图里。

**工程师笔记**

- 写自定义算子前先算流量账：省下几遍显存读写，值不值得一个核函数、一个反向和它们的维护。
- 先试 `torch.compile`，再试 Triton（第 8 章），最后才手写 CUDA。
- 核函数发在 `at::cuda::getCurrentCUDAStream()` 上；输入先检查设备、连续性与数据类型。
- 反向一定要用 `gradcheck` 在双精度的小张量上检验；广播过的输入，梯度要沿广播的维求和。
- 要与 `torch.compile` 配合，用 `torch.library.custom_op` 登记，并给出假实现。
