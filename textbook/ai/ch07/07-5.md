### 7.5.1 问题的提出

在 PyTorch 里写 `y = x @ w`，从按下回车到 GPU 上的矩阵乘法核函数开始执行，中间经过了哪些环节？每个环节要花多少时间？算例 6.2.2 说过，逐词生成时 PyTorch 每个运算在 Python 与框架中要花 10 μs 以上，GPU 大部分时间在等主机。这些时间花在哪里，显存又是怎样分配和回收的？本节打开 PyTorch 看一看。

### 7.5.2 一次调用的旅程

PyTorch 默认的执行方式称为**急切执行**：Python 每执行到一个运算，就立即把它发给 GPU，而不是先攒成一张图（2.5 节的动态图）。设 `x`、`w` 都在 GPU 上、都要记录梯度，`y = x @ w` 依次经过（图 7.5.1、动画 7.5.1）：

1. **Python 绑定**：`Tensor.__matmul__` 是一个 C++ 函数的 Python 包装，参数从 Python 对象转成 C++ 的张量。
2. **分派器**：PyTorch 的每个算子（`aten::matmul`、`aten::mm`……）都可以有多个实现，分别登记在不同的**分派键**下：`Autograd`（自动微分）、`AutocastCUDA`（自动混合精度，第 8 章）、`CUDA`、`CPU`，等等。分派器根据参与运算的张量带有哪些键（在 GPU 上、要梯度……）以及当前的设置，按固定的优先次序找出该调用的实现。
3. **组合算子先分解**：`aten::matmul` 本身没有 CUDA 实现，它是由更基本的算子组合成的：按两个输入的维数整理形状，二维时调用 `aten::mm`，更高维时调用 `aten::bmm`。这种组合算子在自动微分之前就被分解，后面各层看到的是 `mm`。
4. **自动微分这一层**：要记录梯度时，`mm` 先到 `Autograd` 键下的实现：它在计算图上添一个节点（`MmBackward0`），记住反向要用的 `x` 与 `w`（7.6 节），然后“降一级”再分派一次，到 `CUDA` 键下 ATen 中 `mm` 的 CUDA 实现。ATen（A Tensor library）是 PyTorch 的算子库，上千个算子各有 CPU、CUDA 等实现。
5. **ATen 的 CUDA 实现**：向缓存分配器（7.5.4 节）要一块显存放结果，检查各个张量的步长（需要时复制成连续的），调用 cuBLAS。
6. **cuBLAS**：按形状、数据类型挑选一个核函数（7.2 节），调用 CUDA 运行时发出启动。
7. **驱动**：把启动命令写进当前流的队列，立即返回。

到这里，主机上的工作就完成了（共几到十几微秒，7.5.5 节实测），Python 得到了结果张量 `y`，接着执行下一行；而 GPU 稍后才从队列里取出命令执行。这就是异步：`y` 在 Python 看来已经存在，里面的数却可能还没有算出来。只有当程序需要它的值时（`y.item()`、`print(y)`、复制回主机），才会等 GPU 算完（6.2 节）。

分派器是 PyTorch 可扩展性的关键。自动混合精度、`torch.compile` 的追踪（7.8 节）、性能分析器的记录、在“元设备”上只推算形状而不真正计算，都是在分派器中插入一层实现做到的；7.7 节的自定义算子也是向它登记新的实现。

### 7.5.3 张量与视图

回顾 2.3.3 节：一个张量由一块存储和描述怎样读它的形状、步长、起点组成；转置、切片、改形状只要可能，就只产生共用同一块存储的视图（图 7.5.2(a)）。程序 7.5.1 用几行 Python 写了一个最小的张量类，与 NumPy 逐元素核对：形状 (2, 3, 4) 的张量转置后两维，步长变为 {{ex7_5.xt_stride}}，存储不变，但不再连续。

::: 图 7.5.2
src: fig7_5_2
说明: （a）视图只改形状、步长与起点，与原张量共用存储；（b）缓存分配器：向驱动要来的一段显存被切成块分给张量，释放后留在池里反复使用

视图在 GPU 上有两个后果。其一，很多核函数要求输入连续（或至少最后一维连续），不连续的输入要先复制一份——算例 7.1.1 中的“转置复制”就是这样来的（7.2.4 节）。其二，原地修改一个视图，会改到共用存储的其他张量；自动微分为此给每块存储记一个版本号，反向时发现保存的张量被改过，就报错，而不是悄悄算错。

### 7.5.4 显存缓存分配器

`cudaMalloc` 与 `cudaFree` 很慢（要进驱动，常常还要同步整个设备），而训练中每一步都要分配、释放成百上千个张量。PyTorch 的办法是**缓存分配器**：显存一旦向驱动要来，就不再还回去，张量释放后，它的块留在池里，下一次同样大小的请求直接取用。PyTorch 2.x 的主要规则（简化）是：

- 请求的大小向上取整到 512 字节的倍数；不超过 1 MB 的走“小块池”，更大的走“大块池”；
- 池里有够用的空闲块，取其中最小的一块，多余的部分切下来留在池里；
- 没有才向驱动要一整段：小块池每次要 2 MB；大块池中不到 10 MB 的请求每次要 20 MB，更大的按 2 MB 向上取整；
- 释放的块与同一段中相邻的空闲块合并；完全空闲的段平时不还给驱动，只在调用 `torch.cuda.empty_cache()` 时，或 `cudaMalloc` 失败、分配器先释放缓存再重试一次时，才还回去。

块还与流相关联：一个块只在分配它的流上复用，跨流使用张量时要用 `Tensor.record_stream` 告诉分配器，否则可能在另一个流还没用完时就被重新分出去。

**算例 7.5.1** 按上面的规则模拟小型 Transformer 的训练（$B = 32$，$T = 256$，单精度）：前向依次分配各层为反向保存的张量，反向逐层释放，每层另有一块临时的梯度（每步共 {{ex7_5.reqs}} 次请求）。第一步调用 `cudaMalloc` {{ex7_5.mallocs_1}} 次，第二、三步各 {{ex7_5.mallocs_2}} 次、{{ex7_5.mallocs_3}} 次——以后每一步都从缓存里取。已分配显存的峰值 {{ex7_5.peak_MB:.0f}} MB，分配器保留了 {{ex7_5.reserved_MB:.0f}} MB。

所以看显存要分清两个数：`torch.cuda.memory_allocated()` 是张量实际占用的，`torch.cuda.memory_reserved()` 是分配器向驱动要来、留在手里的；`nvidia-smi` 看到的是后者再加上 CUDA 上下文本身（几百 MB）。两者之差是缓存的空闲块。请求的大小参差不齐时，大块切成小块后可能凑不出一块够大的连续空间，出现“显存还剩不少、却分配失败”的碎片现象；设置环境变量 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`，分配器改用可以扩展的段（基于 CUDA 的虚拟内存管理接口），能明显减少碎片。

- 对一个只有 1 个数的张量连续做 20 000 次加法：不记录梯度时，主机上每次调用 {{run7_5.host_ng_us:.1f}} μs，GPU 上平均每次 {{run7_5.gpu_ng_us:.1f}} μs；要记录梯度时（多经过自动微分一层，建图节点），主机上 {{run7_5.host_g_us:.1f}} μs；用 `torch.add(x, 1, out=y)` 免去分配输出，主机上 {{run7_5.host_out_us:.1f}} μs。对照程序 6.2.1：直接用 CUDA 发出一次启动，主机上只要 {{run6_2.enqueue_us:.1f}} μs。核函数本身只有一两微秒，GPU 上的平均时间与主机上的调用时间相当，说明 GPU 在等主机。
- 64 MB 的张量：清空缓存后第一次分配要 {{run7_5.first_us:.0f}} μs（调用 `cudaMalloc`），以后从缓存中取只要 {{run7_5.cached_us:.1f}} μs。
- 小型 Transformer 连续三个训练步：分配器调用 `cudaMalloc` 第一步 {{run7_5.segs_1}} 次，第二步 {{run7_5.segs_2}} 次，第三步 {{run7_5.segs_3}} 次；每步分配张量约 {{run7_5.allocs_2}} 次。已分配的峰值 {{run7_5.peak_MB:.0f}} MB，保留 {{run7_5.reserved_MB:.0f}} MB。实测的请求次数比算例 7.5.1 多得多，因为模拟只计了为反向保存的张量，没有计中间结果、梯度与优化器的临时张量；但“第一步之后几乎不再调用 `cudaMalloc`”这一点应当一致。

由此可以理解 PyTorch 适合什么、不适合什么：每个运算都有几微秒到十几微秒的固定开销，运算本身越大，这个开销越不要紧；全是小运算的程序（小批量推理、逐词生成、很小的模型），时间就耗在框架里。办法是 6.2 节的 CUDA 图和 7.8 节的图编译。

**工程师笔记**

- PyTorch 的调用是异步的：用主机的时钟计时之前先 `torch.cuda.synchronize()`，或用 CUDA 事件。
- 看显存分清“已分配”和“已保留”；`torch.cuda.memory_summary()` 给出分配器的详细统计，`torch.cuda.memory._record_memory_history()` 能记下每次分配的调用栈。
- 显存碎片导致分配失败时，先试 `expandable_segments:True`。
- 跨流使用张量时调用 `record_stream`，或在使用后同步。
- 小运算多时，固定开销占主导：减少运算个数（融合、批处理），或交给 CUDA 图、`torch.compile`。
