### 7.4.1 问题的提出

cuBLAS 快，但它是一个封闭的库：只能做它提供的那些运算，尾处理只有固定的几种。实际中常常需要“矩阵乘法再加一点别的”：注意力里两次矩阵乘法中间夹一个 softmax（FlashAttention，第 9 章），量化模型里一边乘一边把 INT4 的权重解压（第 8 章），矩阵乘法之后接一个特殊的归一化……为每一种都从头写到 cuBLAS 的水平，几乎不可能。NVIDIA 的回答是 CUTLASS（2017 年开源）：把高性能矩阵乘法拆成一组可以拼装的 C++ 模板，用户换掉其中一块，其余的优化原样保留。

### 7.4.2 分块的层次

CUTLASS 的矩阵乘法与第 5 章的做法一脉相承，只是把每一层都做成了可配置的（图 7.4.1）：

- **线程块分块**：一个线程块负责 $C$ 的一块（如 128×128），沿 $K$ 每步取 $A$、$B$ 各一条（如宽 32）放进共享内存（5.8 节）；
- **线程束分块**：线程块里的几个线程束各负责这一块中的一小块（如 64×64），数据从共享内存读进寄存器（5.9 节）；
- **指令分块**：线程束的一小块再分成张量核心一条指令能算的大小（如 Ampere 的 mma.m16n8k16），结果分散在 32 个线程的寄存器里（5.10 节）；
- **流水线**：共享内存里同时放几步的数据，算这一步时，下一两步的数据已经在路上（5.9 节的双缓冲推广到多级，Ampere 用 `cp.async`，Hopper 用 TMA）；
- **尾处理**：累加完成后，对寄存器里的结果做逐元素运算再写回（与 cuBLASLt 的尾处理相同，但可以是用户写的任意运算）。

**算例 7.4.1** 一个典型的半精度配置：线程块分块 128×128×32，线程束分块 64×64，指令 m16n8k16，3 级流水线。线程块有 {{ex7_4.warps}} 个线程束（{{ex7_4.threads}} 个线程）；每个线程束沿 $K$ 每步发 {{ex7_4.mma_per_k}} 条张量核心指令；每个线程要 {{ex7_4.acc}} 个寄存器放累加和；共享内存 {{ex7_4.smem_KB:.0f}} KB。线程块这一级每步做 $2\times128\times128\times32$ 次运算、从显存读 $(128 + 128)\times32\times2$ 字节，计算强度 {{ex7_4.intensity:.0f}} FLOP/B，低于 A10 半精度张量核心的屋脊（{{ex7_4.ridge:.0f}} FLOP/B，3.8 节）——要靠相邻线程块在 L2 中复用 $A$、$B$ 的数据（5.11 节），或者更大的分块，才能被算力而不是带宽限制。

这些参数都是模板参数。CUTLASS 2.x 中，上面的配置写成：

```cpp
using Gemm = cutlass::gemm::device::Gemm<
    cutlass::half_t, cutlass::layout::RowMajor,          // A
    cutlass::half_t, cutlass::layout::RowMajor,          // B
    cutlass::half_t, cutlass::layout::RowMajor,          // C
    float,                                               // 累加用单精度
    cutlass::arch::OpClassTensorOp, cutlass::arch::Sm80,
    cutlass::gemm::GemmShape<128, 128, 32>,              // 线程块分块
    cutlass::gemm::GemmShape<64, 64, 32>,                // 线程束分块
    cutlass::gemm::GemmShape<16, 8, 16>,                 // 指令
    cutlass::epilogue::thread::LinearCombination<cutlass::half_t, 8, float, float>,   // 尾处理：αAB + βC
    cutlass::gemm::threadblock::GemmIdentityThreadblockSwizzle<>, 3>;                // 3 级流水线
```

编译器在编译时把这些参数代进去，生成一个专门的核函数，没有运行时的分支开销。代价是编译慢：一个配置要编译几十秒到几分钟，占几 GB 内存；要试很多配置时，常用 CUTLASS 自带的“分析器”批量生成并实测。本书不对 CUTLASS 做实测（细则中的偏差说明）：调好的 CUTLASS 核函数与 cuBLAS 在同一量级（cuBLAS 内部的许多核函数也是同样的写法），第 5 章已实测过 cuBLAS（表 5.11.1）。

CUTLASS 3.x（2023 年起，面向 Hopper 及以后）把线程块与线程束两级重新组织成“集合”（collective）一级，以适应 Hopper 的线程束组指令 wgmma 与 TMA；CUTLASS 4（2025 年）又加入了用 Python 写这些核函数的方式。不变的是下面要讲的布局。

### 7.4.3 CuTe：布局

分块的每一层都在回答同一类问题：第几个线程、第几个寄存器，对应矩阵的哪一个元素？这个元素在共享内存或显存中的哪个位置？第 5 章是用一个个手写的下标公式回答的，例如 `Bs[k][tcol*8 + j]`。下标公式容易写错，换一种分块又要重写。CuTe（CUTLASS 3 的核心部分）把这类对应关系统一抽象成**布局**：一个形状加一个步长，

$$
L = S : D , \qquad L(c_0, c_1, \dots) = \sum_i c_i\, d_i , \tag{7.4.1}
$$

把坐标映射成位置。形状和步长都可以嵌套，一个整数坐标按“第一维变得最快”展开成多维坐标。例如：

- `(4, 8) : (1, 4)` 是 4×8 的列主序矩阵，`(4, 8) : (8, 1)` 是行主序；
- `((4, 2), (4, 2)) : ((1, 16), (4, 32))` 是 8×8 的矩阵按 4×4 分块存放，块内列主序，块也按列主序排列：行坐标拆成“块内第几行、第几块行”，列坐标同理；
- 第 5 章 `regtile` 的“线程 → 它算的元素”：坐标 $((i, t_y), (j, t_x))$，形状 `((8, 16), (8, 16))`，在行主序的 128×128 输出块里步长为 `((128, 1024), (1, 8))`；`vec` 只是把列拆成 `(4, 2, 16)`、步长改为 `(1, 64, 4)`，行同理——从 `regtile` 到 `vec`，下标公式要整个重写，布局只改了几个数。

在布局之上，CuTe 定义了一套“布局代数”：两个布局可以复合（先用一个，再用另一个）、相乘（把一个布局重复铺开）、相除（把一个布局切成若干块）。按线程块切矩阵、按线程束切线程块、把一条指令的片段（图 7.4.1(c)）对应到矩阵上，都是这几种运算的组合。写核函数的人只描述“怎样切”，下标由库算出，编译时就化成常数。

**工程师笔记**

- 需要“矩阵乘法 + 一点别的”时，先看 cuBLASLt 的尾处理与 cuDNN 的运算图；不够再用 CUTLASS，它的尾处理可以是任意运算。
- CUTLASS 的配置要实测挑选：同一个形状，不同的分块、流水线级数，速度可以差一倍；用它的分析器批量试。
- 编译 CUTLASS 的核函数很慢、占内存多：只编译目标架构（如 `-arch=sm_80`），并控制同时编译的个数。
