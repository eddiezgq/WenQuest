### 7.8.1 问题的提出

前几节看到了急切执行的两个代价。其一，每个运算单独一个核函数，相邻的逐元素运算各自读写一遍显存（算例 7.1.1、7.7.1）；其二，每个运算都有几到十几微秒的固定开销，小运算多时 GPU 等主机（7.5.5 节）。手工融合（7.7 节）能解决前者，但不可能为每种组合都写一个核函数。2.5 节说过，静态图便于全局优化，动态图便于编程。`torch.compile`（2023 年随 PyTorch 2.0 发布）想兼得两者：用户照常写 Python，编译器在运行时把其中的张量运算捕获成图，再为整张图生成融合的核函数。

```python
model = torch.compile(model)          # 默认模式；也可以 mode="reduce-overhead" 或 "max-autotune"
loss = loss_fn(model(x), y)           # 第一次调用时编译，以后直接运行编译好的代码
loss.backward()
```

### 7.8.2 TorchDynamo：捕获图

Python 执行一个函数，实际是在解释执行它的字节码。TorchDynamo 利用 Python 提供的接口（PEP 523），在函数的字节码执行之前截住它，自己“模拟执行”一遍：遇到张量运算，就记进一张 FX 图（PyTorch 中表示计算图的数据结构）；遇到普通的 Python 代码（循环、条件、调用别的函数），就在编译时把它展开。最后得到的图只含张量运算，Python 的那部分已经消失了。

捕获时依赖了一些条件：输入张量的形状、数据类型、所在设备，某个 Python 变量的值……TorchDynamo 把它们记成**守卫**。以后每次调用，先检查守卫：都满足，直接运行编译好的代码；有不满足的（例如批大小变了），就重新编译一份。默认情况下，某一维的长度第一次变化时，TorchDynamo 会把这一维改为“动态”的重新编译，以后它再变就不用重编。

遇到处理不了的代码，TorchDynamo 就**图中断**：把已经捕获的部分编译成一张图，这段代码照常交给 Python 执行，之后再开始一张新图。常见的原因有：把张量的值取回主机（`loss.item()`、`print(tensor)`）、依赖张量取值的分支（`if x.sum() > 0:`）、调用它不认识的 C/C++ 扩展（7.7 节）。图中断不影响结果，但每断一次，就少了一次跨越断点的融合，多了一次在 Python 中的往返。用 `TORCH_LOGS="graph_breaks,recompiles"` 运行，可以看到在哪里断了、为什么重编。

### 7.8.3 AOTAutograd：事先追踪反向

TorchDynamo 只捕获前向。训练还需要反向。AOTAutograd（ahead-of-time autograd）用“假张量”（只有形状、类型，没有数据）把前向图执行一遍，同时让自动微分把反向也追踪出来，得到一张前向与反向连在一起的联合图；高层的算子在这里被分解成两百多个基本的 ATen 算子，便于后面统一处理。

然后它把联合图切成前向图和反向图，决定前向的哪些中间结果要保存给反向、哪些在反向时重新算出来。这正是 7.6.4 节的激活重计算，只是由编译器自动权衡：一个中间结果若可以由已保存的张量经几个便宜的逐元素运算得到（例如 GELU 的输出可以由它的输入重算），重算它比保存它划算——反正这些运算会被融合进反向的核函数里，几乎不多花时间，却省了显存和一次读写。AOTAutograd 用图上的最小割来做这个选择。

### 7.8.4 TorchInductor：融合与生成核函数

TorchInductor 是默认的后端编译器。它把图中的运算分成两类：矩阵乘法、卷积这类，交给 cuBLAS、cuDNN（或在 `max-autotune` 模式下试几种用 Triton 写的模板，挑最快的）；其余的逐元素运算与归约，按数据依赖分组融合，每组生成一个 Triton 核函数（第 8 章讲 Triton）。融合的规则大致是：形状能对上的相邻逐元素运算合成一个；逐元素运算可以并进它前后的归约（如残差加法并进紧接着的层归一化）；能并进来的都不再单独写回显存。

**算例 7.8.1** 按这种规则粗略估计小型 Transformer 的一次前向（$B = 32$，$T = 256$，单精度，只计 6 层，不计输出层与损失）：每层矩阵乘法之外的运算由 {{ex7_8.k_eager}} 个核函数减为 {{ex7_8.k_fused}} 个，显存流量由 {{ex7_8.MB_eager:.0f}} MB 减为 {{ex7_8.MB_fused:.0f}} MB；加上矩阵乘法（按单精度峰值），前向的最短时间由 {{ex7_8.t_eager_us:.0f}} μs 降到 {{ex7_8.t_fused_us:.0f}} μs，快 {{ex7_8.speedup:.2f}} 倍。融合省不掉的是转置复制、注意力权重 $P$ 的读写（$B\times h\times T\times T$ 个数）和 GELU 的输入输出：前两者要等第 9 章的 FlashAttention 把注意力整个融合，GELU 要并进矩阵乘法的尾处理（7.2.5 节）才省得掉。

此外有三种模式：默认模式只做上面的融合；`mode="reduce-overhead"` 再用 CUDA 图（6.2.3 节）提交整张图，消除逐个启动的开销，适合小批量推理；`mode="max-autotune"` 为矩阵乘法等实测挑选最快的实现，并且同样使用 CUDA 图（不要 CUDA 图时用 `"max-autotune-no-cudagraphs"`），编译要慢得多。

### 7.8.6 什么时候用

`torch.compile` 最适合形状固定、反复运行的模型：训练循环、固定批大小的推理服务。它不擅长的是：形状每次都变（反复重编译），代码中有很多图中断（每段图都太短），或者只运行几次（编译时间收不回来）。编译出了问题，可以逐级排查：`backend="eager"` 只做捕获、不编译，`backend="aot_eager"` 再加上 AOTAutograd，确定是哪一级的问题；用 `TORCH_LOGS="output_code"` 可以看到 Inductor 生成的 Triton 源程序——读它是学习融合核函数写法的好材料（第 8 章）。

**工程师笔记**

- 先用急切执行把模型调对，再 `torch.compile`；编译前后在同一批数据上核对损失与梯度。
- 训练循环里避免 `loss.item()`、`print(tensor)` 等图中断；要记录损失，每隔若干步取一次。
- 形状会变的维度，提前用 `torch._dynamo.mark_dynamic` 标出，减少重编译。
- 小批量推理用 `mode="reduce-overhead"`；对矩阵乘法的速度不满意时试 `max-autotune`，但编译慢得多。
- 自定义的 CUDA 算子用 `torch.library.custom_op` 登记，以免图中断（7.7.4 节）。
