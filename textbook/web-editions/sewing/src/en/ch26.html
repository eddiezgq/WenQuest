This is an optional chapter (★). Readers need the hanger system of Chapter 12 and the control material of Chapters 13–18; Chapters 28 and 29 use the metrics introduced here.

The electronically controlled sewing machines of Chapters 13 to 18 already know a great deal: when the main shaft turns and how fast, how many stitches went into a seam, how many times the thread was trimmed, whether the thread broke, and which faults were raised. Yet these numbers have always stayed locked inside each machine. If the floor manager wants to know how many pieces an operation produced today, or which machine stopped most often, the answer still depends on line supervisors keeping notebooks and operators handing in work tickets every day. This chapter shows how to get the data out and turn it into metrics the shop floor can read: what to collect, how to transmit it, how much to send and what to calculate. It then describes how the data connect to the shop-floor management system and the hanger system, how to build a real-time “digital twin” of the sewing floor, and how to handle remote service and security.

26.1 Opening: the “black box” of a sewing line

On a thirty-operator shirt line that is not networked, all management can see is how many pieces leave the line each day and how many work tickets each operator hands in. When one operation becomes a bottleneck, nobody notices until the supervisor walks the line; nobody knows that a certain machine broke its thread a dozen times that morning; and nobody can say how much of an eight-hour day the sewing machines actually spend running. To management the line is a black box: they know how much fabric goes in and how many garments come out.

Once the line is connected, the state and counts of every sewing machine reach the floor server in real time. A dashboard shows whether each machine is sewing, waiting for work or stopped at this moment, how many pieces each operation has completed and how far it is from target, and why each stoppage happened. In a sewing-machinery case published by the Alliance of Industrial Internet (AII), the platform collects sewing time, stitch counts, trim counts and similar data in real time and supports remote parameter setting and fault alerts; on the strength of these data the equipment maker even introduced a pay-per-use leasing model (Alliance of Industrial Internet case study (in Chinese)).

As a worked example, this chapter uses one shift of a single lockstitch machine (shift 480 min, breaks 30 min, standard minute value 0.6 min/piece; all parameters are illustrative values) and works out how much data it generates and what those data can tell us.

26.2 What data a sewing machine can provide

What the controller already knows　To do its own job, the controller of an electronically controlled sewing machine already keeps track of many quantities (bottom layer of Fig. 26-1): main-shaft start/stop and speed (the servo of Chapter 13); stitch count (the encoder counts one stitch per revolution); the number of trimming, backtack and presser-foot-lift actions (the solenoids of Chapter 14); thread breaks (on models with thread-break detection, Chapter 16); fault codes (Chapter 18); and parameters such as stitch length and maximum speed. None of these needs an extra sensor — only a communication port on the control box.

What has to be added　The controller does not know who is sewing or which piece is being sewn. If the operator taps an ID card on a reader next to the machine at the start of the shift, the machine knows the operator. Which order, which operation and which piece is being sewn must come from the barcode on the work ticket or the number on the hanger carrier (Chapter 12: a barcode or RFID tag is read as the hanger passes a reader). Only by matching these two kinds of information with the controller’s data can we work out “who did which operation on which piece, and when”.

Ways of collecting the data　There are three common approaches: the control box has a communication port (serial or fieldbus) to which a network module is connected, sending the data out over Wi-Fi or a wired network; the control box has networking built in; or a group of machines is connected to a gateway that converts protocols, aggregates the data and uploads them. Old machines without a communication port can be fitted with a current transformer on the power lead, so that the current shows whether the main shaft is turning; but this only gives run/stop, not stitch or trim counts.

Device data model　A single sewing floor often has machines from several manufacturers and of several generations, so their data must first be brought into one common structure before downstream systems can handle them uniformly. A machine’s data fall roughly into four classes. Identification: machine number, model, manufacturer, serial number, firmware version, line and workstation; these rarely change. State: whether the machine is at this moment running, idle, stopped or in fault. Counters: cumulative, never-decreasing quantities such as stitch count, trim count, piece count and running time. Reporting the cumulative value is more reliable than reporting increments: a lost message is made good by the next one, and a duplicate does no harm. The receiver must also recognise a counter reset (power-down restart, controller replacement, counter overflow) and continue the series after it. Events: things that happen at a particular moment — start sewing, stop, trim, thread break, alarm, operator change.

The states can be defined following OPC UA for Machinery (OPC 40001-1), the generic OPC UA companion specification for machinery. It divides a machine’s overall state into four: not available (switched off or in energy-saving mode), out of service (in fault or blocked, unable to work), not executing (available, waiting for an external start) and executing (OPC UA for Machinery state model). The states “running, idle, fault, off” commonly used for sewing machines map neatly onto these four: running → executing, idle → not executing, fault → out of service, off → not available. Using the extensions the specification allows, “executing” can be further split into “main shaft turning” and “operator handling the fabric”; as we shall see, the time spent in these two differs greatly.

26.3 Communication: MQTT and OPC UA

MQTT: publish and subscribe　One of the most widely used protocols for connecting shop-floor equipment is MQTT (OASIS MQTT 5.0 standard). It works like a post office: each machine “publishes” its messages to a topic, for example “shirt factory / sewing floor / line 3 station 7 / state”, without caring who receives them; dashboards, the shop-floor management system and databases each “subscribe” to the topics they are interested in, and a message server in the middle (the broker) forwards the messages (Fig. 26-3, left). Machines and applications do not know about each other, so adding a dashboard or swapping a database requires no change on the machine side. MQTT message headers are very small, so it runs well over wireless networks and on small network modules.

Several of its features are very useful on the shop floor. Quality of service (QoS) has three levels: level 0 delivers at most once and may lose messages; level 1 delivers at least once and may duplicate; level 2 delivers exactly once and has the highest overhead. Counters and events normally use level 1, and the receiver removes duplicates using a unique ID carried in the message content (the packet identifier in the MQTT packet itself is reused and cannot be used for de-duplication). Retained messages: for a message published with the retain flag, the broker keeps only the latest one per topic, so a dashboard that has just been opened receives the current state of every machine as soon as it connects, without waiting for the next change. Last-will messages: when a machine connects it leaves a “I have gone offline” message with the broker in advance; if the network fails or the machine loses power, the broker publishes it on the machine’s behalf after the keep-alive times out (typically a few tens of seconds). If the will is also retained and published to the state topic, the machine shows as “offline” on the dashboard instead of showing its last state indefinitely. A normal disconnect does not trigger the will, so the machine must first publish an offline state itself. Subscriptions may use wildcards: + matches one level, # matches all remaining levels and may only appear at the end; a dashboard subscribing to wq/shirt/sewing/+/status receives the state of every machine on the floor.

Unified namespace　How topics are named determines how easy the data are to find. One approach is to name them along the ISA-95 enterprise hierarchy — site, area, line, workstation, machine, level by level — with every system publishing and subscribing on this single topic tree; this is called a unified namespace. It is more than a naming scheme: it also means that every system publishes its current state to the same broker, which becomes the plant’s single real-time source of data, instead of systems being connected to one another pair by pair. The WenQuest Digital Factory that accompanies this book works this way. Topics take the form wq/site/area/unit/category, where the category is state, event, command and so on; every message is JSON in a uniform format, whose outer “envelope” carries the version number, message ID, time (UTC), message type, source, teaching or production mode and the associated work-order number, while the business content goes into data; numeric values are in SI units, with the unit stated in the field name. Carried over to the sewing floor, the unit l03-07 combines line and workstation, so the state topic of line 3, station 7 is wq/shirt/sewing/l03-07/status (Fig. 26-3, right). The digital-factory specification defines three categories — state, event and command — and the state values running, idle, setup, stopped and fault; following the specification’s “add, never change” rule, this chapter adds a counter category and an offline state for sewing machines. Simulated and real sewing machines send messages in exactly the same format, differing only in the source field, so dashboards and databases cannot tell — and need not tell — which is which.

OPC UA: data that come with a manual　Another widely used industrial communication standard is OPC UA. It transmits not just values but also “what this number is”: each data point hangs on an information model and carries its name, unit, type and the machine and component it belongs to, and a client that connects to the server can browse the whole model. Industries build companion specifications on top of it that standardise the model of a given class of equipment. For textiles there is already a companion specification for textile testing instruments; sewing machines do not yet have a dedicated one, so for now the generic Machinery model described above can be used to describe identification and state.

Dividing the work　The two are not mutually exclusive. A common division is this: from machines to gateway and from gateway to platform, where data volumes are large, devices numerous and network conditions poor, MQTT or the equipment maker’s own protocol is usually used; for high-end equipment whose data other systems need to browse and whose parameters they need to read and write, or between systems (for example between the shop-floor management system and an automated line), OPC UA or web APIs are used. For equipment like sewing machines — numerous, inexpensive and with simple data — MQTT plus uniform topics and message formats is often all that is needed.

26.4 Reporting strategy and data volume

How much data one machine produces per shift　In this chapter’s worked example, the lockstitch machine sews about 569 pieces in one shift, its main shaft turns for about 120 min, it makes about 360,000 stitches and trims about 1,750 times. If every stitch were reported as a message, one machine would send 360,000 messages per shift; one message for every press and release of the pedal and every trim gives about 8,600; one summary message per completed piece, about 600; one summary per minute, about 480.

Multiplied across the floor　For a floor of 500 sewing machines working two shifts a day and 300 working days a year, at 250 bytes per message (JSON in the uniform envelope; illustrative value), the difference between these approaches is stark (Fig. 26-4). Reporting every stitch gives an average of more than 6,000 messages per second and about 27 TB of storage per year, nearly all of which nobody will ever look at. Reporting every pedal start/stop and trim gives about 150 messages per second and about 650 GB per year; a summary per piece, about 10 per second and 45 GB per year; a summary per minute, about 8 per second and 36 GB per year. Conversely, summarising only every 10 minutes to keep things simple gives less than 1 message per second, but a stoppage then appears on the dashboard only 10 minutes later, which defeats the purpose of real-time monitoring.

Aggregate at the edge, report events at once　The sensible approach walks on two legs: counter data are first aggregated on the machine or the gateway, and the cumulative value is reported once per piece or once per minute; state changes (stoppage begins, running resumes, thread break, fault) are reported individually and immediately when they occur. This chapter’s illustrative criteria are an average message rate of no more than 500 per second, annual storage of no more than 100 GB, a stoppage shown within 5 s and piece counts updated within 1 min; both “per-piece summary” and “per-minute summary”, combined with immediate state-change reports, meet them. Detailed data such as stitch counts and speed curves can stay on the machine or gateway and be retrieved when a particular machine’s problem needs analysing. Peak message rates can be several times the average (for example when all machines start together at a shift change), so the broker and database must be sized with headroom for the peak.

26.5 From data to metrics

Piece count　What the shop floor cares about most is the piece count. The simplest method is to count trims: each piece is sewn in a few seams, each ending with a trim, so the number of trims divided by the number of seams per piece gives the piece count. Work tickets and hanger carriers are two other methods: scan a work ticket once per bundle of cut parts, or read the carrier number each time a hanger passes the workstation. Each of the three methods has its own sources of error, analysed in the case below.

Sewing-time ratio　The fraction of planned time during which the main shaft actually turns is the number most easily obtained once sewing machines are networked — and the one most easily misread. In the worked example the operator works at 85% of the standard minute value, yet the main shaft turns for only about 27% of the planned time. For the rest of the time the operator is picking up fabric, aligning it, turning it over and putting the parts down; this is an inherent part of sewing work and is already included in the standard minute value. This ratio therefore must not be used directly as a “machine utilisation” figure to assess operators: raising it depends on workstation layout, sewing aids and automatic units (Chapter 12) that cut handling time, not on making operators press the pedal harder.

Overall equipment effectiveness　To measure the overall performance of a workstation, overall equipment effectiveness (OEE) is commonly used. It divides the losses within planned time into three classes (Fig. 26-5):

OEE=A\times P\times Q=\frac{\text{run time}}{\text{planned time}}\times\frac{\text{pieces}\times\text{standard minute value}}{\text{run time}}\times\frac{\text{good pieces}}{\text{pieces}}

Availability A deducts stoppages: in the worked example, waiting for work 25 min, equipment faults 12 min and about 11 thread breaks of 1 min each leave a run time of about 402 min out of 450 min of planned time, so A ≈ 89.3%. Performance P deducts speed losses: at the standard minute value, the run time should yield 670 pieces, but about 569 were actually made, so P = 85%. Quality Q deducts rework: 3% of the pieces need rework, so Q = 97%. Multiplying the three gives OEE ≈ 73.6%, which equals the number of good pieces times the standard minute value, divided by the planned time. The breakdown shows where to start: the largest loss at this workstation is the speed loss (about 60 min), followed by waiting for work (25 min) and equipment faults (12 min), with thread breaks and rework each costing about 10 min. Note that performance here is based on the standard minute value, which includes manual handling, so what it really measures is operator efficiency rather than the machine’s ideal cycle time; OEE calculated this way for a manual sewing workstation cannot be compared directly with the OEE of automatic equipment.

Stoppage reasons　Networking also pays off in the statistics of stoppage reasons. The controller can identify some reasons automatically: thread breaks (on models with detection), equipment fault codes and control-box alarms. Reasons such as “waiting for work”, “changing thread” or “calling the supervisor” are unknown to the controller; the operator must tap them on a small screen next to the machine, or the hanger system can infer them (no hanger on the workstation spur means waiting for work). Sorting a week’s stoppages by reason into a Pareto chart often reveals that the largest losses lie not in the machines but in planning and logistics.

Case: why counting pieces by trims is inaccurate　This is a generic case constructed from first principles. A factory fitted its sewing machines with network modules and counted pieces by dividing the number of trims by the number of trims per piece, then paid piece rates on that count. After a month, operators commonly reported that the count was higher than the work tickets they had handed in, yet the finished goods received by the warehouse matched the tickets.

The reason is that not every trim corresponds to “a seam finished”. When a seam is sewn wrongly, unpicked and resewn, there is an extra trim; after a thread break the machine is rethreaded and the seam restarted, and the previous section is trimmed off, again one extra trim. In the worked example, each piece has a 5% probability of an extra trim due to rework, and each of the roughly 11 thread breaks in a shift adds one more, giving about 1,747 trims; divided by 3 seams per piece this gives about 582 pieces, about 2.3% more than the roughly 569 pieces actually made (Fig. 26-6). Conversely, if an operation sometimes trims in the middle of a seam (for example when changing direction halfway), or the operator sometimes uses hand scissors, the count will be too low. The fewer seams per piece, the larger the error caused by one extra trim.

With work tickets, the error comes from missed scans: with 20 pieces per bundle, if 2% of bundles are not scanned, the count is 2% low — and it is low by whole bundles at a time. In a hanger-equipped floor, counting by carriers is the most accurate: every carrier’s number is read each time it passes a workstation, and it is released only when the operator presses a button on finishing, so there is little chance of a missed count. In practice the data sources are often cross-checked: the piece count is taken from carriers or work tickets, and trim counts and main-shaft running time are used to check whether it is plausible — for example, if a workstation reports many pieces but its main shaft has hardly turned, it needs looking into. Trim counting remains useful: it shows whether rework and thread breaks at that workstation have increased.

26.6 Integration with the shop-floor management system, and the digital twin

Connecting to the MES　Sewing-machine data are only meaningful when matched against the production plan. The manufacturing execution system (MES) on the shop floor receives orders from the enterprise resource planning (ERP) system, breaks them into work orders and operations, and dispatches them to lines and workstations; the piece counts and states reported by sewing machines and the hanger system are the completion records of those operations (production reporting), which then flow back into the ERP to account for labour hours, piece-rate wages and cost (Fig. 26-7). In the WenQuest Digital Factory all systems deal only with the unified data bus; a bridge program translates fields between the bus and the ERP, and no component calls another directly. Replacing a simulated machine tool with real equipment only requires connecting it to the bus; nothing else needs to change.

Digital twin　A digital twin is a virtual sewing floor that changes in step with the real one, and the term has two layers of meaning. The first is a real-time mirror: every sewing machine, workstation and hanger carrier has a corresponding object in the virtual floor, whose state is updated in real time from messages on the bus, so a dashboard or a 3D view of the floor shows what the whole line looks like at this moment. The second is simulation and prediction: starting from the current actual state, the virtual floor is “fast-forwarded” through the next few hours to see in advance which operation will become congested and which order will be late, and to test which of several adjustments (adding an operator, changing the dispatching rule, rearranging the operations) works best. The hanger-dispatching simulation of Chapter 12 and the line simulation of Chapter 29 are models of exactly this predictive kind; once the floor is connected, their inputs are no longer assumed times and efficiencies but the measured data of every operator and every machine.

Teaching platform　The WenQuest Digital Factory turns these two layers into a teaching platform: the simulated factory publishes machine states on the bus in the real message format, students play planner, operator, quality inspector and plant manager, reading metrics, finding problems and making decisions on the home-page dashboard, and the instructor can trigger a stoppage at any time to see how the students respond. Replace its machines with sewing machines and its operations with garment operations, and it becomes a digital-twin teaching environment for a sewing floor; Virtual lab 26-1 demonstrates how the data of one of its sewing machines are generated and turned into metrics.

26.7 Remote service and security

Remote service　Once machines are networked, the equipment maker and the factory’s maintenance department can see fault codes and operating records remotely and diagnose most problems without visiting the site: is a parameter set wrongly, or is the current of a particular solenoid abnormal (Chapter 18)? Parameters can be pushed remotely — for example, at a style change the new stitch length, backtack and trimming settings can be sent to a whole line at once. Firmware can also be upgraded remotely; this should use the dual-bank update of Chapter 18 and be rolled out in batches: upgrade a few machines first, confirm they work, then push to the whole floor, with any machine able to roll back to the old version if something goes wrong. With usage-based data, equipment makers can also lease machines to small factories and charge by sewing time or stitch count, as in the industry-alliance case mentioned earlier.

Network security　Connecting sewing machines also connects the floor’s production systems to the network. The basic measures are: keep the equipment network separate from the office network, exchanging data only through a controlled gateway; encrypt communication between machines and the broker, with a separate account for every machine and every system; authorise by topic, so that a sewing machine can only write to its own workstation’s topics, cannot impersonate another machine and certainly cannot send commands to other machines; and log every command and parameter change sent down, so that it is possible to trace who changed what and when. Firmware for remote upgrades must pass signature verification (Chapter 18).

Data ownership and personal data　Part of a sewing machine’s data is in fact the operator’s personal data: when someone started work, how many seconds each piece took, how long they stopped. Such data can help reveal training needs and workstation-layout problems, but can also be used for excessive surveillance. Under the Personal Information Protection Law of the People’s Republic of China, the factory must inform workers in advance of the purpose, method and scope of processing their personal information and collect only what is necessary; processing necessary for human-resources management may be done without individual consent, but the workers must still be informed. In statistics and displays, use workstations or operations rather than individuals wherever possible; the ownership and permitted use of factory production data that equipment makers see through remote service must also be spelled out in the contract.

26.8 Limits of the model

The shift model in this chapter is a mean-value model: the number of thread breaks and the waiting and fault times are fixed values, with no account of their random variation or their interactions (for example, no thread breaks occur while waiting for work); performance is represented by a single fixed operator efficiency, whereas real efficiency varies with familiarity with the style, time of day and fatigue. Data volume is estimated from the average message rate, ignoring peaks at shift changes, network retransmissions and database-index overhead; 250 bytes per message is only an order of magnitude, and compression or binary encoding can make messages much smaller. Counting errors consider only two causes: extra trims and missed scans. On a real floor, these parameters must be calibrated against a period of measured data.

Shop-floor notes

  • If a machine shows “running” on the dashboard for a long time with no pieces counted, first check whether it has gone offline (was there a last-will message, is the retained state stale?).
  • A low sewing-time ratio does not mean the operator is slacking; look first at the workstation layout and handling motions.
  • If trim-based counts are too high, check rework and thread breaks at that operation; if too low, check for mid-seam trims or hand trimming.
  • If “other” takes a large share of stoppage reasons, the reason codes are poorly designed or operators are reluctant to tap them; simplify the choices.
  • Before pushing parameters remotely, try them on one machine first; both pushes and upgrades must be reversible.
