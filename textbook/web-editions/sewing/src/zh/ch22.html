所以本章讲的是测试的自动化：每一次改动都被自动测出来，测试结果都对应到需求编号上，进数字工厂的历史库；原型能不能升到下一个成熟度，也由这些数据决定。全章围绕一个贯穿的例子：一次看起来很划算的固件优化，让剪线在高转速下偶发失败，手工试缝发现不了，每晚的硬件在环测试当天夜里就把它抓住了。

22.1 引子：一个只在高速时出现的剪线失败

WQ-SC/LS 平缝原型的固件到了 v1.3.2，各项指标都已达标。一位工程师想把停车剪线做快一点。第 14 章算过，从 4000 r/min 停车剪线约 0.38 s：主轴先按伺服能力的 60% 减速到 300 r/min，减速段在剪线那一针开始（0°）之前结束，然后以 300 r/min 缝完剪线针，290° 给剪线电磁铁发令，下一转 55° 剪断。他的改法很直接（v1.4.0）：减速按伺服能力的 100% 规划；减速段不必在剪线针之前结束，推迟到剪线针的 180°，让减速和剪线针重叠。算下来，从 4000 r/min 停车到剪断从 377 ms 缩到 219 ms，每次省约 0.16 s。按第 14 章的说法，一个操作工一天剪几千次线，这就是每天十来分钟。

他在原型上试缝：3000、3500、4000 r/min 各踩几十次，剪线干净利落，再在软件在环（SIL）里跑了一遍剪线转速扫描，全部通过。版本合并了。当天夜里，硬件在环（HIL）台架上的剪线转速扫描报了红：从 5000 r/min 停车的 250 次剪线里，43 次没有剪断面线。

原因藏在一条他没有想到的曲线里（图 22-1）。伺服电机的减速能力并不是常数：转速低于基速时，能力受电流限制，约 4400 rad/s²（第 13 章）；高于基速，电机进入恒功率区，可用转矩随转速升高而下降，基速本身又随电网电压变化。v1.3.2 只用 60% 的能力，余量把这一点吞掉了；v1.4.0 用满 100%，又把减速终点推到剪线针中间，高速起步时主轴跟不上参考曲线，到 290° 发令时还没有降到 300 r/min。剪线电磁铁的延迟是 6–10 ms，动刀进刀角 = 290° + 6nt（第 14 章）；发令时转速超过约 667 r/min，延迟 10 ms 时进刀就晚过 330°，剪不断。算例中电网电压正常时，从 5000 r/min 停车发令时的转速约 514 r/min，还剪得断；电压低 10%，转速约 1150 r/min，必然剪不断。电压随时在波动，于是失败是“偶发”的：4500 r/min 以下与改动前相同（约 0.012%，来自电磁铁延迟本身的尾部），4750 r/min 约 1.2%，5000 r/min 约 17%。

手工试缝为什么测不出？有三个原因，每一个都是本章要解决的问题。第一，工况覆盖不到：人试缝时习惯在 3000–4000 r/min 踩，很少一脚踩到 5000 r/min 再松开，而且不会特意在电网电压偏低时试；在 3000–4000 r/min 试 50 次，看到一次失败的概率只有约 0.6%。第二，次数不够：即使在 4750 r/min 试，失败率 1.2%，试 50 次有一半的机会一次也看不到（22.6 节）。第三，模型不够：SIL 用的是第 13 章的理想电机，没有恒功率区，所以 SIL 扫描全部通过；HIL 台架的电机仿真器用的是按样机实测的转矩–转速曲线，才把它暴露出来。这三条合起来就是自动化测试的出发点：让机器按规定的工况、足够的次数、足够真实的模型，每天晚上把该测的都测一遍。

22.2 测试金字塔

把测试按“离真机多远”分层，越往下越快、越便宜、跑得越勤，用例也越多；越往上越接近真实，但越慢、越贵。画出来是一个金字塔（图 22-2）。WQ-SC 平台的测试分五层，和第 18 章的 V 模型右边那一路是对应的。

单元测试　测固件里的单个函数：编码器计数换算成 0.1° 角度、事件表的解析和查找、状态机在每种输入下转到哪个状态、故障码的编码。第 19 章的固件框架把硬件访问都收在 HAL 后面，所以这些函数可以在电脑上编译运行，几百个用例一分钟跑完。单元测试能发现的是逻辑错误：边界角 359.9° 到 0° 的跨越、参数越界、状态机漏了一条转移。它测不出时序和物理：v1.4.0 的减速规划函数本身算得完全正确，单元测试通过。

软件在环 SIL　把固件的控制部分和一个机器模型连起来，在电脑上按仿真时间运行。机器模型就是本书各章虚拟实验里的那些模型：第 13 章的主轴伺服和电磁铁，第 14 章的剪线时序，第 15 章的 X–Y 插补，第 17 章的选针。SIL 一次跑几分钟，可以做大量参数扫描：惯量 ±20%、摩擦 ±30%、电磁铁延迟 6–10 ms。它的边界就是模型的边界：模型里没有的物理（恒功率区、中断抖动、真实的电磁铁），SIL 看不见。

硬件在环 HIL　真的 WQ-SC 主控板、真的驱动板和电磁铁，接到一台实时仿真器上；仿真器按实测参数算主轴和机构的运动，产生编码器信号送回主控。固件跑在真实的芯片上，中断、DMA、CAN FD 总线都是真的，所以实时性问题、驱动器的真实特性、电磁铁的真实延迟都能测到；还可以故意制造现实中难得一见的故障：编码器断线、过流、电压跌落。HIL 一轮几个小时，放在晚上跑。

整机测试台　真机头装在通用测试台上（22.4 节），负载电机加载，相机看线迹，长时间跑。它测的是模型里根本没有的东西：线迹质量、回针对齐、机械间隙、温升、噪声。一轮一两天，每周或每个候选版本跑一次。

出厂测试 EOL　产品下线时每台都做的测试（第 18 章）。它的对象和前四层不同：前四层验证的是设计，假定被测的那台样机是好的；EOL 验证的是这一台装得对不对、元件好不好，设计默认已经验证过了。

22.4 通用测试台

要让测试自动化，先得有一台能被程序指挥、能自己测量的测试台。第 19 章的思路是“一套平台做四种机器”，测试台也照此办理：一套测量模块，换一块适配板，测四种原型（图 22-3）。

测试台有三部分。左边是测试计算机：跑 Python 测试脚本，经被测原型的网关下发命令、读回原型自己报的数据，同时从测试台模块读“真值”，判定、写报告，把结果发到数字工厂总线。中间是被测原型（DUT，device under test）：网关、WQ-SC 主控、驱动层，以及机头（整机测试台时是真机头，HIL 时由仿真器代替）。右边是测试台模块，它们独立于被测原型测量，这一点很重要：如果停针误差只读原型自己的编码器，编码器装偏了，原型和测试一起“正确”地错下去。

各模块的作用：

  • 负载电机与测功：一台伺服电机经梅花联轴器（零件库已有条目 A-CPL-JAW）接在主轴手轮一侧，按程序加负载转矩（模拟厚料刺布的阻力、或者模拟更大的惯量），同时测主轴的转矩和转速。
  • 编码器信号模拟：HIL 时代替主轴编码器，按仿真器算出的转角产生 A、B、Z 信号（2500 线、四倍频 10000 计数/转，与第 19 章一致），还能按指令注入丢脉冲、断线、抖动。
  • HIL 实时仿真器：按实测的转矩–转速曲线、惯量和摩擦算主轴运动，步长 1 ms 以下；它的模型比 SIL 的“真”一层，因为参数来自对样机的实测（22.1 节的恒功率区就是这样进来的）。
  • 数据采集与电流探头：电磁铁线圈电流、母线电压、编码器角度和固件的发令信号同步采样，后者用主控板的一个调试输出脚引出。
  • 行程传感器：测电磁铁衔铁或动刀的位移，得到真实的吸合、释放时刻；和发令时刻相减就是延迟，再按转速折成转角（REQ-SOL-01）。
  • 线迹相机：拍布面，识别针迹位置，算回针对齐偏差、跳针、线头长度；剪线是否剪断也可以由它判定（面线是否被拉出一长段）。
  • 温度采集：电机、散热器、电磁铁线圈和环境温度，供 4 h 长跑判定温升。

换型　同一台测试台测四种原型，靠的是三件“标准化”的事。机械上，每种原型做一块适配板，把机头或平台固定在测试台的同一组安装孔上，主轴（或横机的机头驱动轴）经同一种联轴器接负载电机；花样机的 X–Y 平台再加两把光栅尺或一个激光位移传感器测实际位置，横机则用编码器模拟器模拟机头位置、用行程传感器看选针器。电气上，测试台和原型之间用同一套带编号的插头，第 19 章的接线表决定哪个插针接什么。软件上，每种原型一个测试配置文件，写明接线表、HAL 驱动、该跑哪些用例；测试脚本本身不变。换型一次只要拆装适配板、换配置文件，半小时以内（示意）。

现场要点

  • 测试台的测量链本身要定期校准：用一个已知转角的分度盘核编码器模拟器和行程传感器，用砝码和力臂核测功单元。测试台不准，所有结论都不可信。
  • “真值”要来自独立的传感器，不能只读被测原型自己报的数。两者都记下来，它们的差本身就是一个很有用的指标。
  • 每台测试台也有序列号和“固件版本”（测试脚本的版本），一起写进结果。

22.5 测试脚本：用 Python 和 pytest 驱动

测试脚本用 Python 写，用 pytest 组织。选它们的理由很朴素：语法简单，工程师和学生都能读；pytest 的“夹具（fixture）”正好用来管理“连上样机、测完断电”这类准备和收尾；参数化测试（parametrize）一行就能把一个用例扩成一组转速；结果能输出成持续集成服务器认识的格式。问渠数字工厂的自动测试也是这样做的：pytest -q tests 跑单元测试，另有一个完整闭环脚本按实验流程把整个工厂走一遍，在推送代码后由 CI 自动运行（数字工厂 README 第五节）。

夹具：连上原型、发结果　下面的 conftest.py 定义两个夹具。dut 经网关的网页接口连上被测原型，读出序列号、固件版本和参数版本；它提供一个 cmd() 方法，下发命令并等它做完，返回原型和测试台测到的数据。report 连上数字工厂的 MQTT 代理，把每条结果按统一信封格式发到 …/measurement 主题。网关的接口名（/api/v1/info、/api/v1/cmd）是本章的示意，以第 19 章网关的实际定义为准。

# tests/conftest.py —— 连接被测原型（DUT），把结果发到数字工厂
import datetime as dt, json, os, uuid
import pytest, requests
import paho.mqtt.client as mqtt

GW    = os.environ.get("WQ_DUT", "http://192.168.10.21")   # 原型网关（示例地址）
BUS   = os.environ.get("WQ_BUS", "bus.lab.local")          # 数字工厂 MQTT 代理
TOPIC = "wq/sewing/lab/tb-01/measurement"                  # 工厂/区域/单元/类别

def pytest_configure(config):
    config.addinivalue_line("markers", "req(id): 这个用例验证的需求编号")

class Dut:
    def __init__(self, base):
        self.base = base
        info = requests.get(base + "/api/v1/info", timeout=5).json()
        self.serial, self.fw, self.param = info["serial"], info["fw"], info["param_ver"]

    def cmd(self, name, **kw):
        """下发一条命令，等原型做完，返回测量结果（dict）。"""
        r = requests.post(self.base + "/api/v1/cmd", json={"cmd": name, **kw}, timeout=300)
        r.raise_for_status()
        return r.json()

@pytest.fixture(scope="session")
def dut():
    d = Dut(GW)
    d.cmd("reset_faults")
    yield d
    d.cmd("safe")                      # 无论成败，测完把执行器断电

@pytest.fixture(scope="session")
def report(dut):
    cli = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2, client_id="tb-01-pytest")
    cli.connect(BUS)
    cli.loop_start()
    run = "run-" + uuid.uuid4().hex[:8]          # 同一轮测试共用一个关联号

    def send(req, case, value, unit, limit, ok, **extra):
        ts = dt.datetime.now(dt.timezone.utc).isoformat(timespec="milliseconds")
        msg = {"v": 1, "id": uuid.uuid4().hex, "ts": ts.replace("+00:00", "Z"),
               "type": "test.result", "source": "tb-01/pytest", "mode": "prod", "corr": run,
               "data": {"req": req, "case": case, "dut_serial": dut.serial,
                        "fw": dut.fw, "param_ver": dut.param,
                        "value": value, "unit": unit, "limit": limit,
                        "result": "pass" if ok else "fail", **extra}}
        cli.publish(TOPIC, json.dumps(msg, ensure_ascii=False), qos=1).wait_for_publish()
    yield send
    cli.loop_stop()
    cli.disconnect()

消息的外层信封（v、id、ts、type、source、mode、corr、data）沿用问渠数字工厂的格式（第 26 章）；test.result 是按规范“只增加、不改动”的原则为测试结果新增的数据类型，主题里的区域 lab 和单元 tb-01 也是本章的示例命名。QoS 用 1 级，接收方按消息编号去重（第 26 章）。

用例　下面是 WQ-SC/LS 验收用例的节选。每个用例做三件事：按规定的工况让原型动作若干次，算出统计量，和判据比较；结果无论成败都先发到总线，再用 assert 判定。

# tests/test_ls_acceptance.py —— WQ-SC/LS 验收用例（节选）
import statistics as st
import pytest
from stats import r_lower, max_fail        # 22.6 节的两个函数

SPEEDS = [3000, 3500, 4000, 4500, 4750, 5000]
TRIMS = {}                                 # 各转速点的 (次数, 失败)，最后汇总判定

@pytest.mark.req("REQ-POS-01")
def test_stop_position(dut, report):
    """停针：50 次停车，最大误差 ≤ 1°，Cpk ≥ 1.33。"""
    e = [abs(dut.cmd("run_and_stop", rpm=3000, stitches=20)["stop_err_deg"]) for _ in range(50)]
    mu, sd, mx = st.mean(e), st.stdev(e), max(e)
    cpk = (1.0 - mu) / (3 * sd)            # 只有上限，用单侧 Cpk
    ok = mx <= 1.0 and cpk >= 1.33
    report("REQ-POS-01", "test_stop_position", mx, "deg", 1.0, ok, cpk=round(cpk, 2), n=50)
    assert ok, f"最大 {mx:.2f}°，Cpk {cpk:.2f}"

@pytest.mark.req("REQ-TRM-01")
@pytest.mark.parametrize("rpm", SPEEDS)
def test_trim_point(dut, report, rpm):
    """剪线：从 rpm 起停车剪线 250 次，记下失败次数（相机判定面线、底线是否剪断）。"""
    n = 250
    fails = sum(not dut.cmd("sew_and_trim", rpm=rpm, stitches=20)["trim_ok"] for _ in range(n))
    TRIMS[rpm] = (n, fails)
    report("REQ-TRM-01", f"test_trim_point[{rpm}]", fails, "count", None, fails <= 1, n=n)
    assert fails <= 1, f"{rpm} r/min：{fails}/{n} 次没剪断"      # 单点出现 2 次以上，先报警

@pytest.mark.req("REQ-TRM-01")
def test_trim_overall(report):
    """全部转速点合计：可靠度的 95% 置信下限 ≥ 99.5%。"""
    n = sum(v[0] for v in TRIMS.values())
    x = sum(v[1] for v in TRIMS.values())
    rl = r_lower(n, x, 0.95)
    report("REQ-TRM-01", "test_trim_overall", rl, "ratio", 0.995, rl >= 0.995, n=n, fails=x)
    assert rl >= 0.995, f"{x}/{n} 次失败，下限 {rl:.4f}（{n} 次最多允许 {max_fail(n)} 次）"

@pytest.mark.req("REQ-XY-01")
@pytest.mark.parametrize("pattern", ["circle_r20.wqp", "zigzag_3mm.wqp", "logo_dense.wqp"])
def test_xy_following(dut, report, pattern):
    r = dut.cmd("run_pattern", file=pattern, rpm=2500)        # 测试台光栅尺测实际位置
    ok = r["follow_err_mm"] <= 0.05 and r["move_in_fabric_mm"] == 0
    report("REQ-XY-01", f"test_xy_following[{pattern}]", r["follow_err_mm"], "mm", 0.05, ok)
    assert ok

几点说明。第一，参数化让一个用例变成一组：test_trim_point 按 6 个转速各跑一次，报告里分别列出，哪个转速出问题一目了然；22.1 节的回归正是靠 4750、5000 这两个点抓住的，如果只测 4000 r/min，它照样漏过去。第二，判据写在用例里，而且和需求表一致：单点出现两次以上失败先报警，合计用二项分布的置信下限判定（22.6 节）。第三，停针误差取绝对值的最大值和 Cpk 两个判据：只看一次停车的误差，v1.3.2 那次“停车更快”的改动（位置增益 200→300 s⁻¹）在 HIL 上单次约 0.91°，是通过的；50 次的统计才显出它的最大值超过 1°、Cpk 只有约 0.3（22.6 节）。第四，测试脚本只认识网关的命令和测量，不认识机型：同一个 test_stop_position 换个配置文件就能测包缝原型。

平缝原型的单元测试是 C 写的固件函数，可以用 C 的单元测试框架在电脑上编译运行，也可以把固件编译成主机上的动态库，用 Python 调它的函数，让 pytest 统一管理全部五层的用例和报告。SIL 用例同样用 pytest 写，只是 dut 夹具连的不是网关，而是一个“固件 + 模型”的仿真进程，命令和返回的格式一样。这样，同一个用例可以先在 SIL 上跑，再原样拿到 HIL 和整机测试台上跑，三层的结果可以直接比较，22.9 节就用到了这一点。

22.6 要测多少次才算数

剪线成功率 ≥ 99.5%，试了 200 次全部成功，够不够？不够。200 次全成功只能说明“成功率不太可能很低”，并不能说明它不低于 99.5%。要回答“够不够”，得把问题说成统计的语言：在置信度 C 下，证明可靠度不低于 R。

22.6.1 零失效验证试验

如果真实的可靠度恰好是 R，n 次试验全部成功的概率是 Rⁿ。要求这个概率不超过 1 − C，也就是说“如果可靠度只有 R，我们几乎不可能看到 n 次全成功”，于是

\[ R^{\,n}\le 1-C \quad\Longrightarrow\quad n\ \ge\ \frac{\ln(1-C)}{\ln R} \]

R = 99.5%、C = 95% 时，n ≥ ln 0.05 / ln 0.995 = 597.6，取 598 次。也就是说，从某个转速停车剪线 598 次一次不失败，才能以 95% 的置信度说剪线成功率不低于 99.5%。表 22-5 列出几组常用的数。有一个容易记的近似：C = 95% 时 n ≈ 3/(1 − R)，即“零失效时，要测的次数约是失效率倒数的三倍”。

22.6.2 有失效时的置信下限

n 次里失败了 x 次，可靠度的点估计是 1 − x/n，但判定要用它的置信下限。设失效率为 p，失败次数服从二项分布；单侧置信上限 pU 是使“失败不超过 x 次”的概率恰好等于 1 − C 的那个 p：

\[ \sum_{k=0}^{x}\binom{n}{k}p_U^{\,k}(1-p_U)^{\,n-k}=1-C,\qquad R_L=1-p_U \]

这就是 Clopper–Pearson 方法，pU 也可以用 β 分布的分位数直接算：pU = Beta⁻¹(C; x+1, n−x)。用 Python 两行就够了：

# stats.py —— 22.6 节
from math import ceil, log
from scipy.stats import beta

def n_zero(R, C):              # 零失效验证需要的次数
    return ceil(log(1 - C) / log(R))

def r_lower(n, x, C=0.95):     # n 次 x 次失败时可靠度的单侧置信下限
    return 0.0 if x >= n else 1 - beta.ppf(C, x + 1, n - x)

def max_fail(n, R=0.995, C=0.95):   # n 次里最多允许失败几次
    x = -1
    while r_lower(n, x + 1, C) >= R:
        x += 1
    return x

print(n_zero(0.995, 0.95))                     # 598
print([round(r_lower(1000, x), 4) for x in range(4)])   # [0.997, 0.9953, 0.9937, 0.9923]

1000 次剪线，0 次失败时下限 99.70%，1 次失败 99.53%，都满足 99.5%；2 次失败时点估计是 99.8%，下限却只有 99.37%，不满足（图 22-4 中）。所以表 22-2 里写“单点 1000 次最多 1 次失败”。22.5 节的转速扫描合计 1500 次，最多允许 2 次失败。

22.6.3 测多少次才能抓住一个回归

上面问的是“证明它好要测多少次”，持续集成还要问另一个问题：“它变坏了，测多少次能发现”。如果一次改动让失效率变成 p，n 次里至少看到一次失败的概率是 1 − (1 − p)ⁿ。要有 95% 的把握抓住 p = 0.5% 的回归，也要约 598 次，和零失效验证的次数一样，这不是巧合，两个问题是同一个式子。22.1 节的回归在 4750 r/min 时 p ≈ 1.2%，250 次就有约 96% 的把握看到；在 5000 r/min 时 p ≈ 17%，几次就能看到。这说明了测试设计的一个原则：把有限的次数花在最可能出问题的工况上。同样 250 次，放在 4000 r/min 一次失败也看不到，放在最高转速就几乎必然抓住。

22.6.4 计量型指标：均值、3σ 和 Cpk

停针误差是一个连续的量，不必只数“过没过”。设 50 次停车误差的均值为 μ、标准差为 σ，判据只有上限 USL = 1°，用单侧过程能力指数

\[ C_{pk}=\frac{\mathrm{USL}-\mu}{3\sigma} \]

Cpk ≥ 1.33 意味着上限离均值至少 4σ。算例中（图 22-4 右，HIL 惯量 6.3×10⁻⁴ kg·m²，每次停车的摩擦和定位速度有小的随机变化，另加 0.03° 的测量噪声）：位置增益 Kp = 200 s⁻¹ 时，均值 0.17°、σ 0.026°、Cpk ≈ 10.7，余量很大；Kp = 300 s⁻¹ 时，均值 0.92°、σ 0.079°、最大 1.13°，Cpk ≈ 0.34，不合格。单次停车 0.91° 看上去还“合格”，统计一下就知道它其实踩在线上。计量型判据比计数型判据省次数：50 次停车就能看清分布，而要用“过/不过”证明 99.5% 要上千次。所以能测出连续值的地方，都应该记下连续值，而不只是 ✓ 或 ✗。

Cpk 假定误差近似正态，而且过程是稳定的。停针误差的分布被摩擦“卡住”时并不正态（第 13 章），样本少时 σ 的估计也很粗；所以判定时同时看最大值，并且在不同的测试台、不同的样机上重复，不要只凭一个 Cpk 数字下结论。

22.7 持续集成：每次改固件都自动测

持续集成（CI）的意思是：每一次提交都自动构建、自动测试；不通过的改动不准合并到主干。它把 22.2 节的金字塔变成一条流水线（图 22-5）。问渠仓库里数字工厂的 CI 是一个现成的样子：只要推送改动了 factory/，就依次“测试 → 服务器演练（装一套真的 ERPNext、走完整闭环）→ 构建镜像 → 部署到服务器”，前一步失败后一步就不跑，失败的日志自动整理成注释。缝纫机固件的 CI 结构相同，只是“演练”换成了 HIL 台架，“部署”换成了发布固件包。

三条流水线　每次推送：编译固件（交叉编译）和主机版，跑单元测试和 SIL，约 12 min，失败就不准合并；开发者喝杯水的工夫就知道结果。每晚：取主干最新版本刷进 HIL 台架的主控，跑 HIL 回归用例，预算 4 h；结果发到总线、进看板，失败自动二分。每周或每个候选版本：在整机测试台上跑约 2 天，四种原型各做 4 h 最高转速长跑、1000 次真剪线、相机看回针和线迹；全部通过才发布，固件版本号和参数版本号随原型上报数字工厂。下面是一个示意的流水线配置（GitHub Actions 的写法，HIL 任务跑在接着台架的那台电脑上）：

# .github/workflows/firmware.yml（示意）

    runs-on: ubuntu-latest

  nightly-hil:                            # 每晚：预算 4 h
    if: github.event_name == 'schedule'
    runs-on: [self-hosted, hil-01]        # 接着 HIL 台架的电脑

    steps:
      - uses: actions/checkout@v4

      - run: python -m pytest tests/hil -m nightly --junitxml=hil.xml
      - if: failure()
        run: tools/bisect_hil.sh "$(cat .last_green)" "$GITHUB_SHA"

一个反面的例子：如果把每晚的剪线用例定成“4000 r/min 剪 1000 次”（55 min），停针用例定成“停 1 次”（2 min），总时间还更短，可是 22.1 节和 v1.3.2 的两个回归一个也抓不住：前者只在高速出现，后者单次停车 0.91° 刚好“通过”。用例集的设计本身也要测，办法是故意往固件里放进已知的缺陷，看用例集能不能抓住它（变异测试的思路），虚拟实验 22-1 的任务 2 就是这样一个练习。

失败自动定位到提交：二分　HIL 失败时，上一晚全绿，这一晚变红，中间也许合并了二三十个提交。逐个试太慢；二分法每次试中间那个，好就往后找、坏就往前找，k 轮能在 2k 个提交里找到第一个坏的，23 个提交要 5 轮。git 自带这个功能：

# tools/bisect_hil.sh GOOD BAD —— 只重跑失败的那一个用例
git bisect start "$2" "$1"
git bisect run sh -c '
  make firmware || exit 125                         # 编不过的提交跳过
  tools/flash.sh build/wqsc.bin || exit 125
  python -m pytest -q tests/hil -k "trim_point and 5000"'
git bisect log > bisect.log; git bisect reset

二分时只跑那一个失败的用例，而且要选它最敏感的工况：在 5000 r/min 剪 250 次，好的提交几乎不会失败、坏的提交平均失败 43 次，一轮就能判清；如果选 4750 r/min，坏的提交也只有约 96% 的概率露出来，二分就可能在某一轮判错，把账算到无辜的提交上。所以二分用的用例要满足两条：坏的一定失败，好的一定通过（统计上），这又回到了 22.6.3 节的算法。

设计要点

  • 测试配置（用例集、判据、测试台的版本）和固件一起放进版本库，一起评审；改判据和改代码一样要留下记录。
  • 不稳定的测试（同一版本时过时不过）比没有测试还糟糕，它让人习惯性地忽略红灯。发现了就查清是测试台、模型还是固件的问题，修好或隔离，不能“再跑一遍试试”。
  • 每晚的报告只看三样：哪些需求变红了、相对上一晚变化最大的指标、二分的结论。细节点进去再看。

出厂测试 EOL　量产以后，每台控制箱和整机下线都要过 EOL。它的项目从验收用例里挑“快、能发现装配缺陷”的：编码器读数和零位、停针 10 次、剪线 20 次（看有没有剪不断，而不是证明 99.5%，那是设计验证的事）、电磁铁线圈电流波形（线圈装错、短路一眼就看得出）、脚踏、固件版本核对和参数写入，再加上第 18 章的电气安全测试（接地连续性、绝缘电阻、耐压）和老化。每台 3–5 min（示意）。EOL 的测试脚本和研发用的是同一套框架，只是用例集不同，所以研发阶段的每一个用例都可能直接变成 EOL 项目。

数据随序列号进数字工厂　EOL 的每一条结果都按 22.5 节的格式发到总线，主题如 wq/sewing/eol/eol-01/measurement，带着序列号、固件和参数版本，进历史库和质量系统（第 27 章）。这样，任何一台机器在它的一生里都可以查到：出厂时停针误差多少、剪线测了几次、用的哪一版固件。

现场数据回流　机器到了用户的车间，联网以后（第 26 章）上报的状态和事件里，有剪线次数、故障码、固件和参数版本。按版本、批次、序列号把这些数据和出厂数据对起来，就能看到实验室里看不到的东西：比如某一版固件的机器在电网电压不稳的厂区“剪线不断”的报修明显多，或者某一批电磁铁的机器两年后吸合变慢。每发现这样一个问题，就在追溯矩阵里加一条 REQ（或收紧一条判据）、加一个能复现它的用例（往往是 HIL 上的一种故障注入或一种工况），下次改固件时就会自动测。第 27 章把这叫做质量闭环；对测试来说，它意味着用例集是跟着产品一起长大的。

22.9 案例：一次固件优化让剪线在高转速下偶发失败

技术问题　回到 22.1 节。这是一个按原理编写的案例，数字由本章的模型算出（figsrc/ch22_model.py，与虚拟实验 22-1 相同），都是示意值。v1.4.0 的“快速剪线”改动在某个周二下午合并：减速按伺服能力的 100% 规划，减速终点从剪线针的 0° 推迟到 180°。推送时的流水线约 12 min 全绿：单元测试检查了减速规划函数的计算，SIL 的剪线转速扫描（3000–5000 r/min，每点 200 次）0 次失败。

发现　当晚 02:00 的 HIL 回归里，剪线转速扫描报红：5000 r/min 点 250 次失败 43 次，4750 r/min 点也有失败，合计远超 1500 次最多 2 次的判据；其他用例全绿（图 22-7 左）。总线上的结果附带每次剪线的发令转速，一眼可见：失败的那些剪线，发令时转速在 700–1200 r/min，而判据要求是 300 r/min 附近。

定位　上一晚全绿，这一晚之间合并了 23 个提交。CI 自动二分，只重跑“5000 r/min 剪 250 次”这一个用例：第 11 个提交通过，第 17 个失败，第 14 个失败，第 12、13 个通过，第 5 轮结束，指向第 14 个提交 a3f9c1e（“trim：减速规划用满能力，终点并入剪线针”），每轮编译、刷写约 3 min，剪 250 次约 13 min，一共约 80 min。早上工程师到岗时，看到的是一份报告：哪条需求、哪个用例、哪个提交、失败时的转速记录。

原因　图 22-7 右边是从 5000 r/min 停车时剪线针里的转速。v1.3.2 按 60% 能力减速，参考曲线在剪线针的 0° 结束，主轴跟着在约 95° 稳定在 300 r/min，离 290° 发令还有将近 200°；v1.4.0 按 100% 能力规划，终点又推迟到 180°，可主轴在恒功率区里减不了那么快，越落越后，到 290° 发令时还有约 514 r/min（电网电压正常）；电压低 5% 时约 850 r/min，低 10% 时约 1150 r/min。进刀角 290° + 6nt 在 n = 850 r/min、t = 8 ms 时已到 331°，晚过窗口。为什么 SIL 没抓住？SIL 的电机模型是第 13 章的理想电机，减速能力处处是 4400 rad/s²，在它里面 v1.4.0 的规划完全可行，失败率与改动前相同（约 0.011%）。HIL 仿真器的转矩–转速曲线来自样机实测，高于基速进入恒功率区，基速随母线电压变化，这才有了问题。

修复（v1.4.1）　两处改动。一是减速按电机实际的转矩–转速曲线规划，并且只用 90%，基速按电压下限（0.9 倍）取；二是加一道保险：剪线针 270° 时检查实测转速，高于 400 r/min 就把剪线推迟一针，宁可慢一针，不能剪不断。修复后从 5000 r/min 停车，无论电压高低，发令时转速都回到 300 r/min；从 4000 r/min 停车到剪断约 0.23 s，比 v1.3.2 的 0.38 s 仍快约 0.15 s，优化的好处大部分保住了。

回归　v1.4.1 在 HIL 上重跑全部每晚用例，剪线扫描 0/1500；再在整机测试台上从 5000 r/min 真剪 1000 次，0 次失败，可靠度下限 99.70%（C = 95%）。另外两件事同样重要：把 HIL 的转矩–转速曲线（含电压系数）移植进 SIL 模型，让 SIL 以后也能在几分钟里抓住这类问题；把“剪线发令时转速”作为一个新的计量型指标写进 REQ-TRM-01 的用例，报告里每晚画趋势，它比“剪没剪断”早得多地显出苗头。

22.10 模型的边界

本章的数字都来自几个简化的模型，用途是看清测试设计里的因果和量级。剪线模型把失败只归到动刀进刀角晚过 330°（或早于 300°），没有考虑线环形状、刀刃磨损、线的种类；电磁铁延迟取正态分布 N(8, 0.667) ms，与第 14 章的 6–10 ms 对应，真实分布可能偏斜，尾部更长，而尾部恰恰决定了 99.5% 这个量级的失效率。伺服的恒功率区用“能力与 nb/n 成正比”表示，基速随电网电压按 5% 的标准差变化，速度环用 3 ms 的一阶滞后表示，都是示意；真实的转矩–转速曲线要在测功台上实测。停针模型就是第 13 章的连续时间模型，加上随机的摩擦和测量噪声；Cpk 的计算假定正态和稳定。

统计方面，零失效公式和 Clopper–Pearson 下限假定每次试验独立、失效率不变。实际上，同一台样机连续剪 1000 次，线、刀、温度都在变，失败也可能成串出现；在一台样机上证明的 99.5%，不等于每台都是 99.5%，所以 DVT 要用多台样机、多种环境。测试金字塔各层的用例数、耗时和费用，表 22-6 的时间分配，成熟度的退出条件，都是为说明方法而取的示意值，具体项目要按自己的需求、台架数量和风险重新定。网关接口、主题命名（lab、eol 区域）和 test.result 数据类型是本章的示例，以第 19 章和数字工厂规范的实际定义为准。最后，测试只能证明“在测过的工况下没有发现问题”，不能证明没有问题；22.1 节的回归如果只在 5200 r/min 以上出现，而扫描只到 5000 r/min，它照样会漏过去。用例的工况范围要覆盖需求规定的全部范围，再留一点余量。

现场要点

  • 手工试缝“没问题”不等于没问题：问一句“试了哪些转速、多少次、什么电压”，再对照表 22-5 看够不够。
  • 剪线时好时坏，先看是不是只在高速停车时出现；查固件版本和减速参数，再查电网电压和电磁铁电压（第 13、14 章）。
  • 现场报修要记下序列号和固件、参数版本，和出厂测试数据对得上，问题才查得下去。
  • 每升级一次固件，至少在一台机器上跑一遍 EOL 用例集，再大批推送。

第 22 章 习题

  1. 要以 90% 的置信度证明剪线成功率不低于 99%，零失效验证需要多少次？如果允许 1 次失败呢？
    参考答案零失效 n ≥ ln 0.1 / ln 0.99 = 229.1，取 230 次；允许 1 次失败约需 388 次（用 22.6 节的 r_lower 逐次试算）。
  2. 剪线测试 1500 次，失败 3 次。点估计和 95% 置信下限各是多少？是否满足 REQ-TRM-01？
    参考答案点估计 99.80%；下限约 99.48%，略低于 99.5%，不满足。1500 次最多允许 2 次失败。
  3. 某次改动可能让剪线失效率变成 1%。每晚想以 99% 的把握发现它，至少要剪多少次？如果每次剪线循环 3 s，要多少分钟？
    参考答案n ≥ ln 0.01 / ln 0.99 ≈ 458.2，取 459 次；约 23 min。
  4. 50 次停车误差的均值为 0.62°，标准差 0.09°，上限 1°。求 Cpk，判断是否合格；要让 Cpk 达到 1.33，在标准差不变时均值最多是多少？
    参考答案Cpk = (1 − 0.62)/(3 × 0.09) ≈ 1.41，合格；均值 ≤ 1 − 4 × 0.09 = 0.64°。
  5. 两晚之间合并了 40 个提交，HIL 剪线用例失败。二分最多要几轮？每轮编译刷写 3 min、跑一个用例 13 min，最多要多久？如果二分用的用例对坏提交只有 90% 的检出率，会出什么问题，怎样避免？
    参考答案⌈log₂40⌉ = 6 轮，约 96 min。检出率不够时，坏提交可能被判为“好”，二分会把问题归到后面一个无辜的提交上；办法是选最敏感的工况（如最高转速）、增加次数使检出率接近 100%，或对二分结果再复核一次。
  6. （讨论）22.9 节说“把 HIL 的转矩–转速曲线移植进 SIL 模型”。这样做之后，是否就可以取消每晚 HIL 的剪线扫描？结合 22.2 节各层能发现的缺陷类型说明理由。
    参考答案不能取消。SIL 加了这条曲线后，能在几分钟里抓住同一类规划问题，这是好事；但 HIL 还测实时性（中断延迟、总线时序）、真实驱动器和真实电磁铁的延迟，这些不在 SIL 模型里。合理的做法是 SIL 先拦住大部分问题，HIL 用较少的次数做确认，把省出的时间给别的用例。
  7. （讨论）为 WQ-SC/OL 包缝原型列出 4 条验收需求（REQ 编号、判据），说明每条在哪一层用什么用例验证，并估计每晚 HIL 需要多少时间。
