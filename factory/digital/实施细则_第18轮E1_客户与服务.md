## 一、目标

厂情中枢已经能看懂车间。但工厂的起点和终点都在客户：订单从哪来，产品出厂后用得怎样、出了问题怎么追、怎么补救。现在这一段数据很少：
- 客户只有名字（从销售订单里来）；
- 线索、商机、报价、合同在本体里都是“ERPNext 可启用 / 待采集”；
- 投诉、满意度、回访、服务工程师根本没有；
- 推演里的违约金是写死在代码里的一张订单（$200/天）。

E1 把“**客户 → 商机 → 报价 → 合同 → 订单 → 交付 → 现场 → 投诉 → 追溯 → 服务 / 召回 → 回访**”接成闭环。按领域包的标准做齐六样：**采集应用、教学模拟器、规则、动作、态势卡、帮助**；再加 AI 代理的工具和评测题，以及一个新实验。

这一轮结束时，两个验收故事要能在网页上完整走通：

**故事一：一张投诉追到车间，再追回现场**
1. 港口客户来电：WQR105-H2504-06 有异响、油温偏高。服务员在手机上登记投诉，扫设备铭牌上的序列号。
2. 厂情中枢马上开一个异常，追因链一路连到：这台设备 → 装的输出轴 → 磨它的那片砂轮 → 同一片砂轮磨的其他轴 → 它们装在哪几台设备、属于哪几个客户。这就是“排查范围”，按孪生健康度排好风险。
3. 右栏给出处理方案：
   - 只修这一台；
   - 修这一台，再给高风险的几台上门点检；
   - 整批召回点检。
   每个方案都给出要派几个工程师、几天能做完、要几套备件、花多少钱（保修期内的不收费，由合同条款决定）、几个客户受影响。
4. 采纳“修这一台 + 高风险点检”，厂长批准后：
   - ERPNext 里生成服务工单，按区域和排班自动派给工程师；
   - 备件发运单生成；
   - 给受影响的客户起草预防性服务通知，人确认后才发出。
5. 工程师完工后回访，客户打满意度分；复盘对比“当时估计”和“实际”。

**故事二：合同条款进入推演**
1. 销售在漏斗里把一条线索推进成商机，用参数配置器出报价。
2. 签合同时录入保修期、延期违约金。合同转成销售订单。
3. 这张订单有延期风险时，推演里的违约金按合同条款算，不再写死。

## 二、决定（已确认）

| 编号 | 决定 | 理由 |
|---|---|---|
| E1-1 | **数据放哪：ERPNext 有现成单据的以 ERPNext 为准，平台只做好用的采集界面，并同步进本体。**<br>· 以 ERPNext 为准：线索（Lead）、商机（Opportunity）、报价（Quotation）、合同（Contract）、服务工单（Issue）、保修（序列号上的保修到期日）。平台经桥接读写，和现有的订单、工单一样；<br>· 平台自建（ERPNext 没有或不好用）：投诉、满意度与回访、服务工程师与排班、排查 / 召回批次。投诉同时在 ERPNext 开一张 Issue（类型“投诉”），财务和售后在 ERPNext 里也能看到；<br>· 本体里这些类型从“ERPNext 可启用 / 待采集”改为“已有数据” | 不另造一套 CRM；企业客户本来就用 ERPNext。平台补的是 ERPNext 的短板：手机采集、追溯、派工 |
| E1-2 | **采集应用：新页“客户与服务”**（销售、服务、厂长默认可见；手机上好用）。四个标签：<br>① **销售漏斗**：线索 → 商机 → 报价 → 合同，看板式，拖动换阶段；报价直接调用参数配置器；<br>② **投诉**：登记（客户、设备序列号（可扫码）、现象、严重度、照片），处理进度，关联的异常和服务工单；<br>③ **服务**：服务工单列表、工程师排班日历（谁哪天在哪个区域、手上几单）、备件发运；<br>④ **回访与满意度**：服务完成后自动生成回访任务，打分 1–5 分加一句话 | 方案“每个领域都有采集应用” |
| E1-3 | **合同条款进入推演和成本**：<br>· 合同有：保修期（月）、延期违约金（$/天，可为 0）、响应时限（小时）；<br>· 推演算违约金时读合同（替换现在写死的 `PENALTY_PER_DAY`）；没有合同的订单不算违约金；<br>· 服务成本：保修期内工时和备件不向客户收费，算工厂的保修成本；过保的收费；<br>· 教学数据给三个客户各配一份合同（峰顶搅拌机：违约金 $200/天，与现在一致，测试结果不变） | 推演用的条款来自真实合同，而不是代码 |
| E1-4 | **投诉 → 追溯 → 排查范围**：<br>· 投诉关联现场设备后，自动开异常（规则 C1），因果链沿用 17B 的“现场 → 总成 → 输出轴 → 砂轮 → 同砂轮的轴 → 它们的现场设备 → 客户”；<br>· 排查范围按风险排序：孪生健康度（红 / 黄 / 绿）、轴承 L10 已用比例、振动；每台标出是否在保修期、属于哪个客户、离哪个工程师最近；<br>· 投诉的设备没有接孪生（序列号查不到）时，照样登记，追因链写明“这台没有出厂数据，追不到车间” | 方案故事一“数字主线” |
| E1-5 | **规则（6 条，其中 C1、C2 由“待数据”转为在跑）**：<br>C1 新投诉（严重度按投诉等级和客户等级）；<br>C2 满意度下降（近 3 次回访平均 < 3.5 分）；<br>C3 投诉超时没响应（超过合同响应时限）；<br>C4 同一批次 2 台以上投诉或报警 → 疑似批次问题（严重）；<br>C5 报价快到期没跟进（3 天内到期）；<br>R3 订单延期会触发合同违约金（与 S1 交期风险并存时，显示违约金金额） | 覆盖投诉、满意度、服务时效、批次、销售跟进、合同风险 |
| E1-6 | **处理预案与新动作（4 种）**：<br>· 预案：C1 / C4 ——“只修这一台 / 修这一台 + 高风险点检 / 整批排查”；C3 ——“改派最近的工程师 / 远程支持先行”；<br>· 新动作：<br>　① **开服务工单并派工程师**（ERPNext Issue，指派到人）；<br>　② **批量点检**（一组服务工单，一次审批）；<br>　③ **备件发运**（ERPNext 出库单，从成品 / 备件库扣）；<br>　④ **客户通知**（预防性服务通知，平台起草，人确认后发出；生产模式发到合同联系人邮箱，教学模式只记录不发）。<br>· 审批：花钱的（批量点检、过保免费、备件）要厂长批；单张保修内服务工单服务主管就能批 | 沿用 17C 的动作框架：试运行 → 审批 → 执行 → 写回本体 |
| E1-7 | **服务方案的“推演”用排班估算，不进车间仿真**：<br>· 每位工程师每天最多 2 单（同城）或 1 单（外地），按排班日历排；<br>· 估算：几天做完、要几人天、几套备件、保修内外各多少钱、受影响客户数；<br>· 车间仿真管的是车间，现场服务不在里面；这里写成一个简单的排班计算，规则和参数写在帮助里 | 够用、可解释；以后人员领域包（E4）有了排班和资质再合并 |
| E1-8 | **服务工程师：先建 6 位虚拟工程师**（东部、南部、北部各 2 位，有区域、技能、排班），存平台自己的表；人员领域包（E4）上线后并入员工和技能矩阵 | 现在没有人员数据；先让派工跑起来 |
| E1-9 | **教学模拟器（教学模式）**：跟着数字孪生的现场天数走：<br>· 每周生成 2–3 条线索（来自展会、官网、老客户介绍），有的会转成商机；<br>· 现场设备健康度变红时，客户一定来电投诉；黄色时有一定概率；<br>· 服务完成后 1–2 天自动回访，按“响应快慢、是否一次修好”给分；<br>· 老师在教师控制台可以注入“批次投诉”情景：同一片砂轮磨的轴所在的 3 台设备在两天内陆续报问题 | 方案“每个领域包都有教学模拟器”；故事一可重复演示 |
| E1-10 | **态势卡和日报**：<br>· “市场与客户”卡：满意度（近 30 天）、开着的投诉、漏斗金额、本月成交；<br>· “客户服务”卡：开着的服务工单、平均响应时间、一次修复率、保修成本；<br>· 日报 / 周报加一节“客户与服务” | 方案第五节态势卡 |
| E1-11 | **AI 代理**：新增 3 个工具（客户 360：订单、合同、设备、投诉、满意度；投诉追溯与排查范围；服务派工估算），评测集加 8 题（客户与服务领域） | 代理能回答“港口客户最近怎么了？”“这批轴还装在谁家？” |
| E1-12 | **教学：实验 16“客户投诉的追溯、召回与服务决策”**（4 学时）：老师注入批次投诉 → 学生先自己从现场设备往回追、列出排查范围 → 在中枢里比较三个处理方案（客户数、成本、天数、风险）→ 选一个并说明理由 → 起草客户通知 → 批准、执行、看回访和复盘。自动评分 + 报告；指导书、报告模板、课程接口 | 每个工具都要能进课；比对模式沿用实验 15 |

## 八、需要 Eddie 确认的问题（附建议）

### 2. 和细则不一样的地方（施工中的偏差）

1. **备件出库用 ERPNext 出库单（Stock Entry，Material Issue），不用发货单（Delivery Note）**：备件（轴承）在 ERPNext 里是“非销售物料”，发货单开不了。
2. **合同条款存在 ERPNext 合同的自定义字段里**（违约金、响应时限、保修期，外加金额、报价单、销售订单），没有另建 `contract_terms` 表；排班也不另建 `engineer_shift` 表，由服务工单现算。
3. **新增角色“售后”**（右上角切换）：服务动作由售后、销售或厂长发起。
4. **动作是 3 种，不是 4 种**：“开服务工单”和“批量点检”合成一个“服务派工”（一张或多张，一次审批）；只派一台且在保修内的不算花钱，售后、销售也能批。“过保免费”的审批这一期没做。
5. **C3（投诉超时）没有单独的“改派 / 远程支持”预案**，和 C1、C4 用同一组三个服务方案；现场报警 V1、V2 也改用这组方案（以前它们没有预案）。
6. **情景数据补了出厂批次**：12 台情景设备分成 4 个砂轮批次（grd-01/S1–S4），否则追溯不到“同一片砂轮”。
7. **销售漏斗是按钮推进，不是拖动换阶段**；报价按参数配置器的标准售价（$1,650/台）算，没有在漏斗里打开配置器。
8. **投诉登记暂不支持扫码、拍照**（表里留了照片字段）；手机宽度可用。
9. **教学模拟器只生成线索，不会自动把线索转成商机**（留给学生扮演销售去推进）。
10. **生产模式的客户通知**：批准后有邮箱才发；合同上还没有联系人邮箱字段，现在都是“已记录，请人工联系”。“发到测试邮件服务器”的测试改为“没有邮箱不发、只记录”的测试。
11. **接口名**：`/api/service/orders` → `/api/service/jobs`；工程师不单独开接口（排班表里带出）；批次投诉注入是 `/api/teach/batch-complaint` 和 `/api/lab16/inject`。
12. **客户 360 加成了第五个标签**；合同条款是 2 级敏感，厂长、老师、销售、售后能看，其他角色只看到合同号。
